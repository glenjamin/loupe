# Loupe: goals and design decisions

Loupe is a native macOS app for reviewing GitHub pull requests. It exists because reviewing on github.com is slow for repos that vendor dependencies, and because a local app can lean on local checkouts in ways a web page can't.

## Goals

- Review PRs faster than on github.com, for one person, on a Mac.
- Vendored and generated files never get in the way: excluded from diffs by default, not merely collapsed.
- The app is usable the moment it opens, with whatever it already knows, and refreshes in the background.
- Keyboard-driven review once the basics are in place.

## Decisions

Each entry says what we chose and why, so a later change can be made knowingly. Add new ones at the end; don't rewrite old ones, note the reversal instead.

### Native app, not a browser extension

A Firefox extension over github.com would get commenting and review submission for free, but it rides GitHub's React DOM, which changes often, so it would be a maintenance tax with a low ceiling. A native app can use local checkouts, cache locally, and own its layout and keyboard model.

Complement, not alternative: a `.gitattributes` line of `vendor/** linguist-generated=true` in a repo collapses vendored files on github.com for everyone. GitHub's docs say only `linguist-generated` affects diffs; `linguist-vendored` only affects language stats.

### SwiftUI + AppKit, built with SwiftPM, no Xcode required

The machine has Command Line Tools only. SwiftPM with an executable target links AppKit and SwiftUI fine, so there is no `.xcodeproj`. Targets are split so that pure logic (`LoupeCore`, `LoupeModel`, `LoupeStore`) has no AppKit dependency and is testable headlessly.

### Diffs come from local checkouts only, never from the API

`git diff` against the checkout gives full-file context, honours pathspec exclusions (`':!vendor' ':!go.sum'`), has no rate limit and no file-count cap. The API's PR file list on a typical Go repo was 98% `vendor/` (741 files, of which 4 were real), and the REST files endpoint omits patches for large files and caps at 3,000 files.

Consequence: a PR can only be reviewed in Loupe when its repo is checked out locally. The app tracks checkout locations (see below). Checkouts are shared with other tools, so Loupe never touches branches, the index or the working tree. The one write it makes is fetching the PR head into its own ref namespace, `refs/loupe/pull/<N>/head`, so the objects stay reachable and nothing races over `FETCH_HEAD`.

For merged PRs, use the API's `baseRefOid` for the merge-base; the local default branch has moved on and the diff comes out empty. Don't rely on `FETCH_HEAD` in a shared checkout; another fetch can overwrite it.

### GitHub GraphQL for metadata; REST only where it is the better fit

One GraphQL search request returns a PR list with CI rollup, review decision, branches and author inline. The REST search endpoint returns issue-shaped objects and needs two or three more requests per PR for the same fields, and has its own 30-per-minute limit. REST is still the right tool for the whole-PR diff (`Accept: application/vnd.github.diff`, if ever needed), `POST /markdown` for GitHub-faithful rendering, and `GET /notifications`.

Known shapes, from `probe/`: CircleCI reports as legacy `StatusContext`s, not `CheckRun`s (only Codecov uses check runs), so CI handling must cover both. A review thread's `line` plus `diffSide` is a file line number, not a diff position; outdated threads have `line: null` and only `originalLine`.

### Auth is borrowed from the `gh` CLI

The app shells out to `gh auth token` per request and never stores the token. Good enough for a personal tool; a Device Flow OAuth app is the path if it's ever shared.

### A local SQLite copy is what the UI shows; GitHub is synced into it

Storage is SQLite via GRDB (migrations, record types, `ValueObservation` for live UI updates), at `~/Library/Application Support/Loupe/loupe.sqlite`. Launch shows stored rows instantly with a "refreshed N ago" label; refresh runs in the background. A failed refresh keeps the stored rows and shows a banner, never a blank list.

Rows have real columns per field, not a JSON blob, so the data is queryable. List membership (authored by me, review requested) is tracked separately from the PR row, since one PR can be in both.

DuckDB was considered and rejected for the app itself: the workload is small row-at-a-time upserts, which is SQLite's strength, and the DuckDB Swift binding lacks migrations and observation. For analytics over the history, point DuckDB's `sqlite` extension at the same file.

### Refresh is incremental after the first load

First load of a list uses `is:open`, paged to exhaustion, and reconciles fully. Every refresh after that drops `is:open` and asks for `updated:>=<last sync minus a small overlap>`, so merges and closes arrive as state changes rather than as absences. The UI filters to open PRs by default with a toggle to show closed and merged.

Fulfilled review requests are the gap: a PR you have reviewed stops matching `review-requested:@me` and never comes back to say so. A `nodes(ids:)` check over the to-review column catches those. Team-level requests are kept, since team membership isn't cheaply knowable.

### Checkout folders are chosen on first launch and searched for checkouts, whose locations live in the database

The folders checkouts are searched for under are asked for on first launch, by a banner above the lists and in the no-checkout pane rather than a panel thrown up at launch, so the lists can be read first; fixed search roots would be one machine's layout, wrong for anyone else. They're kept in `~/.config/loupe/config.json`, not the database, so they can be edited by hand or kept with dotfiles. Until they're chosen nothing is searched and there's nowhere to clone to.

A `localRepo` table in the database, which holds the app's own state, maps `owner/name` to an absolute path. Unknown repos are looked up by exact directory name under each chosen folder in turn, accepted only when the directory is a top-level git repo whose remotes point at that repo on github.com (see "A checkout matches a repo by any of its remotes"). Misses are not stored, so they retry. A stored path whose directory has gone is dropped and re-resolved.

### The diff view is one `NSTextView` with lazy layout

One attributed string per file, TextKit 1 with non-contiguous layout and no wrapping; full-width row backgrounds are painted in the layout manager, not the view, because doing it in the view silently forced layout of the whole file. A 46k-row file opens in about 150ms. Clicking a row yields `(path, side, line)`, the same anchor GraphQL review threads use.

### PRs open in tabs inside one window

Tab 0 is the PR lists and cannot be closed; each opened PR gets a closeable tab with browser-style keys (⌘W, ⌘1–9, ⌘⇧[ and ⌘⇧], ⌃Tab). Open tabs persist across launches. This keeps several reviews in flight without a window per PR.

### One window with the app's own tab strip, not native window tabs

There is one window, and directly under its unified title bar sits a strip of our own: a "Pull Requests" button first, then a tab per open PR, two rows high with the PR's title under `repo #number`. This departs from "Windows are AppKit's, not SwiftUI scenes" as far as it makes a window per PR, and relaxes "The lists tab can't be closed and stays first". Native window tabs (a window per PR grouped through a shared `tabbingIdentifier`) were used for a while, as they look right and give ⌘W, ⌃Tab, "Move Tab to New Window" and "Merge All Windows" for free, but they can't have two-row tabs, and the user wanted the lists to be a button that is always there rather than a tab. Those AppKit extras, dragging tabs to reorder them and seeing two PRs side by side in separate windows are given up for it.

The strip is in the window's content rather than the title bar, where two earlier SwiftUI strips lost their clicks to window dragging, and it's AppKit views rather than SwiftUI so a click always lands; a snapshot-run hook clicks it through the window to prove so. Each PR's view is made when its tab is first shown and then kept, hidden, so tabs keep their diffs, scroll positions and web views. The window's title and toolbar come from SwiftUI's scene bridging, from one SwiftUI view at the window's root that wraps the AppKit strip and content and declares the shown item's title and toolbar, since only the window's root hosting controller bridges them. ⌃Tab, ⌘W and the keys that pick a tab are the app's own. Closing the shown tab shows its neighbour; a middle click on a tab closes it, as in browsers; and the window has no close button. Opening a PR that already has a tab shows it. The open PRs and the shown one are stored and reopened at launch, so SwiftUI's own window restoration is off to avoid duplicates.

### The window's title and toolbar follow the shown tab, declared at the window level

The window has the tall unified title bar and toolbar. It's titled after the shown tab: "Pull Requests" for the lists, `repo #number` for a PR, with the PR's title as the subtitle. One toolbar is declared at the window level, with items that change per tab, as a toolbar or title declared by a tab's own view would come and go with the tab, resizing the title bar on every switch.

### Producing a PR's diff leaves the checkout's other state alone

Fetches pass `--no-tags` and `--no-write-fetch-head`, so the only things they change are `refs/loupe/pull/<N>/head` and, when the base commit is missing, the base branch's remote-tracking ref. Hidden paths are excluded with pathspecs, `linguist-generated` ones through `:(attr:…)` magic against the checkout's own `.gitattributes`, and a second `--name-only` diff over the same pathspecs lists what was hidden, so the count stays honest. An open tab keeps its PR row stored after the PR leaves both lists, so a tab can always be restored. A list holding rows stored before commit oids were fetched gets a full load rather than an incremental one, which fills them in.

### Long diff rows wrap with a hanging indent

Rows soft-wrap at the view's width by default, with a View menu toggle. Each row's paragraph style indents continuation lines by the gutter's width, so wrapped code lines up under the code rather than under the line numbers, as on GitHub. Wrapping stays within TextKit 1's non-contiguous layout, so opening a large file costs the same either way; row backgrounds are painted per visual line and clicks map by character offset, so neither needed changing.

### Code is highlighted with tree-sitter, parsed per hunk

Each hunk's new side and old side are parsed with the file's tree-sitter grammar and coloured from the grammar's own `highlights.scm` with Primer's palette, which is how GitHub highlights diffs, partial snippets and all. Grammars come from their upstream SwiftPM packages through ChimeHQ's SwiftTreeSitter, and a file in an unknown language stays plain. Highlightr was ruled out because it runs highlight.js's regex grammars in JavaScriptCore, a cruder approach than GitHub's; Neon was ruled out because it manages incremental re-highlighting for an editor, and this is a static render. Colours go into the layout manager's temporary attributes, not the text storage, because adding tens of thousands of colour runs to a large storage costs several times as much; files over 5,000 rows paint plain first and take their colours from a background parse.

### Grammars come from CodeEditLanguages, not one upstream package each

Grammars and their highlight queries come from CodeEditLanguages, a single package that bundles about 40 prebuilt grammars, rather than an upstream package per grammar. Each upstream manifest is maintained separately, several of their later releases fail to link under SwiftPM (so CSS, JavaScript and YAML would be held at old tags and Swift at a special one), and every new language means another dependency. One package gives SQL, Dockerfile, Markdown, Python, TOML, `go.mod` and more for free, with its own detection by extension and file name. The cost is a slightly slower prebuilt Go grammar, and a package that hasn't tagged a release since late 2024; Makefile and HCL aren't in it, so are vendored.

### Windows are AppKit's, not SwiftUI scenes

The lists window and each PR's window are `NSWindow`s made and tracked by `WindowManager`, hosting the SwiftUI views in `NSHostingController`s that carry their titles and toolbars into the window. SwiftUI keeps only the menu bar, hung on a `Settings` scene that opens no window. As scenes, the windows fought the app at every turn: SwiftUI's window controller handles `newWindowForTab:`, so the tab bar always showed a "+" that made stray windows SwiftUI then reused; its restoration duplicated the windows the store reopens; and a shared frame autosave name could be held by only one of its windows. Owning the windows removes the "+" (nothing implements `newWindowForTab:`), lets the store be the only restoration, and lets the lists window keep a frame autosave name that PR windows outside a tab group start from. A PR window joins the lists' tab group explicitly, in the stored order. As the app quits SwiftUI still closes every window, so the manager stops forgetting PRs once termination begins.

### Languages and hidden files follow GitHub Linguist, read at the head shown, except that only a root `vendor/` is vendored

Which grammar a path gets, and which paths count as documentation (hidden only if asked), come from GitHub Linguist's own `languages.yml` and `documentation.yml`, vendored from a tagged release and refreshed by `Scripts/update-linguist.sh`. Linguist is what GitHub uses, so Loupe highlights what GitHub does, without hand-maintained lists; the script converts the YAML to JSON so the app needs no YAML dependency. Languages are chosen by name alone: an ambiguous extension takes the first of its languages that has a grammar.

Linguist's `vendor.yml` isn't used. GitHub doesn't hide vendored files in a PR's diff at all, only generated ones, and the list serves language statistics, so it names ordinary source directories: its first pattern, `(^|/)cache/`, would hide a Go repo's `cache` package. Pruning it pattern by pattern kept turning up more such cases, and the one vendored case in the repos reviewed is a Go dependency tree in a top-level `vendor/`. So only paths under the repository's root `vendor/` are hidden as vendored; `node_modules/`, `dist/`, minified bundles and a nested `vendor/` are reviewed. Common lockfiles are hidden too, as is generated code, as "Generated code is also told by its first lines, as Linguist does" describes.

`.gitattributes` `linguist-*` attributes override all of this either way, as on GitHub, so `linguist-vendored` can still hide any path or keep one under `vendor/`. They're read from the `.gitattributes` files at the head of the changes shown, as GitHub reads them from the PR's head (the commit itself for a picked commit and each commit's stats, the head too for a deleted file), not the working tree's, as the checkout is the user's own, on whatever branch it was left on. `git check-attr --source=<commit>` would do this directly but needs git 2.40, and Loupe runs `/usr/bin/git`, which Command Line Tools ships as 2.39. So the `.gitattributes` blobs that could apply (one in each changed path's directory and above) are found with one `git cat-file --batch-check` for every head at once, written into a throwaway index file in the temporary directory (`GIT_INDEX_FILE`, `update-index --index-info`), and read with `check-attr --cached`, which ignores the working tree. The checkout's index, working tree and refs are untouched; `$GIT_DIR/info/attributes` and the user's global attributes still apply. Each head costs two short git runs, a few at a time across the commit picker's commits.

### The diff view reads like GitHub's

Rows are 12pt on a 20pt line, with the code padded from the edges and its column set by a tab stop after an inline gutter: right-aligned old and new numbers and a `+`/`-` marker, on a darker tint of the row. The gutter stays inline text, tagged so copies strip it, so clicks, find and copying keep working on one string. Hunk headers mute the line ranges and keep the function context in the text colour. Within a run of deletions followed by as many additions, each pair of lines is diffed by token and the changed words are tinted more strongly, as GitHub does; pairs sharing under 30% of their tokens, lines too long to diff cheaply, and changes only to whitespace (gofmt realigning a block) get no emphasis. This happens while building the attributed string, so it's measured with it. Each file sits in a bordered box under a header bar with its path and counts.

### Open PRs learn of changes from notifications, and offer a reload

An open PR's window notices when the PR changes on GitHub and says so in a banner with a Reload button, as github.com does, rather than replacing the diff under the reader or waiting for the lists' three-minute refresh. A refresh that moves the PR's head doesn't re-diff on its own: a reviewer partway through a diff keeps their place until they choose to move on.

The signal is GitHub's notifications API, polled with `If-Modified-Since`: a 304 costs no rate limit, so an idle poll is free, and GitHub's `X-Poll-Interval` (60 seconds) sets the pace, which is latency enough for review. Webhooks would be immediate but need admin rights on each repo and a process reachable from GitHub to receive them. Notifications only say which PRs to look at; the open PRs they name are then fetched in one `nodes(ids:)` query and stored, so the window compares stored rows and doesn't care which route an update came by. That lookup also fetches commit, comment and review thread counts, which the list searches don't: on a full page of 100 results they took the search to GitHub's time limit and it returned 502s, so a search keeps the counts last looked up. A token that can't read notifications falls back to that query over every open PR each minute. Notifications only cover threads the user participates in, which is every PR they've authored or been asked to review, and so nearly every PR Loupe opens. Whether a push on its own updates a notification hasn't been confirmed; if not, the lists' refresh still brings a moved head to the banner within a few minutes.

### The lists tab can't be closed and stays first

The lists are the app's home, so their window has no close button and refuses closing, including the tab bar's "Close Other Tabs", which asks the window's delegate rather than checking the button. With no SwiftUI window scene there is no File menu of SwiftUI's, so the app supplies "Close Tab" (⌘W) and "Close All" (⌥⌘W); both pass over the lists rather than beep at them. "Merge All Windows" run from a PR's window would put the lists last, so they are moved back to the first tab.

### Snapshots are how anyone sees the UI without a screen

`Scripts/snapshot.sh` builds the app, launches it as an invisible accessory process with its windows off every screen, waits for lists and diffs to load, writes a PNG per window and quits. Agents can't launch a GUI from the sandbox, so this is the only sanctioned way to run the app other than `--bench`; launching it any other way opens real windows on the user's screens.

### The PR view is one pane, with Conversation at the top of the sidebar and shown from GitHub's own HTML

A PR's sidebar is always there, with a Conversation row at the top above the commit picker and file list, and the pane beside it shows the conversation or the selected file's diff. One pane keeps the file list and commit picker in reach while reading the conversation, and switching is one click in the same place as the files; GitHub-style Conversation and Files changed tabs were tried first. The "Edit description" button of "The viewer's own PR descriptions are edited as markdown, starting from GitHub's copy" is a pencil at the trailing end of the Conversation row.

The Conversation row is drawn as a selected list row (accent background, white text) while the conversation is shown, rather than as a push button, so it reads as part of the same navigation as the files. It sits outside the file list's `List`, so the list shows no selected row meanwhile; its selection is kept, and picking any file shows the files again. The sidebar is there before the diff is ready, with only the Conversation row until the commit picker and files can be listed. PRs open on the conversation, ⌃1 and ⌃2 switch, and each PR's choice is kept. The file count is the commit picker's "All changes" row.

The conversation is one web view built from the `bodyHTML` fields GraphQL returns for the description, comments and reviews, so mentions, code blocks, tables, task lists and emoji render exactly as on github.com with no markdown engine of our own; the HTML and its styling are ours to change. The diff stays native. Known limit: images attached to private repos need a browser session and may not load.

### Viewed files sync with GitHub, and pulling past a file's end marks it viewed

A file's "Viewed" state is GitHub's own `viewerViewedState`, read and written through GraphQL (`files { path viewerViewedState }` paged to the end, as vendored files swamp the list; `markFileAsViewed` and `unmarkFileAsViewed`), so a review started in Loupe carries on at github.com and back. It's stored per PR and path so a tab shows it at once, and fetched afresh when a tab opens and on Reload. A change shows immediately and is put back if GitHub refuses it. `DISMISSED`, a viewed file changed by a later push, is flagged in the sidebar and counts as not viewed when moving on.

Moving on is a gesture like pull-to-refresh at the bottom: pulling past the end of a file's diff reveals an indicator that fills over about 80pt, gives a haptic tap when full, and letting go then marks the file viewed and shows the next file not viewed, wrapping to the top. Reaching the end is the moment a reviewer has finished a file, so the gesture costs nothing extra and needs no reach for a checkbox. Only a live drag counts, never momentum bouncing off the end, so a fling through a file can't mark it by accident; the threshold logic is a pure type, `OverscrollTrigger`, since scroll events can't be driven headlessly. ⌘↓ and `]` do the same from the keyboard and ⇧V toggles the shown file. The bare keys are handled by a key monitor that steps aside while text can be typed, rather than as menu shortcuts, which would take them from every text field.

### Each file's diff ends in a footer that moves on; pulling past it is a shortcut

Every PR file's diff ends in a footer inside the scrolled content, a bar like the file's header with a button that marks the file reviewed and shows the next one not reviewed. A pull past the end can't be the only way: a mouse wheel never pulls past the end, and on a trackpad the stretch had to be held while 80pt filled, so the user found the control hard to reach at all. The footer is reached by ordinary scrolling and clicked like any button; a file shorter than the view has it straight after its last row. The pull stays as a shortcut and fills the footer's own button rather than a separate indicator that existed only mid-stretch. The footer lives in the scroll view's clip view, placed in the document's coordinates, with a bottom content inset to make room, so the text view stays the document view and its wrapping and lazy layout are untouched.

### The conversation tab: replies come from threads, and the web view is kept

An addendum to the conversation tab's decision. GitHub's timeline omits reviews that only reply in threads, so thread replies are fetched with `reviewThreads` (bodies and authors) and shown inside the thread under the review that started it, as github.com does; a review's own comments give each thread's path, lines and diff hunk. The conversation is stored in tables per kind of row (timeline items, review comments, threads, thread comments, checks), keyed by PR and item id, and fetched on opening a PR's tab and on Reload rather than when the tab is first chosen, so it's usually there by then. The web view is made the first time Conversation is chosen and kept hidden behind the files after that, as is the diff behind it, so neither loses its place. The page is assembled in Swift rather than by a script in the page, so it runs with no script at all under a Content-Security-Policy that loads only GitHub's images. ⌃1 and ⌃2 switch, since ⌘1–⌘9 pick window tabs.

### Hidden files are listed, and diffed only when shown

Vendored, lockfile and generated files stay out of the main `git diff`, as a vendor tree can be enormous and would slow every diff, but they are listed under their own "Vendored, lockfiles and generated" section below the files to review, as a reviewer sometimes needs to check a dependency bump or a regenerated file. Listing them keeps them free until opened, which was the reason for leaving them out. Their change kinds come from the same `--name-status` listing that decides what's hidden, so they cost no extra git run. Each one is diffed on its own, by literal pathspec (with a rename's old path, so the rename is kept), only when selected, and kept in memory. Until then its row says "added", "modified" and so on in place of line counts, rather than running `--numstat` over a whole vendor tree for counts nobody may look at. Their reviewed state is GitHub's, as for any file, but moving on and the reviewed count pass over them, so the review keys never walk a reviewer through vendored code.

### A commit picker shows one commit's changes, listing each commit's whole first line and diff-stat

As on github.com's "Files changed", a picker above the file list shows "All changes" or one of the PR's commits. The commits come from `git log <merge-base>..<head>` in the checkout, not from GitHub, so they always match the diff shown. A commit's changes are from its first parent, or the empty tree for a root commit, and are diffed when first picked and kept per tab; a range names its commits, so a cached diff can never go stale. Reloading goes back to "All changes". Reviewed state stays per path, as GitHub keeps it, whatever is shown.

The picker is a button naming what's shown that opens a popover, about 480pt wide, with a SwiftUI `List` of "All changes" then each commit, oldest first: its whole first line, wrapping if long, over its diff-stat (`3 files  +42 −7`) and short oid. A menu would cut each title to its width and say nothing of how big a commit is, which is what a reviewer weighs when choosing whether to step through commits, as github.com's commits dropdown shows; it stays native rather than an `NSMenu` of custom views. The shown choice is ticked and starts highlighted; a click picks and closes, and the arrow keys move with Return picking, so moving through the list doesn't diff each commit passed.

The stats count only the files to review, as the "N of M reviewed" count does, leaving out hidden vendored, lockfile and generated files. The whole PR's comes from its parsed diff at no cost; each commit's from `git diff --numstat` over its range, so it matches that commit's diff, a few runs at a time, with one `git check-attr` over all their paths to decide what's hidden. They're counted when the commits are first shown on the Files tab rather than when the popover opens, so it opens complete: over 30 commits of this repo it took about 165ms, in the background. They're kept per tab by range and dropped when the diff is produced again. A binary file counts as a file with no lines.

### Pulling past the footer is pull-to-refresh: held past the end, counted at half rate, fired on release

Pulling past a file's footer marks it reviewed, as the pull-to-refresh pattern the user expected. Progress is the finger travel of a live drag past the end, not the view's own movement, so damping plays no part. Crossing the target arms it: one haptic tap, the footer's button full and green, and the hint saying what letting go will do ("Release …" for "Pull …"). Pulling back under the target disarms it. It fires only when the fingers lift while armed, once per gesture; lifting short or a cancelled gesture does nothing, and the fill empties. Momentum never counts, so a fling into the end can't fire it, and a mouse wheel has no pull at all, using the footer's button or ⌘↓ and `]`.

The start of a pull has to cost something, as an ordinary trackpad scroll that reaches the end with the fingers moving spends the rest of its travel past it, easily 80pt. So counting starts only once the fingers have been past the end for 200ms within the same drag, and beyond a 40pt lead-in, like a touch slop; travel during the dwell is spent. A swipe that runs through the end and lifts within the dwell never arms, however far it travels, and pulling back to the end starts the dwell over. Counted travel goes in at half rate towards a 64pt target, `SwipeRefreshLayout`'s numbers (AOSP: `DRAG_RATE = 0.5`, a 64dp target, firing on release), so a deliberate pull arms after about 168pt of finger travel; at half rate the fill keeps to about the pace of the damped rubber band, so it reads as resisting, where full rate to a larger threshold would arm at the same distance. `UIRefreshControl` also needs well over 100pt, and MacPullToRefresh (an AppKit implementation) fires only if still past its line at release. None has a time component, but none has to tell a pull from the tail of a trackpad swipe. MacPullToRefresh's filling to the pull's peak isn't taken: finger travel doesn't jitter as the clip view's bounds do, and a fill held at its peak would show green when letting go won't fire. The constants sit at the top of `OverscrollTrigger`, to tune by feel; event timestamps feed the dwell, so it's tested headlessly.

Tried and dropped: measuring the rubber band's stretch, which AppKit damps to a fraction of the finger's travel, so it was too hard; and unresisted slack below the footer that fired mid-drag, which any drag running past the end set off.

The progress fills the footer's button inside its rounded bezel, accent while filling and green when armed, with a button style of its own drawn like a large push button. The hint, worded for the case at hand (moving on, the last file, or already reviewed), sits below the end, shows only during a live drag and stays empty through the dwell and lead-in.

### A checkout matches a repo by any of its remotes

A fork's checkout has the fork as `origin` and the repo it came from as another remote, often `upstream`, and PRs to that repo were reported as having no checkout. So a checkout now matches a repo when any of its remotes points at it on github.com, whether found by name under the search roots or located by hand. When one directory per search root is a candidate, one whose `origin` is the repo wins over a fork's, so a plain clone is preferred. Fetching a PR uses the checkout's remote for the PR's repo (`origin` if several match) for both the PR's ref and the base's remote-tracking branch, still writing only under `refs/loupe/`. The remote is looked up again at fetch time with one git call rather than stored beside the path, so the store is unchanged and a remote renamed since stays right. Remote URLs are read as configured, before any `insteadOf` rewrite, since that's what names the repo.

### Checks show as a bare glyph whose hover popover lists each check, looked up by id in small batches

A PR's overall check state is a plain coloured tick, cross, clock or question mark, with no filled circle, as the filled symbols were the loudest thing in a row. Resting the pointer on it opens a popover like github.com's: a summary line ("2 of 5 checks failed"), then a row per check, failing first, then pending, then the rest in GitHub's order, each with its coloured status glyph, its name, and its description in secondary caption type (a check run's title, where Codecov puts its coverage). A row with a link opens it in the browser and shows a pointing hand. Until the contexts have been looked up it names only the overall state. The summary and ordering are pure functions in `LoupeModel`, tested without a UI. A native tooltip was tried first: it takes about a second to appear and is plain text, so a reviewer scanning the lists waited on it and couldn't follow a check to its page.

The rest is 120ms, longer than the pointer takes to sweep across the glyph; if the glyph has moved by the end of the wait, it was scrolled under a resting pointer, and the wait starts again. The popover stays while the pointer is over it, so its links can be clicked, and goes 150ms after the pointer has left both glyph and popover, enough to cross the arrow, or at once on a click elsewhere or once a link is opened. `NSPopover`'s own animation, about half a second each way, is off, and the popover's window fades in and out over 80ms instead, as no animation at all popped in and out too abruptly. It's the only popover opened by hovering; the reviewers, avatars and other hover text are native tooltips, and popovers opened by a click keep `NSPopover`'s animation. It's an `NSPopover` from an `NSViewRepresentable` anchor behind the glyph rather than SwiftUI's `.popover`, so the anchor's own tracking area times the rest and the window it was shown from is made key again if the popover took it, as hovering must not move the keyboard from the list or diff. The rows aren't focusable, so none shows a focus ring.

The per-check contexts and merge state come from a lookup by id, not from the list searches: asking the searches for contexts took a 100-PR search from about 7.5s to 8.4–9.6s, and a denser one to GitHub's 502 at about 11s. A check finishing doesn't change a PR's update time (19 of 44 of the author's PRs had a check finish after it), so the searches for changes never report it, and the lookup runs after each list refresh over every open PR stored, listed or only open in a tab. Its cost goes with how many checks a batch carries: with 160 open PRs, a batch of 50 failed every time with a 502 or `RESOURCE_LIMITS_EXCEEDED` on each check run's `detailsUrl`, while batches of 10 took 1–4s. So a batch is 10 PRs, 4 asked at once, which brought those 160 to about 23s, against 48s one batch at a time. Each batch is stored as it lands, so one GitHub gives up on leaves only its PRs as last looked up. The rollup state comes from the same lookup, so the glyph and its popover agree. Contexts are stored per PR in their own table, replaced on each lookup; only the first 50 of a commit are fetched. The refresh counts as loading until the checks are in. A PR looked up directly in neither list shows its stored row, with the copy in memory from that lookup standing in only until the stored row is read back, so status lookups reach its tab.

### Conflicts show as a badge, from the same lookup by id as checks

A PR whose branch conflicts with its base gets a quiet "Conflicts" badge beside its state badge, in the lists and in the PR header; nothing shows for a clean merge or while GitHub is still working it out. The state is GitHub's `mergeable`, which GitHub computes lazily in the background and answers `UNKNOWN` until it has, so a freshly pushed PR may show nothing until a later refresh.

It's asked for in the lookup by id that fetches checks after each refresh, not in the searches. Measured on a full page of 100: adding it to the author search took it from about 7.5s to 8.5–9.5s, the denser 100-PR search hit a 502 again, and 67 of the 100 came back `UNKNOWN`. In the lookup it raised a batch of 50 from about 2.6s to 3.6–4.9s, within the limit, and answered for all 50 there, though a lookup can still meet `UNKNOWN` on a PR GitHub hasn't got to. The searches and the by-id row lookup leave the stored value alone, so it's only replaced by the next status lookup.

### PRs open on the Conversation tab

A PR's tab now opens on Conversation rather than Files changed, reversing the earlier default. The description and the discussion so far say what a change is for and what's still open, which is what to know before reading its diff, as github.com's own default page assumes. The tab shown is still kept per PR while the window lives, so switching to Files changed sticks.

### Hidden files show their line counts from the start

Each hidden file's additions and deletions come from `git diff --numstat` over the paths hiding them, run beside the main diff, so the hidden section shows `+N -M` like the files to review without producing their diffs. On atrium vendor bumps of 1,000 to 2,400 files it took about 80ms. A row still says added, deleted or renamed, which the counts alone don't, and a binary file says so rather than `+0 -0`.

### Reviewers show in the header on the viewer's own PRs, where they're asked and withdrawn

On a PR the viewer wrote, the header's right side lists its reviewers as github.com's sidebar does: everyone asked and not yet answered, then everyone else's latest review (approved, changes requested, commented or dismissed), each with a plain symbol rather than a filled badge so the header stays quiet. Someone asked again after reviewing shows as asked. The author's own reviews, which are their replies to threads, aren't listed, nor is an unsubmitted one. Two columns of up to three rows fit beside the title; beyond that the last place says how many more, with their names in its tooltip. The data comes with the conversation (`reviewRequests` and `latestReviews`), is stored with it and shown from the store at once, so it refreshes when the conversation does. Whether the PR is the viewer's is decided by its author's login against the viewer's, which the lists store; a tab looks it up itself if nothing has yet.

A button there opens a picker of the repo's assignable people and, for an organisation's repo, its teams; a token that can't read teams still finds people, and that failure isn't shown. As on github.com, everyone asked and not yet answered is listed first, in GitHub's order and ticked, then the candidates, all filtered as typed. Choosing someone unticked calls `requestReviews` with `union: true`, so others already asked stay asked; anyone who has reviewed and isn't asked shows unticked, so choosing them asks again, as github.com's re-request does. Choosing a ticked reviewer withdraws their request. Either change shows at once, is put back with GitHub's reason in the popover (or, once it's closed, as a warning symbol beside the reviewers) if GitHub refuses, and once GitHub agrees the conversation is fetched again and the PR's row follows, so its TODO step does too. Requests aren't queued or retried: asking someone notifies them, so a failed request is left for the viewer to make again.

GraphQL can't withdraw one request: its only way is `requestReviews` without `union`, which replaces the whole set and would drop anyone asked meanwhile, from github.com or another tab. So withdrawing is REST, `DELETE /repos/{owner}/{repo}/pulls/{number}/requested_reviewers`, naming people (and bots) by login and teams by their slug alone. It touches only the request: someone asked again after reviewing goes back to showing their earlier review, an approval included, as unticking them does on github.com. Dismissing a review is a separate act and isn't offered.

### Markdown files can be read rendered, by GitHub's own renderer

A PR's file that Linguist takes for Markdown has a "Source | Rendered" toggle in its header, Source by default. Rendered shows the file at the head of the shown changes (the whole PR or the picked commit), or for a deleted file at their base, read from the checkout with `git show <oid>:<path>` and rendered by GitHub's `POST /markdown` in `gfm` mode with the repo as context, so it reads as on github.com without a markdown engine of our own, as the conversation does. It's shown in a web view with the conversation's template, stylesheet and Content-Security-Policy (no scripts, only GitHub's images), and links open in the browser. Relative links resolve against the file's directory on github.com at that commit, which suits links to other files; relative images then point at an HTML page and don't load, as private repos' images wouldn't anyway. `gfm` mode renders a soft line break as `<br>`, as comments show it, so the file layout hides `<br>` inside paragraphs, which a file view on github.com shows as a space; an explicit hard break is lost with them. `markdown` mode was rejected as it drops task lists and the table markup GitHub uses. Each rendering is kept per file and commit while the tab lives, so toggling back is instant, and the toggle's choice is kept per path. The rendering covers the diff rather than replacing it, so the diff keeps its scroll position; the review footer is the diff's, so moving on from a rendered file is by the keys or the header's checkbox. Change highlighting within the rendered view, GitHub's rich diff, isn't attempted: it would mean diffing two renderings' DOMs.

### Web views stay in GitHub's light theme

The conversation tab and rendered markdown files use GitHub's own HTML, which carries dark-theme variants, and the page's stylesheet had a dark palette behind `prefers-color-scheme: dark`, so both followed the system appearance. The user prefers reading them in GitHub's light theme, so the stylesheet keeps only the light palette and the web view's appearance is pinned to aqua, which is where WebKit takes `prefers-color-scheme` from. The native diff and chrome still follow the system.

### Wrapped rows hang two columns in from the code

An addendum to "Long diff rows wrap with a hanging indent": a continuation that started exactly on the code column was easy to read as a new line, so wrapped lines now hang two character widths further in, as editors do.

### The viewer's own PR descriptions are edited as markdown, starting from GitHub's copy

On a PR the viewer wrote, decided by login as for reviewers, an "Edit description" button sits at the trailing end of the Conversation / Files changed row while the conversation is shown. It swaps the web view for a native editor in the same place: a plain `NSTextView`, monospaced, with spelling, smart quotes, dashes, text replacement and link detection off, as it holds markdown that GitHub renders and any substitution would change what's sent. Below it a caption says the description is GitHub-flavoured markdown, beside Cancel and Save; ⌘↩ saves and Esc cancels, the text view taking both itself so they work while typing. Save is disabled until the text differs, and Cancel with changes asks before dropping them. There's no preview: saving shows GitHub's own rendering, as the conversation is fetched again straight after, and a second renderer of our own could disagree with it.

The editor starts from the description fetched afresh from GitHub when it opens, not the stored copy, because descriptions are also edited on github.com, where images are uploaded and links added, and saving a stale copy would silently undo that. If that fetch fails the editor says so and offers Retry, rather than falling back to the stored copy. The raw `body` is still fetched and stored with the conversation, so it's at hand, but is never what's edited. Line endings are made newlines when the editor opens, since a description typed in a browser can come back with `\r\n` and would otherwise count as changed before anything was typed. Saving calls `updatePullRequest` with the body alone; a refusal keeps the editor open with its draft and the reason. A change made on github.com while the editor is open is still overwritten by saving; checking for one first was left out until it bites.

### The viewer's own PR shows "Self-reviewed" once every file to review is marked viewed

The author wanted a way to mark their own PR as ready for others to review, and reviewing it themselves in Loupe is that moment. So on a PR the viewer wrote, once every file to review (not the "Vendored, lockfiles and generated" section) is marked Reviewed, a quiet green "Self-reviewed" badge shows beside the state badge, in the lists and in the PR header. A file changed by a later push (`DISMISSED`) counts as not viewed, as when moving on. Whether the PR is the viewer's is decided as for its reviewers, by the author's login against the viewer's.

It's knowledge only Loupe has, derived from GitHub's viewed state plus the local diff: which files are to review comes from the diff, so producing a PR's diff records its reviewable paths beside its head commit, replaced with each diff. The badge needs that head to be the PR's current head, so a push clears it until the new diff is produced and its files reviewed. The lists show it from the store with no network, so a PR never opened in Loupe shows nothing; the header follows the viewer's marks as they're made. It does nothing on GitHub: no draft to ready, no label, no review request. Whether it should is left for later.

### Who could review is fetched once a run per repo, and filtered as you type

Searching GitHub (`assignableUsers(query:)` and the org's teams) after each pause in typing made every search in the request-a-review popover wait on two round trips. Instead a repo's assignable people and its org's teams are fetched once a run, all pages of 100, kept in memory by `owner/name` and shared by every tab, and the popover filters them locally on login and name, ignoring case, as each key is typed. The repos I review have about 16 to 21 assignable people and the org 8 teams, so it's one page of each. Opening the reviewers on one's own PR starts the fetch, so the popover usually opens full; a fetch already on its way is shared, and one that fails isn't kept, so opening the popover again retries. A refusal to read teams still leaves them out quietly and the people are kept; any other failure fails the fetch rather than being taken as no teams. They're not stored, so someone joining a repo shows up on the next launch.

### Grammars CodeEditLanguages lacks are vendored as C targets

CodeEditLanguages has no Protocol Buffers grammar, and the repos I review have many `.proto` files, so that grammar is vendored as its own SwiftPM C target, `TreeSitterProto`: upstream's generated `parser.c` and headers, unmodified, with its `highlights.scm` as the target's resource. It's coder3101/tree-sitter-proto, which nvim-treesitter uses and which is maintained, at a tagged release; mitchellh's and treywood's grammars haven't changed since 2021 and 2023. Its query uses the standard capture names the highlighter already maps, and its parser's ABI is within what the resolved tree-sitter runtime accepts. A generated parser is plain C with no build step, so vendoring it avoids the separate upstream SwiftPM manifests that "Grammars come from CodeEditLanguages" moved away from. `Scripts/update-tree-sitter-proto.sh <ref>` re-fetches it, records the tag and commit in `VERSION`, and prints the parser's ABI to check. Scalar types (`string`, `int32`) take the keyword colour, as the query marks them built-in types; as with other grammars, a hunk starting inside a `message` can leave its first fields' types plain. Its query is found the way CodeEditLanguages' are, in its resource bundle beside the executable or in the app's `Contents/Resources`, where `Scripts/bundle.sh` already copies every bundle. Another missing language (HCL, Makefile) would be added the same way.

### Hidden context is expanded from the checkout, with GitHub's arrows

Hunk headers carry GitHub's expand arrows in their gutter: ↑ reveals 20 lines above a hunk, ↓ 20 below the hunk before, ↕ closes a gap of 20 lines or fewer in one go, and a row after the last hunk reveals 20 more towards the file's end. 20 is GitHub's step. A gap that closes merges its two hunks, keeping the earlier header's function context, and headers are recounted so they stay true to their lines. The arrows are characters in the gutter, not SF Symbols, as the gutter is text; they're tagged like the line numbers, so copies leave them out, and carry a tooltip and a pointing-hand cursor. They act on the first click even in an inactive window, as buttons do.

The lines come from the file at the head of the changes shown, the PR's head or the picked commit, read with `git show` once per file and commit and kept while the tab lives, rather than by diffing again with more context: lines outside hunks are the same on both sides, so the new side's text and the offset the changes before them leave give both line numbers, and the change is a pure function on the parsed diff that tests can check against `git diff -U` with the whole file. The file is read when shown so the end-of-file row can be offered; until it's read, only the arrows that don't need its length show. Added, deleted and binary files have nothing to reveal. What's revealed is kept per file and range, so moving between files or commits keeps it, and producing the diff again drops it, as the lines it was revealed around may have moved. The clicked arrow's row holds still on screen while the lines arrive, so another click reveals more; when the gap closes and the row goes, the code next to it holds instead. Revealed rows are ordinary context rows, so they're highlighted with the rest of their hunk.

### The file list marks a viewed file with a tick before its counts, not a checkbox

A file's row shows no checkbox to mark it reviewed: a control that appears on hover in a row that is also a selectable, dimmable list item read as odd. Marking stays with ⇧V, the diff header's checkbox, the footer's button and pulling past the footer. A viewed file has a tick at the trailing end, just before its `+A −D`, in a slot kept empty when it isn't viewed so marking a file doesn't shift the row. There it reads with the numbers as another fact about the file, where a leading slot set it apart, ahead of a name it pushed right.

The leading space stays, empty, as wide as a directory's chevron, so a file's document symbol lines up with its sibling folders'. Without it, folders sat the chevron's width left of their sibling files, as in Finder and on github.com, but those step in about a chevron's width a level; at 12pt a file then sat left of its own parent folder's symbol and read as the parent's sibling.

Directory rows can't be selected, by click or by the arrow keys. The tree tags each row with its id, a string like a file's path, so a directory row is marked selection-disabled; otherwise the arrow keys stopped on it, leaving "No file selected". A click on one only folds or opens it.

### Checking the header's Reviewed box moves on

Checking the diff header's Reviewed box marks the file viewed and shows the next file not viewed, as the footer's button, pulling past the footer, ⌘↓ and `]` do. Ticking it is the same act as finishing the file, so it moves on like the other ways of marking rather than leaving the reviewer to move on by hand. Unchecking it stays on the file, since taking a mark back means there's more to look at there. ⇧V still only toggles the shown file, for marking or unmarking without moving.

### Generated code is also told by its first lines, as Linguist does

Linguist's `generated.rb` decides "generated" mostly from content, so a `.pb.go` file that `protoc-gen-go` wrote is collapsed on github.com because of its `// Code generated … DO NOT EDIT.` line, and naming rules alone would list it for review. `GeneratedCode` ports every rule of `generated.rb`, at the release `VERSION` names, that looks only at a file's first lines, each under Linguist's name with its extensions, line counts and strings or regexes unchanged: `generated_go?` (a line starting `// Code generated ` in the first 40, so it also catches mockgen, stringer and the rest), protoc's and Thrift's output, generated HTML, source maps, parser generators and about twenty more, plus the first-line test of `compiled_coffeescript?`. Linguist has no rule for Swift, so a `.pb.swift` stays in review, as on github.com.

Rules needing the whole file or its end aren't ported: `minified_files?` (average line length over every line), `has_source_map?` and `vcr_cassette?` (the last lines), `generated_net_docfile?` (the second-last line), `generated_postscript?` (a scan of all its data) and `compiled_coffeescript?`'s scoring of every line. Each would mean reading whole files, often large ones, for little. The path-only rules of `generated.rb` (more lockfiles, `.idea/`, `Pods/` and so on) are a separate question and aren't taken.

The content is read from git, not the working tree, since the checkout may be on any branch and is the user's own: the file as the range shown leaves it (the PR's head, or the picked commit), or for a deleted file as it was at the range's base. Only paths whose name brings in a content rule, and that path rules and attributes haven't already decided, are read, all in one `git cat-file --batch` per diff (and one for all of the commit picker's ranges), keeping each file's text only up to the last line its rules read. A `.gitattributes` `linguist-generated` either way still wins, and such a path is never read. A file hidden by its content is hidden exactly as one hidden by its path: out of the diff, in the hidden section with its line counts, out of the review count, the reviewable paths recorded for the Self-reviewed badge, and the commit picker's stats. On atrium, reading all 569 non-vendored files that have a content rule, 6.5MB, took about 130ms in a debug build, git itself about 50ms; a PR's few dozen such files cost a few milliseconds.

### Review threads show inline in the whole PR's diff, as native views over reserved rows

Each review thread shows under the line it ends on in the file's diff, as on github.com: its comments in order, each with its author, a relative time and its body. A thread over several lines notes the range in its header. The anchor is GitHub's own `line` on `diffSide`, a file line number on the head (RIGHT) or base (LEFT), so a comment on a deleted line sits under that line; it's matched against the rows' line numbers, so lines revealed around a hunk can bring a thread into place. Threads with nowhere to go, outdated ones (`line` is null), those on the whole file, and those on a line the diff doesn't show, are listed after the last row under "Not on the current diff", each with the end of the diff hunk it was made on, so nothing is lost. A resolved thread is one quiet line, "Resolved · N comments · login" naming who started it, until clicked; a hidden comment is a line saying so until clicked. What's opened stays open while the tab lives. The file list shows each file's unresolved count beside its name, hidden files' included, and the reviewed count is untouched.

Threads only show on "All changes". GitHub anchors a thread to the PR's current diff, and a single commit's diff numbers its lines differently, so a thread placed there could sit on the wrong line; with a commit picked, neither the diff nor the file list shows any.

The diff stays one `NSTextView`, which "What I'd change in the plan" named the risk. Each block of threads gets an empty row of its own height in the attributed string, a one-line paragraph with a fixed line height, and an `NSHostingView` is laid over that row as a subview of the text view, so it scrolls with the text and the lazy layout, wrapping, find and copying of the code are untouched. The row is tagged as gutter, so a copy across it leaves it out, as it does the line numbers. The SwiftUI view reports its natural height for the width it's given and the row's paragraph is changed to match, which moves only what's below. Rejected: TextKit 2 attachment view providers, as the view is TextKit 1 for its row painting; and a text view per hunk with views between, which breaks selection across hunks. Placing a block lays out the text above it, so a thread near the end of a very large file costs a whole-file layout when shown.

Bodies are GitHub's `bodyHTML`, read natively into paragraphs with bold, italic, code and links, code blocks, quotes, list items, table rows and rules, and shown as SwiftUI `Text`, whose links open in the browser. A web view per comment was ruled out as heavy, and `NSAttributedString`'s HTML import because it runs WebKit on the main thread and fetches images; here images become links to themselves, so nothing is fetched to show a comment. Threads come with the conversation, which now asks each thread for its anchoring (`startLine`, `diffSide`, `originalLine`, `originalStartLine`, `subjectType`), who resolved it, what the viewer may do with it, its first comment's `diffHunk`, and each comment's REST `databaseId` and `minimizedReason`; they're stored with it, so they show at once and refresh when it does.

### Replies post at once over REST, and resolving shows before GitHub agrees

Each thread the viewer may reply to has a Reply button that opens a plain-text field under it, with the description editor's conventions: markdown as GitHub takes it, ⌘↩ sends, Esc cancels, and cancelling with text asks first. A reply posts at once, as github.com's "Add single comment" does, not into a pending review, since submitting reviews isn't built. It goes over REST, `POST /repos/{owner}/{repo}/pulls/{number}/comments/{comment_id}/replies` naming the thread's first comment by its REST id: GraphQL's `addPullRequestReviewThreadReply` takes only an optional "pending review to which the reply will belong", so whether it posts at once, or joins a pending review the viewer already has, isn't documented, while the REST endpoint is the long-standing way to reply. Whether the REST reply also behaves when the viewer has a pending review on the PR hasn't been tried; no mutation was run live. A refusal keeps the draft open with the reason under the thread, as the description editor does.

A thread's header has Resolve conversation or Unresolve conversation, whichever GitHub says the viewer may (`viewerCanResolve`, `viewerCanUnresolve`), through `resolveReviewThread` and `unresolveReviewThread`. The change shows at once and is put back with the reason if GitHub refuses, as viewed files are; a thread resolved here folds to its one line, as on github.com. After a reply or a change, only the PR's review threads are fetched again, in one query rather than the conversation's paged timeline, so the thread shows as GitHub has it, and stored. Drafts and errors are kept per thread while the tab lives, so moving to another file and back doesn't lose them.

### New comments start from a "+" in the gutter, on a line or a selected range, wherever GitHub can place the lines

Hovering a row of a diff that takes comments shows a small accent "+" over the start of its gutter, as github.com does; clicking it, or middle-clicking the row, opens a field under the row with the reply's conventions, "Insert a suggestion" included. The "+" is an `NSButton` the text view places itself on mouse movement, from a tracking area over its visible rect, so it costs nothing until the pointer moves. Unchanged lines take comments on the new side, as on github.com. Hunk headers and the row after the last hunk offer no "+". Lines revealed around a hunk take comments on the new side with their new line number, as github.com's Files changed page allows after expanding; GitHub's docs don't settle whether the REST endpoint takes a `line` outside the diff's hunks (they call `line` "the line of the blob in the pull request diff", and the September 2025 changelog for comments on unchanged lines says "API support is currently limited"), so it's offered and tried live, and a refusal shows under the draft as any other does.

A comment posted at once is REST, `POST /repos/{owner}/{repo}/pulls/{number}/comments` with `commit_id`, `path`, `line` and `side`, because GraphQL's `addPullRequestReviewThread` is documented as adding to a pending review. `commit_id` is the head of the diff shown rather than the PR's latest head, as the line numbers are that diff's; when the PR has moved on, the banner offers a reload. After posting, the threads are fetched again, so the comment shows as GitHub has it, under its line. Only one new comment is open at a time: clicking another row's "+" moves an empty one there but leaves one with text where it is, so nothing typed is lost without asking. A comment being written stays with the changes it was started on: picking other changes hides it, and going back shows it again.

The whole PR's diff takes comments, and so do one commit's changes, as github.com allows and a commit-by-commit review wants: the comment goes with that commit as `commit_id` and its line numbers. How GitHub numbers a comment on an older commit isn't documented (only that an older `commit_id` "may render your comment outdated") and wasn't tried live, but a line on the new side is the same in that commit's diff whichever way GitHub reads it, so every added and unchanged row takes comments. A deleted line is numbered in the base, so deleted rows take comments only on a commit whose parent is the PR's merge base, where the commit's base and the PR's are the same. The changes since an earlier head are commented on as a commit's when they're exactly one commit's, its parent as anchor and the commit as head. Otherwise, whatever they start from, rebased replays included, they end at the head, so their new side's numbers are the head's and a comment there goes on the head exactly as one on the whole PR's diff does, at once or into a review, ranges included; their deleted lines take none, being the earlier head's, which GitHub doesn't number, and nor does a file the PR doesn't change. Changes that don't end at the head, such as a force-push's from the conversation, take none.

Threads show on a commit's changes when GitHub says they were made on that commit, the first comment's `originalCommit`, stored with each thread, under their original line on their first line's side (`startDiffSide`), as github.com shows them, and are replied to as anywhere. A thread made on the whole PR's diff has the head at the time as its original commit, so the head commit's changes show those whose lines it changes; threads made on other commits belong to the whole PR's diff, where they show outdated or on their line as GitHub reports. The changes since an earlier head that end at the head show the head's threads on their lines, without the "elsewhere" list of threads not on its lines.

A comment on several lines is picked as on github.com: a press on a row's "+", or anywhere in the gutter of a row that takes comments, picks lines rather than text, dragging up or down tints the rows from the pressed one to the pointer in github.com's yellow, and letting go opens one comment on them all; a press without a drag opens one on that line. Shift-clicking a row's "+" or gutter while a comment is open stretches it from the far end of its lines to that row; a comment with text in it isn't moved. Selecting text across rows and then clicking the "+" or middle-clicking a row within it also comments on the selected rows, from the first that takes comments to the last. The press goes to the "+" when it's under the pointer, which hands the press, drag and release to the text view, and the "+" stays shown through the drag, as a hidden view stops getting the drag it started. Copying is unaffected, as the gutter is never copied.

A range is posted with `start_line` and `start_side` (or `startLine` and `startSide` into a review). GitHub's docs don't state the rules for a range, so Loupe keeps to the case it can be sure of: one hunk of the diff as produced, start before end, possibly from a deleted line to an added one. A drag goes only as far as that allows, asking the tab with `commentRange(from:to:)`, the same check starting the comment makes, so the tint never shows more lines than the comment gets; a selection across hunks or onto revealed lines comments on the clicked row alone. While it's written, the range's rows are tinted, the card says "Comment on lines 12–18" (marking either end "(old)" when it's a deleted line), and "Insert a suggestion" takes the new side of every line in it. A thread on several lines names its range the same way. The "+" and the threads and comment cards laid over the rows are among the text view's accessibility children, which a text view leaves out, so VoiceOver and the UI suite can reach them.

### The viewer's own PRs can be merged from the header, with merge commits only

On a PR the viewer wrote, decided by login as for its reviewers, a Merge button sits under the reviewers while it's open, and goes once it's merged or closed. It only ever makes a merge commit, as the user never wants squash or rebase, so there's no method to pick and the repo's merge settings aren't fetched; a repo that doesn't allow merge commits refuses the merge, and GitHub's message shows like any other refusal. On anyone else's PR the place stays empty, kept for review controls.

Whether it can be merged is GitHub's own merge-box verdict, `mergeStateStatus`, rather than one worked out here from checks, reviews and conflicts: only GitHub knows the base branch's protection rules, which checks are required and whether pre-receive hooks apply, and recomputing those would drift from what github.com says. It's asked for, with `reviewDecision`, in the lookup by id that already fetches checks and `mergeable` after each refresh, stored in its own column, so it costs no extra request and is as fresh as the checks. The button is green and enabled for `CLEAN`, `HAS_HOOKS` or `UNSTABLE` (failing checks that aren't required) with the review decision `APPROVED`, and red and disabled otherwise with the first reason that applies, in this order: "Conflicts with <base>" (`DIRTY`, or `mergeable` `CONFLICTING`), "Changes requested" or "Not approved" (any other review decision, none included, as only approved PRs are merged from here), "Checks failing" (`BLOCKED` with a failing rollup) or "Blocked by branch protection" (`BLOCKED` otherwise, such as required checks still running), "Draft", then "Behind <base>" (`BEHIND`). GitHub answers `BLOCKED` for a draft, `DRAFT` being deprecated, so a draft is told by `isDraft` and given as the reason rather than branch protection. `UNKNOWN`, or a PR not yet looked up, gives a plain disabled button with no reason while GitHub works it out. A disabled button loses its tint, so the red is carried by a symbol beside the reason.

Clicking asks first, naming the branches ("Merge grpc-cache-status into master?"), then calls `mergePullRequest` with `mergeMethod: MERGE` and `expectedHeadOid` set to the head last looked up, so a push between that lookup and the click is refused by GitHub rather than merged unseen. A spinner shows while it runs. Once merged the PR is looked up again by id, so the header's badge says Merged, the lists update and the button goes; a refusal shows GitHub's message under the button. The head branch isn't deleted: GitHub's "Automatically delete head branches" repo setting does that where a repo wants it, and Loupe doesn't second-guess it.

### A hunk is parsed led by the line its header names

A hunk that starts inside a declaration lost most of its colours. Parsed alone, a TypeScript type's members or a Go struct's fields read as labelled statements or broken code, and the highlights query doesn't colour those. In PRs reviewed in Loupe, porter's `src/config.ts` had no colours at all, and Go struct, Ruby class and YAML list hunks lost their keywords and keys. Git's hunk header already names the enclosing line (`@@ -122,7 +122,6 @@ export type grpcServiceConfigs = {`), so each hunk's sides are parsed with that line in front, parsed but not shown. It's git's nearest line that starts a declaration, not one known to enclose the hunk: when that declaration closed before the hunk, the line nests what follows inside it. So a side is parsed both ways over its first lines, and in full whichever way colours more of them, ties going to the header's line. A line git cut short at its 80-byte limit is never used, as half a signature makes the code after it parse as parameters, and colours more for it. Across 960 hunks from recent merges and PRs in the repos I review, 38 hunks gained colour and none lost any correct colour (some `go.mod` hunks lost a keyword colour wrongly given to `go` inside module paths). On the bench, highlighting a Go file of 63 short hunks went from 31 to 47ms, and a TypeScript file of 51 hunks from 147 to 158ms. Parsing the whole file instead, as a checkout allows, would also colour hunks inside a multi-line string, such as a GraphQL template literal, which the header can't help with, as tree-sitter can't make an unterminated template string. That needs both versions of each file read before the first paint, so it's left for now.

### Codecov's coverage failures don't make a PR's checks fail

GitHub's rollup read as failing on most PRs because of Codecov alone: its project check fails on tiny drifts in total coverage that nobody acts on, and its patch check's target is set too high in these repos, so a well-tested diff still fails it. So a failed `codecov/project` (name in any case) is tolerated, and so is a failed `codecov/patch` while the diff coverage that leads its description ("76.92% of diff hit (target 98.23%)") is at least 70%, Glen's threshold for a diff worth a look. A patch check whose description is missing or doesn't parse still fails, as do Codecov's other checks. When GitHub's rollup is failure or error and every failing check is tolerated, Loupe shows pending if any check is still pending and passed otherwise; any other rollup is shown as GitHub gave it, and so is a failure with no failing check fetched to explain it (rows not yet looked up, or a commit with more checks than are fetched).

The rule is one function in `LoupeModel` (`CheckContext.isToleratedFailure`, `CheckState.tolerating(_:)`), applied when the store turns a row into a `PullRequestSummary`, so the list glyph, the header glyph and its failed names, the popover and the merge button's reason all take the same state without each working it out. The store keeps GitHub's rollup and checks as given, so the rule can change without a migration or a fresh lookup. In the popover a tolerated failure keeps its row and description with its cross in the secondary colour, listed after real failures and pending checks; the summary line doesn't count it as failed but ends "1 coverage failure ignored". The header names a patch check below the threshold as `patch`. GitHub's own `mergeStateStatus` is untouched, so a `BLOCKED` PR whose only failures are tolerated gives "Blocked by branch protection" rather than "Checks failing". The conversation page's checks list still shows each check as GitHub reports it.

### Revealed lines can all be hidden again from the file's header

It only hides what's revealed in the changes shown, the whole PR's or one commit's, as each keeps its own. Hiding them one gap at a time isn't offered: GitHub has no such control either, and once gaps have merged hunks there's no clean step back. It's absent while nothing is revealed, so the header stays as it was for most files. When the diff is shown anew without an arrow having been clicked, as when the revealed lines go, the first code row in view that's still there holds still on screen, rather than the scroll offset, so hiding lines above the reader doesn't move what they were reading.

### Middle-clicking a row starts a comment on it; double-click selects a word

A middle click anywhere on a row that offers the "+", its gutter or its code, starts a comment there as the "+" does, so a reviewer needn't aim for a small target at the row's edge; elsewhere a middle click does nothing. Double-click was tried first, but a double-click should select a word, as in any text view, and taking it on commentable rows meant copying a word from most of the diff needed a drag. So a double-click (and a triple-click) selects as NSTextView does everywhere in the diff. The middle click uses the same row lookup as the "+", so the two can't disagree about which rows take comments, and the "+"'s tooltip mentions it.

### The pull reveals a hidden strip by growing the bottom inset, and skips its dwell when a drag begins at the end

A PR file's diff scrolls to its normal maximum, the footer directly under the last row and a short file resting unscrolled. Pulling at that maximum brings into view a strip hidden below the end, saying what the pull will do, and only once it's showing does the button start to fill, as `UIRefreshControl`, `SwipeRefreshLayout` and MacPullToRefresh do it. The strip is as tall as the trigger's lead-in, 40pt, one constant: the lead-in's travel brings it into view one-to-one with the fingers, and only travel beyond it fills the button. A scroll that runs into the end mid-drag reveals the strip with its spent travel, which reads as a bounce, while the dwell still holds the fill. Momentum and mouse wheels never reveal it.

The pull adds what it has revealed to the scroll view's bottom inset and scrolls to the new maximum, so AppKit's own scrolling holds the view there and a short file is scrollable by exactly the revealed amount. While past the end the drag's moves go to the pull alone, so nothing else moves the view. Letting go, armed or not, animates the view back to the footer's maximum in 0.2s and then drops the extra inset, and momentum after a drag that ended in the pull is dropped so it can't fling the document; when it fired, the next file replaces the view, and a file replaced mid-pull drops it at once. Holding the clip view's bounds past the scroll maximum, as MacPullToRefresh does, was tried: AppKit kept resetting them on a file that exactly fits the pane, so the strip jumped and the pull disarmed. A scrollable gutter of half the view's height below the footer was tried too, and was just a big empty section to scroll to.

Whether the view is at its end is read from its bounds only until a drag is past it; from then the pull's own travel says, so nothing AppKit does to the bounds can disarm it. Travel back at zero is leaving the end: the pull is undone, the fill empties, further moves scroll the document, and coming back is a scroll reaching the end, so it dwells. The rubber band is off for a PR's diff, as at the bottom it would add to the strip's movement and leave AppKit mid-bounce under the inset, so the top doesn't bounce either; a plain diff file, with no footer, keeps it.

The dwell guards against a scroll running into the end mid-drag, so a drag that begins at the end, which has no scroll behind it, skips it and counts from the lead-in straight away; the scroll view says whether the view was at its end as the fingers touch down. That makes pulling immediate in a file shorter than the view, which is at its end from the start, and in a long file already scrolled to the bottom. A drag that reaches the end while scrolling still dwells, as does one that began at the end, went back into the document and came down again.

The sidebar's files are a tree, as github.com's "Files changed" tree is: directories as disclosure rows with a folder symbol, open to start with, files under them with a document symbol, and a run of directories each holding only one directory shown as one row named `a/b/c`. The "Vendored, lockfiles and generated" section is a second tree under its own header, so a generated `.pb.go` still sits under its directory; its rows say added, deleted, renamed or copied before their counts at the trailing end. Moving on to the next file not viewed, and the file a PR opens on, follow the tree's order rather than git's, so they go down the list as shown; git sorts `a/b.txt` before `a/c/d.txt`, the tree the other way round. The diff file mode (`swift run Loupe <diff>`) uses the same tree.

### Homebrew's git is preferred to Apple's

Loupe runs the first of `/opt/homebrew/bin/git` (Homebrew on Apple silicon), `/usr/local/bin/git` (Homebrew on Intel) and `/usr/bin/git` that exists and can be run, chosen once at first use and logged with its `git --version`. Apple's git, from Command Line Tools, lags upstream (2.39 here, against Homebrew's 2.49). Homebrew's is the one Glen's shell runs, so Loupe's diffs match what he sees in the terminal, and newer flags become available. Both read the same global config and credential helpers, so nothing else changes, and with no Homebrew git Loupe behaves exactly as before.

`PATH` isn't consulted: an app launched from Finder or the Dock doesn't get the shell's `PATH`, and recovering it by running a login shell would be slow and fragile. The fixed list covers both Homebrew prefixes. A `LOUPE_GIT` environment variable naming a path wins outright, for testing against a particular git.

Homebrew's git is new enough for `check-attr --source`, but the throwaway-index reading of `.gitattributes` stays, so Apple's git and Homebrew's behave alike and a machine without Homebrew needs nothing else.

### Links to PRs open them in the app, from inside it or from other apps

PRs reference each other constantly, as one PR's description says "Needs porter#1522", and most PRs reach a reviewer as links in Slack and mail; following such a link out to the browser leaves the review behind. So a link to `github.com/<owner>/<repo>/pull/<number>` opens that PR's tab, or shows it if it's already open, whether it's clicked in the conversation, a rendered markdown file or a review thread's comments in the diff, or comes from another app. Every other link, issues, commits and compares included, opens in the browser, as does ⌘-click or a middle click on a PR link, which ask for a browser tab.

Loupe declares its own `loupe` URL scheme, and `https` with the `Alternate` handler rank. Being the default browser would put the rest of the web in an app that can only send it on, so Loupe never asks to be; a link router such as Finicky or Velja, which already chooses a browser per link, sends `github.com/*/pull/*` here, rewritten to `loupe://` or as the https URL, as `open -a Loupe <url>` does. A `loupe:` PR link is a GitHub link with its scheme swapped, as a router's rewrite produces, or the shorter `loupe:///<owner>/<repo>/pull/<number>`; anything may follow the number. A PR link from another app brings the window forward, unhidden and unminimised. An https link that isn't a PR goes to the default browser without bringing Loupe forward; a `loupe:` URL that names no PR is logged and dropped, as there's no page to send it to. Links that arrive while Loupe is launching wait until the window has been restored, then open in the order they came.

A PR in either list, or already open, opens at once. Any other gets its tab at once too, built from the link alone, so a click from Slack visibly lands rather than showing whatever was there while GitHub answers: `repo #number` in bold with a spinner where the title will be, and "Looking up the pull request…" in its pane. The lookup is by repo and number, with the lists' rows' fields, and doesn't block the window. Once GitHub answers, the PR's tab takes the link's place in the strip, still shown if it was, so it reads as one tab filling in. The PR is stored with its tab in one write, so a list refresh can't drop it as unlisted first; it then behaves as any PR opened from the lists, viewed files and conversation included, and is forgotten when its tab closes. A second link to the same PR meanwhile shows that tab rather than asking again; several links arriving together each get their tab, in the order they came.

If GitHub has no such PR the viewer can see, or the lookup fails, the tab stays, its strip line saying "Couldn't open" and its pane why, with Retry, Open on GitHub and Close: a tab that disappeared into the browser would be more surprising than one that explains itself, and the browser is still one click away. The link's tab isn't stored, as the `openTab` table holds PRs by id and there's no id until GitHub answers; while it's shown the lists are stored as shown, so quitting mid-lookup reopens on the lists and loses the link, which is rare and cheap to click again.

### "Review required" is a badge in GitHub's attention colour

As plain caption text, "Review required" read as information rather than as the thing blocking the merge. It's now a badge like Conflicts, in Primer's attention colour as GitHub shows it, with help saying a review is needed before merging. "Approved" and "Changes requested" stay as coloured text: they're outcomes rather than something still owed.

### Who could review is offered most recently asked first, from a history of requests

The request-a-review popover offered candidates in GitHub's order, people then teams, so the few colleagues the viewer usually asks were wherever their logins happened to sort. Now everyone asked lately in that repo comes first, most recent first, then the rest in GitHub's order; typing filters that list as before. Each request made from Loupe, re-requests included, is appended to a `reviewRequest` table once GitHub accepts it, never on the optimistic add or after a refusal: the repo (lowercased `owner/name`), the reviewer's node id, login or team `org/slug`, kind, the PR's id and when. It isn't tied to the `pullRequest` table, so the history outlives the PRs it was made on.

An empty history would order nothing at first, so the reviewers already on the viewer's own stored PRs count too: anyone asked or reviewing on one counts as used at that PR's last update, unless the table has something newer for them. GitHub doesn't say when a request was made, and those requests weren't made from Loupe, so they aren't written to the table; the one store query merges both. The order is read from the store once a run per repo, alongside the candidates, and each accepted request updates it in memory so the list reorders straight away; reviewers stored with a conversation later in the run count from the next launch.

The ordering is one function of the candidates and when each was last asked, so more can be weighed in later: spreading reviews around, so the same few people aren't always asked, and GitHub's suggested reviewers. Neither is built yet.

### Only the diff and its threads wait for a reload; the rest of an open PR follows GitHub

The banner of "Open PRs learn of changes from notifications, and offer a reload" appears only when new commits are pushed, "New commits pushed" with Reload, as the diff is the one thing a reviewer is partway through and must not have replaced under them. A comment, a review, an approval or a change of state moves nothing in the diff, so a banner for those was noise the user had to act on to see what they'd been told about.

When the stored PR shows activity (its update time, state, review decision or counts), the tab fetches its conversation, which brings the review threads with it, and its viewed states in the background, whether or not new commits wait for a reload: a reviewer reading the old diff still wants to see a new comment, an approval or a resolved thread in the conversation, the header and the file list. It waits a couple of seconds so a burst of changes is one fetch, never overlaps another fetch or the tab's load, and checks again once done. The tab observes its stored row, so whatever stored the change, a notification, the fallback timer or the lists' refresh, is noticed. A failed fetch keeps what's shown.

What waits is where threads are placed on the diff. GitHub places a thread by the current head's lines, so once the head moves a freshly fetched thread could sit on the wrong row of the old diff. The tab keeps the threads as last fetched while the diff was of the PR's head, and while new commits wait, the inline threads and "Not on the current diff" are drawn from those; once the diff is produced again, by Reload or a retry, or the banner is dismissed to keep the old diff, they're the conversation's own again. Everything else, the file list's unresolved counts included, follows the latest fetch, so a count can briefly differ from the threads shown inline. The viewer's own actions on the diff's threads (a reply, resolving or unresolving, a new comment on a shown line) act on the lines shown, so their result appears inline at once; after the next fetch, the threads acted on and a new one the viewer started take GitHub's latest copy, and the rest stay as they were. The diff reads all of this through one property, `placedThreads`, separate from the conversation's threads, so anything else shown on the diff's lines, such as a pending review's comments, is placed the same way.

The conversation's web view loads a whole new page for new content, which would put the reader back at the top, so it reads the scroll position before replacing the page and restores it once loaded, from the app's own script world, outside the page's no-script policy. Reply drafts and the description editor are native, outside the page, so a refresh never touches them.

A noticed change on an open PR also looks up its checks and merge state, which the lookup by id leaves out, so an approval doesn't leave `mergeStateStatus` at `BLOCKED` and the merge box saying "Blocked by branch protection" until the lists' next refresh. It reuses the status lookup the lists run after each refresh rather than widening the by-id query, so both stay one query each with known costs.

### "Review required" isn't shown in the To review list

Every PR in To review is there because a review is being asked of the viewer, so a "Review required" badge on each row said nothing and drew the eye in amber to every one alike. The To review list leaves it out; "Approved" and "Changes requested" still show there, as they say how others' reviews went. Mine and an open PR's header keep the badge, as there it's news.

### Review requests left unanswered for two weeks are hidden from To review

A PR stays out of the To review list once the viewer's request to review it is more than 14 days old. The age is the request's, not the PR's: when the viewer was last asked, re-requests included, taken from the newest `ReviewRequestedEvent` naming them in the PR's latest request events. The check that drops fulfilled requests already looks up each to-review PR by id on every refresh, so it now asks for those events as well, on the first load as on later ones, and stores the time on the PR as `reviewRequestedAt`. A request of any team counts as asking the viewer, as team membership isn't cheaply known. With no request of the viewer among the events, the PR's update time stands in, since GitHub counts a request as an update.

The PR is hidden when the list is read, not removed from the store, so it stays known to tabs and links, and a fresh request brings it back with the next refresh. The viewer's own PRs aren't affected. A quiet caption under the list says how many are hidden, so a shorter list isn't a mystery.

A request nobody acted on for two weeks is stale noise in a list meant for what to review next; GitHub's own list never prunes them, so they pile up. Glen's list on the day this was built held six such requests, the oldest a year old.

### Reviews are submitted as on github.com, from a pending review that's listed and pruned from the header

The flow is GitHub's own: comments made into a review are held in the viewer's pending review, which only they can see, until it's submitted with a summary and a verdict. Its GraphQL is `addPullRequestReview` with no `event` to start one (holding the first comment through its `threads` input, and `commitOID` set to the head the diff shows, whose line numbers the comment uses), `addPullRequestReviewThread` to add a comment to it, `submitPullRequestReview` with `COMMENT`, `APPROVE` or `REQUEST_CHANGES` and the summary, `deletePullRequestReviewComment` to drop one comment and `deletePullRequestReview` to abandon it. Submitting with no review pending calls `addPullRequestReview` with the event and summary, which submits at once. None of them was run live; their inputs are from introspection.

The pending review is asked for beside the review threads, `reviews(first: 1, states: [PENDING], author: $viewer)` with its id, body and comment count, in both the conversation's query and the threads-only one, and stored on the conversation's row, so the header knows of it at once on the next launch. GitHub lists the viewer's pending comments in `reviewThreads`, so each thread comment's `state` is asked for and stored, and a thread whose first comment is pending is the review's. Those show in place like any thread, each pending comment with a "Pending" badge in the attention colour, but without Reply or Resolve: GitHub says `viewerCanReply` on them (and not `viewerCanResolve`), but how a reply posted at once would sit beside an unsubmitted comment hasn't been tried, and no one else can see the thread to answer yet. After every change to the review the threads and pending review are fetched again. They're the viewer's own, so, as replies do, they show on the diff being read even while new commits wait for a reload, turn submitted there once the review is, and go from it with an abandoned review. A refusal while adding to the review fetches them anyway, so a review started or submitted on github.com since is known when the comment is sent again; GitHub allows one pending review per viewer per PR, so the stale case is refused rather than doubled.

The review's controls sit at the header's right end, where the viewer's own actions sit on their own PRs, as "Verdicts are one click from the header; the summary is written apart from them" describes. The summary is kept while the tab lives. After submitting, the conversation is fetched again, so the review shows in it and in the reviewers, and so is the PR's status, so the review decision and merge state in the header, its tab and the lists follow.

Each pending comment, in the diff's threads and in the reply sheet over the conversation, has a small "Delete…" beside its Pending badge. It asks first, as discarding a typed comment does, since the text can't be got back. GitHub keeps a pending review emptied this way, which would still show as pending here and on github.com, so Loupe deletes it too when it has no summary saved on GitHub; a summary being written in Loupe is kept for the next review, and one saved on GitHub keeps the review. A refusal shows on the thread, as a refused reply does, with the comment left. Editing a pending comment isn't offered: threads carry only GitHub's HTML of each comment, not its markdown, so it would need the query, the store and the model to change.

The header's "N pending comments" is a plain button opening a popover, "Your pending review", that lists every pending comment in the diff's order (file, then line, with those on a whole file or off the diff after a file's lines): its `path:line`, then for a reply "replying to @login:" and the first line of the comment before it in its thread, or for a new thread the line of code it's on, then the first three lines of the comment as plain text. Clicking a row closes the popover and shows the thread in the diff through the same path as the conversation's "Show in diff"; each row has the same "Delete…", and the footer has "Discard review with N pending comments…", so a review can be pruned from one place without hunting through files. The Summary popover has the same discard button; both ask first.

### A new comment posts at once or starts a review on any PR; ⌘↩ and ⌘⇧↩ send its two buttons

Where the viewer can start a review, the comment box has github.com's two buttons: "Add single comment", which posts at once over REST, and "Start a review". ### An npm lockfile shows its package changes, still among the hidden files

A `package-lock.json` or `npm-shrinkwrap.json` in the "Vendored, lockfiles and generated" section shows the packages it adds, removes, updates and moves in place of its JSON diff, which for a dependency bump is thousands of lines saying little. The model is ported from the npm tool `diff-package-lock`: lockfile v2 and v3 `packages` are keyed by path, a package's name is its `name` or the part after the last `node_modules/`, its version is `link:<resolved>` for a link, and the project's own root entry and any path with no name are skipped. Comparing the two trees by key gives updates, removals and additions, and a removal and an addition with the same name and version are paired as a move, as when npm hoists or nests a package. Unlike the tool, a v1 lockfile's nested `dependencies` are keyed by the path they'd install at, so a v1 file compares with a v2 one rather than every package showing as moved. Only versions are compared, so a change to `resolved` or `integrity` alone says "No package changes".

Both versions are read with `git show` at the shown changes' base and head (an added lockfile is all additions, a deleted one all removals) and parsed off the main actor, as a lockfile can be megabytes; the result is kept per range and path like the hidden file's diff. The list is sorted by key, monospaced, with the place in `node_modules` dimmed as a file's directory is, and the glyph in the diff's colours: green for added, red for removed, and the attention colour for updated and moved. A "Changes | Raw diff" toggle in the file's header, like markdown's "Source | Rendered", switches to the diff, which still sits underneath and keeps its review threads and comments; the summary says how many threads are on the file, as only the diff shows them. The choice is kept per path while the tab lives. If either version won't parse, the diff shows with a line saying why.

Lockfiles stay hidden rather than moving to the files to review: they're derived from the manifests that are reviewed, and their changes are a consequence of those, so they don't count towards "N of M reviewed" or the self-review. Making them readable where they are lets a reviewer check what a bump brought in without making every lockfile something to tick off.

### ⌥← and ⌥→ move by code words in comment boxes

Comments are mostly about code, and they're written by people whose hands know a code editor's word movement, so in every box behind `MarkdownTextView` (line comments, replies, the PR's comment, the review summary and the description) ⌥← and ⌥→ move the insertion point by code words, and ⌥⇧← and ⌥⇧→ extend the selection by the same stops, keeping its other end fixed. The rule: characters are words (letters, digits and underscores, Unicode letters and digits included), whitespace, or punctuation (everything else, emoji too). A move skips any whitespace, then one whole run of word characters or of punctuation. So `obj.Field|` steps left to `obj.|Field`, `obj|.Field` and `|obj.Field`; `foo(bar, baz)|` steps over `)`, `baz`, `, `, `bar`, `(` and `foo`; going right, `|foo(bar, baz)` stops after `foo`, `(`, `bar`, `,`, ` baz` and `)`. Whitespace is never a stop of its own, newlines included, and the ends of the text stay put. There are no camelCase stops: `fooBar` is one word, as identifiers are what's being stepped over and camel stops would be wrong for snake_case and acronyms alike.

It's ⌥ because that's the key macOS gives word movement everywhere else, so it's where hands already reach; ⌘ was tried first, from a misstated request, and took away going to a line's ends. ⌘← and ⌘→, with or without ⇧, are AppKit's own, and AppKit's natural-language word movement isn't offered on any other key. ⌥⌫ and ⌥⌦ delete by AppKit's words, as they aren't taken. The keys are caught in the text view's `keyDown`, beside ⌘↩, rather than by overriding `moveWordLeft:` and the rest, so a key binding that maps something else to those actions keeps doing what it says. Plain arrows and everything else are the text view's own.

In the conversation the page runs no script of its own, so the app quotes the selection from its own script world. ### Text diffs are unified only; side by side is for images

Side by side only matters to Glen for images, which already compare old and new 2-up, so text diffs have no split view, and unchanged lines take comments on the new side only. A split view, as github.com's "Split", was built and removed; how it worked is kept here in case it's wanted later.

It was the same `DiffTextView`, so selection, find, highlighting, blocks, anchors and lazy layout were shared. Each split row was one paragraph: the left side, a line separator (U+2028), the right side. A text container subclass gave each side's lines half the width, and a layout-manager delegate lifted the right side's lines beside the left's and stretched its last line to the foot of the taller side, so the sides wrapped independently. Every row being a paragraph kept TextKit 1's non-contiguous layout working: a 46k-row file opened as fast as unified, and only whole-file layout cost about twice as much. Rejected then: `NSTextTable`, which defeats non-contiguous layout (on 5k rows, drawing mid-file took 1.4s and whole-file layout six times unified's); and two text views side by side, whose rows stay level only by laying both out in full, and which split find, selection and blocks in two.

Each side was a row of its own to clicks, the "+" and double-clicks, the left's lines commented on `LEFT` by their old number; TextKit finds the line under a point by height alone, so the layout manager searched the side the point was on. A selection kept to the side it began on. It always wrapped, fell back to unified in a pane too narrow for two sides of about 50 columns, and since TextKit hangs the right side's first line like a continuation, split rows had no paragraph indent and the container hung continuations itself.

### The changes since a head the PR was rebased from are its old changes replayed onto the new base

This is how the commit picker's "since" entries handle a head the PR was rebased from. Diffing an earlier head straight to a rebased one mixes in everything the base gained between the two merge-bases, which is exactly what a returning reviewer doesn't want to read. So the PR's changes as they were (old merge-base to old head) are applied onto the new merge-base, giving the tree the old PR would have had on the new base, and the entry diffs that tree to the head: only the author's own edits since show, as a normal diff with the same hidden files, viewed states and Reload as any other choice. Commenting stays on the whole PR's diff, as for every choice but "All N commits".

The replay is `git merge-tree --write-tree -z --name-only --no-messages --merge-base=<old merge-base> <new merge-base> <old head>` (git 2.40 or later for `--merge-base`; Homebrew's git, which Loupe prefers, is newer), which builds the tree without touching branches, the index or the working tree. A file whose old changes conflict with the new base can't be separated from the rebase, so it falls back on its own: the replayed tree takes the old head's version of each conflicted path (or drops it if the old head had none), through `read-tree`, `ls-tree`, `update-index --index-info` and `write-tree` on an index outside the checkout. That file then shows its whole change since, base's included, and says so: "Couldn't separate from rebase" in its header, "rebase" in the file list, each with the hover popover explaining. Other files are unaffected, and files only the base touched never show. Rebuilding the old head's changes by hand (a patch through `git apply`) was the alternative; merge-tree does the same three-way merge with git's rename handling, in one command.

A replay that comes out as the head's own tree means the push only rebased, so rather than an empty diff the entry stays, dimmed and unpickable, as "Only rebased since, no changes" with when, so the reviewer knows they're up to date.

### Objects Loupe makes are written to its own object directory, never a checkout's

merge-tree writes the trees and merged blobs it makes into the object database. Checkouts are shared with other tools and Loupe only ever fetches into them (the PR head into `refs/loupe/`, and since "The commit picker offers what's changed…", an earlier head by oid with no ref, which is a fetch like the rest and so stays). Objects of Loupe's own making don't belong there, so the replay runs with `GIT_OBJECT_DIRECTORY` set to `~/Library/Caches/Loupe/replayed-objects` and the checkout's own object directory (`git rev-parse --path-format=absolute --git-path objects`) as `GIT_ALTERNATE_OBJECT_DIRECTORIES`: it reads the checkout's objects and writes only to Loupe's. Every local git run that may read a replay (diffs, stats, a file's first lines or bytes) has Loupe's directory as an alternate; fetches never do, or a fetch could take an object there as present and leave the checkout without it. The directory is shared by all checkouts, since objects are named by their content, and is a cache: anything the system clears is made again when next asked for. Nothing prunes it yet; a replay writes only the trees and blobs it changed, which are small.

### Stacked PRs follow GitHub's own stacks and branch chains, and only a stack's bottom PR can be merged

### The report's files are fetched as the page asks for them, with the `circleci` CLI's own token, falling back to the CLI downloading the whole job

The report's link is `output.circle-artifacts.com`, which for a private project redirects to `app.circleci.com/private/output/…` and answers 404 without a CircleCI session. Signing in inside the view would mean letting CircleCI's and GitHub's sign-in pages into it and keeping their cookies, and Glen found a separate CircleCI login annoying, so Loupe uses the `circleci` CLI's sign-in, as it borrows `gh`'s for GitHub. The CLI has no command that prints its token, so, at Glen's request and until it gains one (he has asked upstream), `Scripts/circleci-token` reads it where the CLI keeps it, following its source (circleci-cli v1.7.0): `CIRCLE_TOKEN` or `CIRCLE_CLI_TOKEN`, else the login keychain's generic password with service `com.circleci.cli:<host>` and the OS user name as account, stored by zalando/go-keyring as `go-keyring-base64:` and the token in base64, else `token:` in the CLI's config file. The host is `CIRCLE_HOST`, else the config's `host:`, else `https://circleci.com`. Reading only the config file missed `circleci auth login`'s token, which is kept in the keychain. That sign-in keeps only the OAuth access token, with no refresh token or expiry, so a token CircleCI turns down needs `circleci auth login` again. `bundle.sh` copies the script into the app's resources, a bare build finds it in the checkout, and `LOUPE_CIRCLECI_TOKEN_COMMAND` names another command, as the tests do with a fake. It's run each time a report not kept from before is opened, its token kept in memory only, and run once more when CircleCI turns the token down (401 or 403), so a new sign-in is picked up without restarting.

The page is loaded as `loupe-artifact://<artifact host>/output/job/<job>/artifacts/<node>/<path>`, and a `WKURLSchemeHandler` answers each request, the page and every relative file it loads, so the token never enters the page, its URLs or WebKit's storage, and the page keeps no cookies or storage. A `file:` URL wouldn't do: the report fetches its data and loads Storybook in frames, which WebKit restricts for file URLs, and the handler can refuse anything outside the shown report's job, including `..` and links out of its directory. A file not already on disk is fetched over https with `Circle-Token`, which `output.circle-artifacts.com` accepts directly. Redirects are followed by Loupe itself, over https only, with the token sent only to `circle-artifacts.com`, `circleci.com` and their subdomains. Absolute links to the same job's artifacts are served the same way; other pages go to the browser.

A job's artifacts never change, so each file fetched is kept in `~/Library/Caches/Loupe/artifacts/<job id>` (the URL session keeps no cache) and reopening a report is instant. A job not opened for 30 days is deleted, checked whenever a download starts; opening a job marks its directory's modification time as the record of when it was last opened. The report itself is fetched before the page loads, so a refusal shows the pane's "isn't signed in" failure with `circleci auth login`, and its absence says the report isn't among the job's artifacts.

When the script prints no token (signed out, no keychain item), the CLI downloads the whole job instead, with its own sign-in. The CLI is found as `gh` is (Homebrew's, then `/usr/local/bin`, then `PATH`, `LOUPE_CIRCLECI` overriding), since an app opened from Finder has launchd's `PATH`, and is run with its prompts, colour, spinner and update check off. It writes into a `.partial-` directory beside the job's, renamed into place only once it exits cleanly having written as many files as it said it would, so an interrupted, failed or cancelled download is never served; one left by a crash is deleted a day on. The pane shows a bar of files written against the count the CLI announces, with Cancel, which stops the CLI and leaves nothing behind; otherwise a wait shows "Loading the visual review report…". A download replaces any files fetched earlier for the job; signed out with only some fetched, the rest answer 404 until signed in again or the job is pruned. When the CLI can't be run, the pane says to `brew install circleci` and sign in with `circleci auth login`; when it exits with its authentication status, it shows the CLI's own words and `circleci auth login`; any other failure shows what the CLI said. Each has Try Again, Open in Browser and Open Artifacts Tab.

### Whitespace changes can be hidden per PR, as github.com's "Hide whitespace"

A reindented block or a reformatted file buries the change that matters, and github.com's "Hide whitespace" (`?w=1`) is how a reviewer reads past it there. Loupe offers the same from a quiet `space` button in each file's header, tinted while on, and View ▸ Hide Whitespace (⌃⌘H; ⌃⌘S was the split view's, and keys near ⌘W are avoided since ⌥⌘W closes every tab). It belongs to the PR's tab, off as each tab opens and not remembered: Glen judged whether it helps depends on the PR, so it's not a View setting like Wrap Lines. The menu item acts on the shown tab.

The diff is `git diff --ignore-all-space` (`-w`). GitHub's own words, in its 2011 "GitHub Secrets" post and since, are only "the diff with whitespace ignored", naming no git option; `-w` ignores all of it, so a space added between words counts for nothing, where `--ignore-space-change` would still show it. That choice isn't confirmed against github.com. It applies to every choice of changes (the whole PR, a commit, the changes since an earlier head or a force-push, replayed or not), to hidden files diffed when shown, and to lines revealed around hunks. With it, git leaves out a file only whitespace changed in, so the files listed come from the diff with whitespace, which is always made too, and take the hunks of the one without: such a file stays listed and its diff says "Whitespace-only changes", as on github.com. Both ways are kept per range while the tab lives, and so are lines revealed in each, as their hunks differ, so toggling back is instant. A reload keeps the setting and makes the diff that way before showing it.

Line counts don't follow it, as github.com's don't: the file list, each file's header and the commit picker's diff-stats count the changes with whitespace, as do the reviewed count and "Self-reviewed", which go by the files of the whole PR's diff.

Comments stay on, as on github.com. Lines in a whitespace-ignored diff are still numbered as in the file, and git shows an unchanged line as the head has it, so threads land under the same rows (a thread on a reindented line, either side, now sits under it as an unchanged line), and a comment posts the head's or base's own line number. A hunk ignoring whitespace lies within one hunk of the real diff, as every change it shows is in that diff too, so a range of lines picked in it is one GitHub takes. Word-level emphasis already skipped changes to runs of whitespace; with whitespace hidden, a word split or joined only by whitespace (`foo bar` for `foobar`) isn't emphasised either.

### UI checks are scripts driving the real app in-process, invisibly, and snapshot runs only read

Agents building keyboard, click and hover behaviour need to see it work, and each check was a new `LOUPE_SNAPSHOT_*` hook in Swift. It runs inside the app rather than as XCUITest. The cost is that some of what the window server does has to be done by hand. SwiftUI only builds its accessibility tree once an assistive app asks, so a script run asks at launch, as VoiceOver does. A context menu is asked for but not shown, as it would track the real mouse.

Snapshot runs talk to the real GitHub and the user's checkouts, and a script can click anything, Merge and Submit included. Before this, only the merge rehearsal kept writes from GitHub. So every snapshot run now sends GitHub only queries, `GET`s, `HEAD`s and `POST /markdown`, and refuses every mutation and REST write before it leaves the process. git is kept to reading the checkouts, fetching into `refs/loupe/` and writing Loupe's own objects and indexes; no clone, branch switch or the like. Opening links in the browser and checkouts in an editor are refused too, as they'd show on the user's screen. Each refusal is printed and recorded, so a script can assert that clicking a button tried to make the change it should. The refusal reaches the UI as GitHub's or git's own error would. ### A conflicting PR's files are found by merging locally into the base branch's fetched tip, and marked as it opens

Each job is read only when shown, and an ended job's reads are kept in memory, as they never change; they aren't stored, as reading them again on the next launch is quick. Artifacts open in the browser, which CircleCI's web sign-in serves, rather than in Loupe. The chosen panel stays as jobs are switched, so the same thing can be compared across them.

### To review is sectioned into To review, Reviewing and Approved, beside Mine in a resizable split

The PRs asked of the viewer are split by how far they've got with each, so what's waiting on them stands apart from what's waiting on the author. They're one GitHub list split in the model (`ReviewStage`), not three queries, so a review moves a PR between sections without a refresh.

The three were first tried as columns of their own beside Mine, which gave three quarters of the window to reviews, though most time goes on Mine and incoming reviews are turned around quickly. So the To review column is one list with a heading row per stage, each taking only the rows it has and with its own hidden-older-than-a-month toggle, and Mine and To review sit side by side with a divider the viewer drags to give either more room, down to 280pt each. Where it was left is kept in the app's preferences as Mine's share of the width, so it holds as the window resizes and across launches. ### A merged PR shows its merge commit's checks, and a tab follows running checks every 15 seconds

Once a PR is merged, what matters is whether the base branch's CI passed on the commit the merge made, so the header shows that commit's checks under "Merged": the checks glyph with its hover list, the base branch's name, and the failed checks' names in red. The head's checks stay where they were, as they describe what was reviewed. A failed CircleCI job on the merge commit joins the head's in the CircleCI section, under the job's own name, as the job lookup matches a workflow's jobs by the check's name. The merge commit's checks come with the existing lookup of statuses by id (`mergeCommit`, null while open), stored apart from the head's.

A check finishing isn't an update to the PR and brings no notification, so the lists' refresh, every few minutes, is too slow to watch a run finish. While a PR is open in a tab, its checks and merge state are looked up every 15 seconds, in one round and batch, until they pass or fail: an open PR's head checks while they're `PENDING`, and a merged PR's merge commit checks while it merged in the last day. Only `PENDING` is followed, not `EXPECTED`, which a required check that never reports can leave for ever. Besides, the lists' refresh asks about each PR merged in the last day until its merge commit's checks have finished; a day is ample for the base branch's CI and stops a merge commit without checks being asked about for ever. An older merged PR is asked about as its tab is shown, as every tab is, and merging from Loupe looks them up at once.

### GraphQL is vendored as Protocol Buffers is, with the grammar's own query

GraphQL schemas and queries were plain. Descriptions take the comment colour, as the grammar's query says, types the entity colour, fields the constant colour and arguments the variable colour.

### SCSS is vendored as Protocol Buffers is, its query on top of CSS's

SCSS stylesheets were plain. The grammar is tree-sitter-grammars/tree-sitter-scss, vendored as the `TreeSitterSCSS` target as "Grammars CodeEditLanguages lacks are vendored as C targets" describes. It's the maintained successor to serenadeai/tree-sitter-scss, which nvim-treesitter still pins and which hasn't changed since 2022; its one tag predates its licence file, so it's pinned to a commit, recorded in `VERSION`, and its parser is ABI 15. The grammar extends tree-sitter-css, and its own highlights query covers only what SCSS adds (variables, `@mixin`, `@include`, `//` comments), so the highlighter compiles CodeEditLanguages' CSS query beneath it, as nvim-treesitter's `; inherits: css` does: selectors, properties and values colour as in a `.css` file. nvim-treesitter's SCSS query was the alternative, but it's written for serenadeai's node names. As the query lists its generic `(identifier) @variable` after the mixin's name, and later patterns win, a mixin's name where it's declared stays plain while an `@include`d one takes the entity colour.

### A suffix Linguist doesn't know is passed over for colouring

Files such as `database.yml.ci` and `memcache.yml.docker`, one copy of a config per environment, were plain: Linguist goes by a name's last extension, and `.ci` and `.docker` are no language's. So when Linguist finds no language for a path at all, the highlighter looks it up again less its last extension, and colours `database.yml.ci` as YAML and `settings.json.sample` as JSON. It's not a YAML rule, as any language's files get such suffixes. ### Makefiles are vendored as Protocol Buffers is, with the grammar's own query

Makefiles were plain. It's pinned to the commit nvim-treesitter pins, recorded in `VERSION`: that's nine commits of parsing fixes past the last tag, and the first with a licence file. ### Go templates are vendored as Protocol Buffers is, colouring only the actions

Go templates were plain. The grammar is ngalaiko/tree-sitter-go-template, the one nvim-treesitter and Helix use, vendored as the `TreeSitterGoTemplate` target as "Grammars CodeEditLanguages lacks are vendored as C targets" describes; it has no tags, so it's pinned to the commit nvim-treesitter pins, recorded in `VERSION`. ### Handlebars is coloured with Ember's Glimmer grammar, and `.hb` is Handlebars

Handlebars templates were plain. There's no established Handlebars tree-sitter grammar: nvim-treesitter gives Handlebars files ember-tooling/tree-sitter-glimmer, Ember's dialect (Helix uses it for Ember's templates only), and so does Loupe, vendored as the `TreeSitterGlimmer` target as "Grammars CodeEditLanguages lacks are vendored as C targets" describes, at the commit nvim-treesitter pins (a few parsing fixes past the last tag), recorded in `VERSION`. ### A thread GitHub calls outdated but made on the head stays on its lines, with its code built by Loupe

### A line with no newline after it ends in a ⊖, as on GitHub

git's `\ No newline at end of file` was parsed onto the line before it but never shown, so a change that only added or removed a file's final newline looked like a line replaced by itself. Such a line now ends in a muted ⊖, a space after its code, whose help says which side lacks the newline and, when only one does, whether the change adds or removes it. Which row it's on says the rest: a deleted row's for the old file, an added row's for the new one, an unchanged row's for both. ### Mermaid diagrams are drawn by a vendored Mermaid, in the app's own script world
