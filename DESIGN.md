# Loupe: goals and design decisions

Loupe is a native macOS app for reviewing GitHub pull requests. It exists because reviewing on github.com is slow for repos that vendor dependencies, and because a local app can lean on local checkouts in ways a web page can't.

## Goals

- Review PRs faster than on github.com, for one person, on a Mac.
- Vendored and generated files never get in the way: excluded from diffs by default, not merely collapsed.
- The app is usable the moment it opens, with whatever it already knows, and refreshes in the background.
- Keyboard-driven review once the basics are in place.

## Decisions

Each entry says what we chose and why, so a later change can be made knowingly. Add new ones at the end; don't rewrite old ones, note the reversal instead.

### Native app, not a browser extension

A Firefox extension over github.com would get commenting and review submission for free, but it rides GitHub's React DOM, which changes often, so it would be a maintenance tax with a low ceiling. A native app can use local checkouts, cache locally, and own its layout and keyboard model.

Complement, not alternative: a `.gitattributes` line of `vendor/** linguist-generated=true` in a repo collapses vendored files on github.com for everyone. GitHub's docs say only `linguist-generated` affects diffs; `linguist-vendored` only affects language stats.

### SwiftUI + AppKit, built with SwiftPM, no Xcode required

The machine has Command Line Tools only. SwiftPM with an executable target links AppKit and SwiftUI fine, so there is no `.xcodeproj`. Targets are split so that pure logic (`LoupeCore`, `LoupeModel`, `LoupeStore`) has no AppKit dependency and is testable headlessly.

### Diffs come from local checkouts only, never from the API

`git diff` against the checkout gives full-file context, honours pathspec exclusions (`':!vendor' ':!go.sum'`), has no rate limit and no file-count cap. The API's PR file list on a typical Go repo was 98% `vendor/` (741 files, of which 4 were real), and the REST files endpoint omits patches for large files and caps at 3,000 files.

Consequence: a PR can only be reviewed in Loupe when its repo is checked out locally. The app tracks checkout locations (see below). Checkouts are shared with other tools, so Loupe never touches branches, the index or the working tree. The one write it makes is fetching the PR head into its own ref namespace, `refs/loupe/pull/<N>/head`, so the objects stay reachable and nothing races over `FETCH_HEAD`.

For merged PRs, use the API's `baseRefOid` for the merge-base; the local default branch has moved on and the diff comes out empty. Don't rely on `FETCH_HEAD` in a shared checkout; another fetch can overwrite it.

### GitHub GraphQL for metadata; REST only where it is the better fit

One GraphQL search request returns a PR list with CI rollup, review decision, branches and author inline. The REST search endpoint returns issue-shaped objects and needs two or three more requests per PR for the same fields, and has its own 30-per-minute limit. REST is still the right tool for the whole-PR diff (`Accept: application/vnd.github.diff`, if ever needed), `POST /markdown` for GitHub-faithful rendering, and `GET /notifications`.

Known shapes, from `probe/`: CircleCI reports as legacy `StatusContext`s, not `CheckRun`s (only Codecov uses check runs), so CI handling must cover both. A review thread's `line` plus `diffSide` is a file line number, not a diff position; outdated threads have `line: null` and only `originalLine`.

### Auth is borrowed from the `gh` CLI

The app shells out to `gh auth token` per request and never stores the token. Good enough for a personal tool; a Device Flow OAuth app is the path if it's ever shared.

### A local SQLite copy is what the UI shows; GitHub is synced into it

Storage is SQLite via GRDB (migrations, record types, `ValueObservation` for live UI updates), at `~/Library/Application Support/Loupe/loupe.sqlite`. Launch shows stored rows instantly with a "refreshed N ago" label; refresh runs in the background. A failed refresh keeps the stored rows and shows a banner, never a blank list.

Rows have real columns per field, not a JSON blob, so the data is queryable. List membership (authored by me, review requested) is tracked separately from the PR row, since one PR can be in both.

DuckDB was considered and rejected for the app itself: the workload is small row-at-a-time upserts, which is SQLite's strength, and the DuckDB Swift binding lacks migrations and observation. For analytics over the history, point DuckDB's `sqlite` extension at the same file.

### Refresh is incremental after the first load

First load of a list uses `is:open`, paged to exhaustion, and reconciles fully. Every refresh after that drops `is:open` and asks for `updated:>=<last sync minus a small overlap>`, so merges and closes arrive as state changes rather than as absences. The UI filters to open PRs by default with a toggle to show closed and merged.

Fulfilled review requests are the gap: a PR you have reviewed stops matching `review-requested:@me` and never comes back to say so. A `nodes(ids:)` check over the to-review column catches those. Team-level requests are kept, since team membership isn't cheaply knowable.

### Checkout locations live in the database and are discovered automatically

A `localRepo` table maps `owner/name` to an absolute path. Unknown repos are looked up by exact directory name under `~/Development/tamarinworks/` then `~/Development/GitHub/`, accepted only when the directory is a top-level git repo whose `origin` points at that repo on github.com. Misses are not stored, so they retry. A stored path whose directory has gone is dropped and re-resolved. The search roots are a list in the model so they can become a setting.

### The diff view is one `NSTextView` with lazy layout

One attributed string per file, TextKit 1 with non-contiguous layout and no wrapping; full-width row backgrounds are painted in the layout manager, not the view, because doing it in the view silently forced layout of the whole file. A 46k-row file opens in about 150ms. Clicking a row yields `(path, side, line)`, the same anchor GraphQL review threads use.

### PRs open in tabs inside one window

Tab 0 is the PR lists and cannot be closed; each opened PR gets a closeable tab with browser-style keys (⌘W, ⌘1–9, ⌘⇧[ and ⌘⇧], ⌃Tab). Open tabs persist across launches. This keeps several reviews in flight without a window per PR.

### The window's chrome is the same whichever tab is showing

The title is always "Loupe", with the selected tab in the subtitle, and one unified toolbar is declared at the window level with items that change per tab. A toolbar or title declared by a tab's own view would come and go with the tab, resizing the title bar on every switch.

### PRs open as native window tabs, replacing the custom tab strip

The PR lists are one window and each opened PR is its own window, all grouped as AppKit window tabs (the tabs Safari, Finder and Terminal use) through a shared `tabbingIdentifier` and `tabbingMode = .preferred`. This replaces the SwiftUI tab strip above: two custom attempts looked wrong and weren't clickable on the user's machine, while AppKit's tabs look right and give ⌘W, ⌃Tab, "Move Tab to New Window" and "Merge All Windows" for free. The app adds only ⌘1–⌘9, ⌘⇧[ / ⌘⇧] and "Show Pull Requests" (⌘T), which reopens the lists if they were closed. Opening a PR that already has a window brings it forward. The open PRs and the frontmost one are stored and reopened at launch, so SwiftUI's own window restoration is turned off to avoid duplicates.

### Each window declares its own title and toolbar

Every window has the tall unified title bar and toolbar, so tabs match in height. The lists are titled "Pull Requests"; a PR is titled `repo #number`, which its tab shows, with the PR's title as the subtitle. The app icon sits beside each title where a document's icon would. This supersedes the single "Loupe" title with a per-tab subtitle, which only made sense while the tabs were one window.

### Producing a PR's diff leaves the checkout's other state alone

Fetches pass `--no-tags` and `--no-write-fetch-head`, so the only things they change are `refs/loupe/pull/<N>/head` and, when the base commit is missing, the base branch's remote-tracking ref. Hidden paths are excluded with pathspecs, `linguist-generated` ones through `:(attr:…)` magic against the checkout's own `.gitattributes`, and a second `--name-only` diff over the same pathspecs lists what was hidden, so the count stays honest. An open tab keeps its PR row stored after the PR leaves both lists, so a tab can always be restored. A list holding rows stored before commit oids were fetched gets a full load rather than an incremental one, which fills them in.

### Long diff rows wrap with a hanging indent

Rows soft-wrap at the view's width by default, with a View menu toggle. Each row's paragraph style indents continuation lines by the gutter's width, so wrapped code lines up under the code rather than under the line numbers, as on GitHub. Wrapping stays within TextKit 1's non-contiguous layout, so opening a large file costs the same either way; row backgrounds are painted per visual line and clicks map by character offset, so neither needed changing.

### Code is highlighted with tree-sitter, parsed per hunk

Each hunk's new side and old side are parsed with the file's tree-sitter grammar and coloured from the grammar's own `highlights.scm` with Primer's palette, which is how GitHub highlights diffs, partial snippets and all. Grammars come from their upstream SwiftPM packages through ChimeHQ's SwiftTreeSitter, and a file in an unknown language stays plain. Highlightr was ruled out because it runs highlight.js's regex grammars in JavaScriptCore, a cruder approach than GitHub's; Neon was ruled out because it manages incremental re-highlighting for an editor, and this is a static render. Colours go into the layout manager's temporary attributes, not the text storage, because adding tens of thousands of colour runs to a large storage costs several times as much; files over 5,000 rows paint plain first and take their colours from a background parse.

### Grammars come from CodeEditLanguages, not one upstream package each

Grammars and their highlight queries come from CodeEditLanguages, a single package that bundles about 40 prebuilt grammars. This replaces ten upstream grammar packages: each upstream manifest is maintained separately, several of their later releases fail to link under SwiftPM (so CSS, JavaScript and YAML were held at old tags and Swift at a special one), and every new language meant another dependency. One package gives SQL, Dockerfile, Markdown, Python, TOML, `go.mod` and more for free, with its own detection by extension and file name. The cost is a slightly slower prebuilt Go grammar, and a package that hasn't tagged a release since late 2024; Makefile and HCL still have no grammar there.

### Windows are AppKit's, not SwiftUI scenes

The lists window and each PR's window are `NSWindow`s made and tracked by `WindowManager`, hosting the SwiftUI views in `NSHostingController`s that carry their titles and toolbars into the window. SwiftUI keeps only the menu bar, hung on a `Settings` scene that opens no window. As scenes, the windows fought the app at every turn: SwiftUI's window controller handles `newWindowForTab:`, so the tab bar always showed a "+" that made stray windows SwiftUI then reused; its restoration duplicated the windows the store reopens; and a shared frame autosave name could be held by only one of its windows. Owning the windows removes the "+" (nothing implements `newWindowForTab:`), lets the store be the only restoration, and lets the lists window keep a frame autosave name that PR windows outside a tab group start from. A PR window joins the lists' tab group explicitly, in the stored order. As the app quits SwiftUI still closes every window, so the manager stops forgetting PRs once termination begins.

### Languages and hidden files follow GitHub Linguist's data

Which grammar a path gets, and which paths are hidden as vendored, come from GitHub Linguist's own `languages.yml`, `vendor.yml` and `documentation.yml`, vendored from a tagged release and refreshed by `Scripts/update-linguist.sh`. Linguist is what GitHub uses, so Loupe highlights and hides the same files GitHub does, and picks up new languages and vendoring rules without hand-maintained lists. `.gitattributes` `linguist-*` attributes override it either way, as on GitHub. The YAML is converted to JSON by the script so the app needs no YAML dependency. Linguist's content heuristics aren't run; an ambiguous extension takes the first of its languages that has a grammar.

### The diff view reads like GitHub's

Rows are 12pt on a 20pt line, with the code padded from the edges and its column set by a tab stop after an inline gutter: right-aligned old and new numbers and a `+`/`-` marker, on a darker tint of the row. The gutter stays inline text, tagged so copies strip it, so clicks, find and copying keep working on one string. Hunk headers mute the line ranges and keep the function context in the text colour. Within a run of deletions followed by as many additions, each pair of lines is diffed by token and the changed words are tinted more strongly, as GitHub does; pairs sharing under 30% of their tokens, lines too long to diff cheaply, and changes only to whitespace (gofmt realigning a block) get no emphasis. This happens while building the attributed string, so it's measured with it. Each file sits in a bordered box under a header bar with its path and counts.

### Open PRs learn of changes from notifications, and offer a reload

An open PR's window notices when the PR changes on GitHub and says so in a banner with a Reload button, as github.com does, rather than replacing the diff under the reader or waiting for the lists' three-minute refresh. This reverses re-diffing automatically when a refresh moves the PR's head: a reviewer partway through a diff keeps their place until they choose to move on.

The signal is GitHub's notifications API, polled with `If-Modified-Since`: a 304 costs no rate limit, so an idle poll is free, and GitHub's `X-Poll-Interval` (60 seconds) sets the pace, which is latency enough for review. Webhooks would be immediate but need admin rights on each repo and a process reachable from GitHub to receive them. Notifications only say which PRs to look at; the open PRs they name are then fetched in one `nodes(ids:)` query and stored, so the window compares stored rows and doesn't care which route an update came by. That lookup also fetches commit, comment and review thread counts, which the list searches don't: on a full page of 100 results they took the search to GitHub's time limit and it returned 502s, so a search keeps the counts last looked up. A token that can't read notifications falls back to that query over every open PR each minute. Notifications only cover threads the user participates in, which is every PR they've authored or been asked to review, and so nearly every PR Loupe opens. Whether a push on its own updates a notification hasn't been confirmed; if not, the lists' refresh still brings a moved head to the banner within a few minutes.

### The lists tab can't be closed and stays first

The lists are the app's home, so their window has no close button and refuses closing, including the tab bar's "Close Other Tabs", which asks the window's delegate rather than checking the button. With no SwiftUI window scene there is no File menu of SwiftUI's, so the app supplies "Close Tab" (⌘W) and "Close All" (⌥⌘W); both pass over the lists rather than beep at them. "Merge All Windows" run from a PR's window would put the lists last, so they are moved back to the first tab.

### Linguist's vendor list is narrowed for review

Linguist's `vendor.yml` serves language statistics, so it also names things a reviewer must see: `testdata/`, test fixtures, `.github/`, git and editor config, `Jenkinsfile`, `.d.ts` declarations. GitHub itself never hides vendored paths in a diff. Loupe hides dependency trees, minified bundles, lockfiles and generated files, and keeps the rest; the kept patterns are listed verbatim in `PathFilter` and a test checks each still exists in Linguist's list, so a Linguist update that renames one is noticed rather than silently hiding files.

### Snapshots are how anyone sees the UI without a screen

`Scripts/snapshot.sh` builds the app, launches it as an invisible accessory process with its windows off every screen, waits for lists and diffs to load, writes a PNG per window and quits. Agents can't launch a GUI from the sandbox, so this is the only sanctioned way to run the app other than `--bench`; launching it any other way opens real windows on the user's screens.

### The conversation tab is a web view of GitHub's own HTML

A PR view has GitHub-style segmented tabs, Conversation and Files changed, inside the window rather than a second tier of native tabs. The conversation is one web view built from the `bodyHTML` fields GraphQL returns for the description, comments and reviews, so mentions, code blocks, tables, task lists and emoji render exactly as on github.com with no markdown engine of our own. The diff stays native. The HTML and its styling are ours to change later. Known limit: images attached to private repos need a browser session and may not load.

### Viewed files sync with GitHub, and pulling past a file's end marks it viewed

A file's "Viewed" state is GitHub's own `viewerViewedState`, read and written through GraphQL (`files { path viewerViewedState }` paged to the end, as vendored files swamp the list; `markFileAsViewed` and `unmarkFileAsViewed`), so a review started in Loupe carries on at github.com and back. It's stored per PR and path so a tab shows it at once, and fetched afresh when a tab opens and on Reload. A change shows immediately and is put back if GitHub refuses it. `DISMISSED`, a viewed file changed by a later push, is flagged in the sidebar and counts as not viewed when moving on.

Moving on is a gesture like pull-to-refresh at the bottom: pulling past the end of a file's diff reveals an indicator that fills over about 80pt, gives a haptic tap when full, and letting go then marks the file viewed and shows the next file not viewed, wrapping to the top. Reaching the end is the moment a reviewer has finished a file, so the gesture costs nothing extra and needs no reach for a checkbox. Only a live drag counts, never momentum bouncing off the end, so a fling through a file can't mark it by accident; the threshold logic is a pure type, `OverscrollTrigger`, since scroll events can't be driven headlessly. ⌘↓ and `]` do the same from the keyboard and ⇧V toggles the shown file. The bare keys are handled by a key monitor that steps aside while text can be typed, rather than as menu shortcuts, which would take them from every text field.

### Each file's diff ends in a footer that moves on; pulling past it is a shortcut

Every PR file's diff ends in a footer inside the scrolled content, a bar like the file's header with a button that marks the file reviewed and shows the next one not reviewed. This revises the gesture above as the only way: a mouse wheel never pulls past the end, and on a trackpad the stretch had to be held while 80pt filled, so the user found the control hard to reach at all. The footer is reached by ordinary scrolling and clicked like any button; a file shorter than the view has it straight after its last row. The pull stays as a shortcut, now over about 40pt, and fills the footer itself rather than a separate indicator that existed only mid-stretch. The footer lives in the scroll view's clip view, placed in the document's coordinates, with a bottom content inset to make room, so the text view stays the document view and its wrapping and lazy layout are untouched.

### The conversation tab: replies come from threads, and the web view is kept

An addendum to the conversation tab's decision. GitHub's timeline omits reviews that only reply in threads, so thread replies are fetched with `reviewThreads` (bodies and authors) and shown inside the thread under the review that started it, as github.com does; a review's own comments give each thread's path, lines and diff hunk. The conversation is stored in tables per kind of row (timeline items, review comments, threads, thread comments, checks), keyed by PR and item id, and fetched on opening a PR's tab and on Reload rather than when the tab is first chosen, so it's usually there by then. The web view is made the first time Conversation is chosen and kept hidden behind the files after that, as is the diff behind it, so neither loses its place. The page is assembled in Swift rather than by a script in the page, so it runs with no script at all under a Content-Security-Policy that loads only GitHub's images. ⌃1 and ⌃2 switch, since ⌘1–⌘9 pick window tabs.

### Hidden files are listed, and diffed only when shown

Vendored, lockfile and generated files stay out of the main `git diff`, as a vendor tree can be enormous and would slow every diff, but they are listed under their own "Vendored, lockfiles and generated" section below the files to review, as a reviewer sometimes needs to check a dependency bump or a regenerated file. This revises the goal of excluding them rather than merely collapsing them: they still cost nothing until opened. Their change kinds come from the same `--name-status` listing that decides what's hidden, so they cost no extra git run. Each one is diffed on its own, by literal pathspec (with a rename's old path, so the rename is kept), only when selected, and kept in memory. Until then its row says "added", "modified" and so on in place of line counts, rather than running `--numstat` over a whole vendor tree for counts nobody may look at. Their reviewed state is GitHub's, as for any file, but moving on and the reviewed count pass over them, so the review keys never walk a reviewer through vendored code.

### A commit picker shows one commit's changes

As on github.com's "Files changed", a popup above the file list picks "All changes" or one of the PR's commits, oldest first. The commits come from `git log <merge-base>..<head>` in the checkout, not from GitHub, so they always match the diff shown. A commit's changes are from its first parent, or the empty tree for a root commit, and are diffed when first picked and kept per tab; a range names its commits, so a cached diff can never go stale. Reloading goes back to "All changes". Reviewed state stays per path, as GitHub keeps it, whatever is shown.

### One window with the app's own tab strip, replacing native window tabs

This reverses "PRs open as native window tabs, replacing the custom tab strip" and "Windows are AppKit's, not SwiftUI scenes" as far as they make a window per PR, and relaxes "The lists tab can't be closed and stays first". The user wanted the lists to be a button that is always there rather than a tab, and tabs two rows high with the PR's title under `repo #number`, which native window tabs can't do. So there is one window, and directly under its unified title bar sits a strip of our own: a "Pull Requests" button first, then a tab per open PR. It's in the window's content rather than the title bar, where both earlier SwiftUI strips lost their clicks to window dragging, and it's AppKit views rather than SwiftUI so a click always lands; a snapshot-run hook clicks it through the window to prove so. Each PR's view is made when its tab is first shown and then kept, hidden, so tabs keep their diffs, scroll positions and web views as separate windows did. The window's title and toolbar still come from SwiftUI's scene bridging, from one SwiftUI view at the window's root that wraps the AppKit strip and content and declares the shown item's title and toolbar, since only the window's root hosting controller bridges them. ⌃Tab, ⌘W and moving between tabs are now the app's own; "Move Tab to New Window", "Merge All Windows", dragging tabs to reorder them and seeing two PRs side by side in separate windows are lost. Closing the shown tab shows its neighbour, as native tabs did; a middle click on a tab closes it, as in browsers; and the window itself has no close button, as the lists' window had none.

### Pulling past the footer is real scrolling, fires mid-drag, and fills the button

This revises how the pull shortcut feels; the user found it still too hard and too slow. Below the footer is some slack, about the footer's height again, added to the bottom content inset, so pulling past the footer is ordinary unresisted scrolling instead of AppKit's rubber band, which resists hard. Progress is how far into the slack the view has scrolled, and the slack is there whatever the file's length, so a file shorter than the view can still be pulled. It fires the moment a live drag crosses the threshold, now about 32pt, with the haptic tap then, rather than waiting for the fingers to lift. Momentum still never fills or fires it, so a flick through a short file can't skip it. Once fired it stays spent until the view is back out of the slack, and the rest of that gesture, momentum included, is dropped so it doesn't scroll the next file. With no rubber band to spring back, the view glides back out of the slack once scrolling stops with the fingers lifted, however it got there. The progress fills the footer's button itself, inside its rounded bezel, accent while filling and green as it fires, rather than a band across the whole footer; the button has its own style, drawn like a large push button, to make that possible. The footer's button was also unclickable: a clip view hit-tests only within its document view, and the footer sits below the text view in the inset, so the clip view is a subclass that hit-tests its other subviews too.

Addendum: like pull-to-refresh, the slack holds a caption saying what the pull will do, worded for the case at hand (moving on, the last file, or already reviewed). It fades in with a live drag's progress, says "Marked reviewed" as it fires, and shows nothing at rest or while the view settles back from a pull let go short.

### A checkout matches a repo by any of its remotes

A fork's checkout has the fork as `origin` and the repo it came from as another remote, often `upstream`, and PRs to that repo were reported as having no checkout. So a checkout now matches a repo when any of its remotes points at it on github.com, whether found by name under the search roots or located by hand. When one directory per search root is a candidate, one whose `origin` is the repo wins over a fork's, so a plain clone is preferred. Fetching a PR uses the checkout's remote for the PR's repo (`origin` if several match) for both the PR's ref and the base's remote-tracking branch, still writing only under `refs/loupe/`. The remote is looked up again at fetch time with one git call rather than stored beside the path, so the store is unchanged and a remote renamed since stays right. Remote URLs are read as configured, before any `insteadOf` rewrite, since that's what names the repo.

### Checks show as a bare glyph, and hovering lists each check

A PR's overall check state is a plain coloured tick, cross, clock or question mark, with no filled circle, as the filled symbols were the loudest thing in a row. Hovering it gives a native tooltip like GitHub's checks popover: a summary line ("2 of 5 checks failed"), then a line per check with a glyph, its name and its description (a check run's title, where Codecov puts its coverage), failing first, then pending, then the rest in GitHub's order. The text is built by a pure function in `LoupeModel` so it's tested without a UI.

The per-check contexts come from a separate lookup by id, not from the list searches. Measured against the real API on a full page of 100 open PRs: the author search took about 7.5s without contexts and 8.4–9.6s with them, and a denser 100-PR search went from about 9s to GitHub's 502 at about 11s in three tries of four, which is the time limit the activity counts already hit. A lookup of only id, rollup state and contexts takes about 2.5s per 50 PRs and 4–5.5s per 100, so it runs after each list refresh in batches of 50, over every open listed PR. Every one is asked about because a check finishing doesn't change a PR's update time (19 of 44 of the author's PRs had a check finish after it), so the searches for changes never report it; the rollup state is taken from the same lookup, so the glyph and its tooltip agree. The contexts are stored per PR in their own table and replaced on each lookup, so the tooltip works from the stored copy; until the first lookup the tooltip only names the overall state. The refresh counts as loading until the checks are in. Only the first 50 contexts of a commit are fetched.

### Conflicts show as a badge, from the same lookup by id as checks

A PR whose branch conflicts with its base gets a quiet "Conflicts" badge beside its state badge, in the lists and in the PR header; nothing shows for a clean merge or while GitHub is still working it out. The state is GitHub's `mergeable`, which GitHub computes lazily in the background and answers `UNKNOWN` until it has, so a freshly pushed PR may show nothing until a later refresh.

It's asked for in the lookup by id that fetches checks after each refresh, not in the searches. Measured on a full page of 100: adding it to the author search took it from about 7.5s to 8.5–9.5s, the denser 100-PR search hit a 502 again, and 67 of the 100 came back `UNKNOWN`. In the lookup it raised a batch of 50 from about 2.6s to 3.6–4.9s, within the limit, and answered for all 50 there, though a lookup can still meet `UNKNOWN` on a PR GitHub hasn't got to. The searches and the by-id row lookup leave the stored value alone, so it's only replaced by the next status lookup.

### PRs open on the Conversation tab

A PR's tab now opens on Conversation rather than Files changed, reversing the earlier default. The description and the discussion so far say what a change is for and what's still open, which is what to know before reading its diff, as github.com's own default page assumes. The tab shown is still kept per PR while the window lives, so switching to Files changed sticks.

### Hidden files show their line counts from the start

Each hidden file's additions and deletions come from `git diff --numstat` over the paths hiding them, run beside the main diff, so the hidden section shows `+N -M` like the files to review without producing their diffs. On atrium vendor bumps of 1,000 to 2,400 files it took about 80ms. A row still says added, deleted or renamed, which the counts alone don't, and a binary file says so rather than `+0 -0`.

### Reviewers show in the header on the viewer's own PRs, and more can be asked there

On a PR the viewer wrote, the header's right side lists its reviewers as github.com's sidebar does: everyone asked and not yet answered, then everyone else's latest review (approved, changes requested, commented or dismissed), each with a plain symbol rather than a filled badge so the header stays quiet. Someone asked again after reviewing shows as asked. The author's own reviews, which are their replies to threads, aren't listed, nor is an unsubmitted one. Two columns of up to three rows fit beside the title; beyond that the last place says how many more, with their names in its tooltip. The data comes with the conversation (`reviewRequests` and `latestReviews`), is stored with it and shown from the store at once, so it refreshes when the conversation does: on opening the PR and on Reload.

A button there opens a search of the repo's assignable people and, for an organisation's repo, its teams. They're two queries, so a token that can't read teams still finds people, and that failure isn't shown. Choosing someone calls `requestReviews` with `union: true`, so others already asked stay asked; the reviewer shows as asked straight away, the conversation is fetched again once GitHub agrees, and if it refuses they're taken off and the reason shows in the popover (or, once it's closed, as a warning symbol beside the reviewers). Anyone who has reviewed has a re-request button using the same call, as on github.com. Requests aren't queued or retried: asking someone notifies them, so a failed request is left for the viewer to make again.

Whether the PR is the viewer's is decided by its author's login against the viewer's, which the lists store; a tab looks it up itself if nothing has yet. On anyone else's PR the place is left empty, kept for the approve and request-changes controls that will come with submitting reviews.

### Markdown files can be read rendered, by GitHub's own renderer

A PR's file that Linguist takes for Markdown has a "Source | Rendered" toggle in its header, Source by default. Rendered shows the file at the head of the shown changes (the whole PR or the picked commit), or for a deleted file at their base, read from the checkout with `git show <oid>:<path>` and rendered by GitHub's `POST /markdown` in `gfm` mode with the repo as context, so it reads as on github.com without a markdown engine of our own, as the conversation does. It's shown in a web view with the conversation's template, stylesheet and Content-Security-Policy (no scripts, only GitHub's images), and links open in the browser. Relative links resolve against the file's directory on github.com at that commit, which suits links to other files; relative images then point at an HTML page and don't load, as private repos' images wouldn't anyway. `gfm` mode renders a soft line break as `<br>`, as comments show it, so the file layout hides `<br>` inside paragraphs, which a file view on github.com shows as a space; an explicit hard break is lost with them. `markdown` mode was rejected as it drops task lists and the table markup GitHub uses. Each rendering is kept per file and commit while the tab lives, so toggling back is instant, and the toggle's choice is kept per path. The rendering covers the diff rather than replacing it, so the diff keeps its scroll position; the review footer is the diff's, so moving on from a rendered file is by the keys or the header's checkbox. Change highlighting within the rendered view, GitHub's rich diff, isn't attempted: it would mean diffing two renderings' DOMs.

### Web views stay in GitHub's light theme

The conversation tab and rendered markdown files use GitHub's own HTML, which carries dark-theme variants, and the page's stylesheet had a dark palette behind `prefers-color-scheme: dark`, so both followed the system appearance. The user prefers reading them in GitHub's light theme, so the stylesheet keeps only the light palette and the web view's appearance is pinned to aqua, which is where WebKit takes `prefers-color-scheme` from. The native diff and chrome still follow the system.

### Wrapped rows hang two columns in from the code

An addendum to "Long diff rows wrap with a hanging indent": a continuation that started exactly on the code column was easy to read as a new line, so wrapped lines now hang two character widths further in, as editors do.

### The viewer's own PR descriptions are edited as markdown, starting from GitHub's copy

On a PR the viewer wrote, decided by login as for reviewers, an "Edit description" button sits at the trailing end of the Conversation / Files changed row while the conversation is shown. It swaps the web view for a native editor in the same place: a plain `NSTextView`, monospaced, with spelling, smart quotes, dashes, text replacement and link detection off, as it holds markdown that GitHub renders and any substitution would change what's sent. Below it a caption says the description is GitHub-flavoured markdown, beside Cancel and Save; ⌘↩ saves and Esc cancels, the text view taking both itself so they work while typing. Save is disabled until the text differs, and Cancel with changes asks before dropping them. There's no preview: saving shows GitHub's own rendering, as the conversation is fetched again straight after, and a second renderer of our own could disagree with it.

The editor starts from the description fetched afresh from GitHub when it opens, not the stored copy, because descriptions are also edited on github.com, where images are uploaded and links added, and saving a stale copy would silently undo that. If that fetch fails the editor says so and offers Retry, rather than falling back to the stored copy. The raw `body` is still fetched and stored with the conversation, so it's at hand, but is never what's edited. Line endings are made newlines when the editor opens, since a description typed in a browser can come back with `\r\n` and would otherwise count as changed before anything was typed. Saving calls `updatePullRequest` with the body alone; a refusal keeps the editor open with its draft and the reason. A change made on github.com while the editor is open is still overwritten by saving; checking for one first was left out until it bites.

### The viewer's own PR shows "Self-reviewed" once every file to review is marked viewed

The author wanted a way to mark their own PR as ready for others to review, and reviewing it themselves in Loupe is that moment. So on a PR the viewer wrote, once every file to review (not the "Vendored, lockfiles and generated" section) is marked Reviewed, a quiet green "Self-reviewed" badge shows beside the state badge, in the lists and in the PR header. A file changed by a later push (`DISMISSED`) counts as not viewed, as when moving on. Whether the PR is the viewer's is decided as for its reviewers, by the author's login against the viewer's.

It's knowledge only Loupe has, derived from GitHub's viewed state plus the local diff: which files are to review comes from the diff, so producing a PR's diff records its reviewable paths beside its head commit, replaced with each diff. The badge needs that head to be the PR's current head, so a push clears it until the new diff is produced and its files reviewed. The lists show it from the store with no network, so a PR never opened in Loupe shows nothing; the header follows the viewer's marks as they're made. It does nothing on GitHub: no draft to ready, no label, no review request. Whether it should is left for later.

### Who could review is fetched once a run per repo, and filtered as you type

Searching GitHub (`assignableUsers(query:)` and the org's teams) after each pause in typing made every search in the request-a-review popover wait on two round trips. Instead a repo's assignable people and its org's teams are fetched once a run, all pages of 100, kept in memory by `owner/name` and shared by every tab, and the popover filters them locally on login and name, ignoring case, as each key is typed. The repos I review have about 16 to 21 assignable people and the org 8 teams, so it's one page of each. Opening the reviewers on one's own PR starts the fetch, so the popover usually opens full; a fetch already on its way is shared, and one that fails isn't kept, so opening the popover again retries. A refusal to read teams still leaves them out quietly and the people are kept; any other failure fails the fetch rather than being taken as no teams. They're not stored, so someone joining a repo shows up on the next launch.

### Pulling past the footer is pull-to-refresh: finger travel arms it, letting go fires it

This supersedes "Pulling past the footer is real scrolling, fires mid-drag, and fills the button" for the gesture itself; the filled button and the hint stay. Neither earlier version was the pull-to-refresh pattern the user expected. Measuring the rubber band's stretch made it too hard, as AppKit damps the stretch to a fraction of the finger's travel; unresisted slack firing mid-drag made it far too sensitive, as any drag running past the end fired. Now the rubber band is back and the footer is the last thing in the document, with no slack below it, and progress is the finger travel of a live drag counted from when the view is already at its end, so the damping no longer matters and reaching the end costs nothing. About 80pt of travel, the usual pull-to-refresh distance, arms it: one haptic tap, the button full and green, and the hint saying what letting go will do. Pulling back under that disarms it. It fires only when the fingers lift while armed, once per gesture; lifting short, or a cancelled gesture, does nothing and the fill empties as the rubber band springs back. Momentum never counts, so a fling into the end can't fire it, and a mouse wheel has no pull at all, using the footer's button or ⌘↓ and `]`. With firing on release there's nothing left of the gesture to swallow and no slack to glide back from, so both are gone. A short file still stretches its text view to the view's height, so it can be pulled too. The hint sits in the gap the rubber band opens below the footer and shows only during a live drag, fading in with progress.

### Grammars CodeEditLanguages lacks are vendored as C targets

CodeEditLanguages has no Protocol Buffers grammar, and the repos I review have many `.proto` files, so that grammar is vendored as its own SwiftPM C target, `TreeSitterProto`: upstream's generated `parser.c` and headers, unmodified, with its `highlights.scm` as the target's resource. It's coder3101/tree-sitter-proto, which nvim-treesitter uses and which is maintained, at a tagged release; mitchellh's and treywood's grammars haven't changed since 2021 and 2023. Its query uses the standard capture names the highlighter already maps, and its parser's ABI is within what the resolved tree-sitter runtime accepts. A generated parser is plain C with no build step, so vendoring it avoids the separate upstream SwiftPM manifests that "Grammars come from CodeEditLanguages" moved away from. `Scripts/update-tree-sitter-proto.sh <ref>` re-fetches it, records the tag and commit in `VERSION`, and prints the parser's ABI to check. Scalar types (`string`, `int32`) take the keyword colour, as the query marks them built-in types; as with other grammars, a hunk starting inside a `message` can leave its first fields' types plain. Its query is found the way CodeEditLanguages' are, in its resource bundle beside the executable or in the app's `Contents/Resources`, where `Scripts/bundle.sh` already copies every bundle. Another missing language (HCL, Makefile) would be added the same way.

### Hidden context is expanded from the checkout, with GitHub's arrows

Hunk headers carry GitHub's expand arrows in their gutter: ↑ reveals 20 lines above a hunk, ↓ 20 below the hunk before, ↕ closes a gap of 20 lines or fewer in one go, and a row after the last hunk reveals 20 more towards the file's end. 20 is GitHub's step. A gap that closes merges its two hunks, keeping the earlier header's function context, and headers are recounted so they stay true to their lines. The arrows are characters in the gutter, not SF Symbols, as the gutter is text; they're tagged like the line numbers, so copies leave them out, and carry a tooltip and a pointing-hand cursor. They act on the first click even in an inactive window, as buttons do.

The lines come from the file at the head of the changes shown, the PR's head or the picked commit, read with `git show` once per file and commit and kept while the tab lives, rather than by diffing again with more context: lines outside hunks are the same on both sides, so the new side's text and the offset the changes before them leave give both line numbers, and the change is a pure function on the parsed diff that tests can check against `git diff -U` with the whole file. The file is read when shown so the end-of-file row can be offered; until it's read, only the arrows that don't need its length show. Added, deleted and binary files have nothing to reveal. What's revealed is kept per file and range, so moving between files or commits keeps it, and producing the diff again drops it, as the lines it was revealed around may have moved. The clicked arrow's row holds still on screen while the lines arrive, so another click reveals more; when the gap closes and the row goes, the code next to it holds instead. Revealed rows are ordinary context rows, so they're highlighted with the rest of their hunk.

### Pulling past the footer counts only once held past the end, at half rate

This supersedes "Pulling past the footer is pull-to-refresh: finger travel arms it, letting go fires it" for how far and how long the pull takes; the rest of it stands. The user still found it too sensitive: a normal scroll that reaches the end with the fingers moving spends the rest of its travel past the end, easily 80pt on a trackpad, so it armed and fired on lift and files were marked reviewed while just scrolling to the bottom. Pull-to-refresh elsewhere makes the start of a pull cost something. Android's `SwipeRefreshLayout` (AOSP) ignores movement within the touch slop, counts drag at `DRAG_RATE = 0.5` of the finger's travel, and fires on release once that passes the target, 64dp by default, so about 128dp of finger travel. `UIRefreshControl` arms once the content is well past the control's height after rubber-band damping, also well over 100pt of finger travel. MacPullToRefresh (adamtheturtle, MIT), an AppKit implementation, brackets the pull with the live-scroll notifications, arms at 44pt of damped overscroll and fires only if still over that at release.

None of those has a time component, but none needs to tell a pull from the tail of a swipe the way a trackpad does, so the pull now starts counting only once the fingers have been past the end for 200ms within the same drag, and beyond a 40pt lead-in, like a touch slop. Travel during the dwell is spent: counting starts from wherever the fingers were when it passed, or the lead-in if that's further. So a swipe running through the end and lifting within the dwell never arms, however far it travels; a deliberate pull arms after at least 40pt plus 128pt, about 168pt of finger travel. Pulling back to the end starts the dwell over. Counted travel goes in at half rate towards a 64pt target, SwipeRefreshLayout's numbers, rather than at full rate to a larger threshold: the arming distance is the same either way, but at half rate the button's fill keeps to about the pace of the damped rubber band, so it reads as resisting. The fill and the hint stay empty through the dwell and lead-in. As before, it fires only if armed when the fingers lift, so pulling back under the target cancels, which is MacPullToRefresh's "still past the line at release" too. Its other idea, filling to the peak of the pull so the indicator doesn't flicker, isn't taken: finger travel doesn't jitter as the clip view's bounds do, and a fill held at its peak would show green when letting go won't fire. The four numbers are constants at the top of `OverscrollTrigger`, to tune by feel; the event timestamps feed the dwell, so it's tested headlessly.

### The commit picker lists each commit's whole first line and diff-stat

This revises "A commit picker shows one commit's changes" as far as its popup menu goes. A menu cuts each title to its width and says nothing of how big a commit is, which is what a reviewer weighs when choosing whether to step through commits, as github.com's commits dropdown shows. It's now a button naming what's shown that opens a popover, about 480pt wide, with a `List` of "All changes" then each commit, oldest first: its whole first line, wrapping if long, over its diff-stat (`3 files  +42 −7`) and its short oid. The shown choice is ticked and starts highlighted; a click picks and closes, and the arrow keys move with Return picking, so moving through the list doesn't diff each commit passed. It stays native, a SwiftUI `List` in a `.popover`, rather than an `NSMenu` of custom views.

The stats count only the files to review, as the "N of M reviewed" count does: hidden vendored, lockfile and generated files are left out. The whole PR's comes from its parsed diff at no cost. Each commit's comes from `git diff --numstat` over its range (first parent, or the empty tree for a root commit), so it matches the diff that commit shows, a few runs at a time, with one `git check-attr` over all their paths to decide what's hidden. They're counted when the commits are first shown on the Files tab rather than when the popover opens, so it opens complete: over 30 commits of this repo it took about 165ms, in the background. ### The checks glyph opens a popover after a short rest, not a tooltip

This supersedes the tooltip part of "Checks show as a bare glyph, and hovering lists each check". A native tooltip takes about a second to appear and is plain text, so a reviewer scanning the lists waited on it and couldn't follow a check to its page. Resting the pointer on the glyph for 200ms now opens a popover like github.com's: the same summary line, then a row per check in the same order (failing, then pending, then the rest), each with its coloured status glyph, its name, and its description in secondary caption type, where Codecov puts its coverage. ### Generated code is also told by its first lines, as Linguist does

This supersedes "Languages and hidden files follow GitHub Linguist's data" where it says Linguist's content heuristics aren't run, for generated files; languages are still chosen by name alone. A `.pb.go` file that `protoc-gen-go` wrote was listed for review in Loupe but collapsed on github.com, because Linguist's `generated.rb` decides "generated" mostly from content: Go's convention is a `// Code generated … DO NOT EDIT.` line at the top. `GeneratedCode` ports the rules of `generated.rb`, at the release `VERSION` names, that look only at a file's first lines, each with Linguist's extensions, line counts and strings or regexes unchanged: `generated_go?` (a line starting `// Code generated ` in the first 40, so it also catches mockgen, stringer and the rest), `generated_protocol_buffer_from_go?` (20 lines), `generated_protocol_buffer?` (protoc's C++, Java, Python, Objective-C, Ruby and PHP output, 3 lines), `generated_javascript_protocol_buffer?`, `generated_typescript_protocol_buffer?`, `generated_twirp_ruby?`, `generated_apache_thrift?` (6 lines), `generated_grpc_cpp?`, `generated_jni_header?`, `generated_dart?`, `generated_jison?`, `generated_parser?` (PEG.js), `generated_html?` (pkgdown, mandoc, Doxygen and `<meta name="generator">`, 31 lines), `source_map?`, `generated_racc?`, `generated_jflex?`, `generated_grammarkit?`, `generated_jooq?`, `generated_antlr?`, `compiled_cython_file?`, `generated_module?`, `generated_unity3d_meta?`, `generated_roxygen2?`, `generated_perl_ppport_header?`, `generated_gamemakerstudio?`, `generated_gimp?`, `generated_visualstudio6?`, `generated_haxe?`, `generated_sorbet_rbi?` and `generated_mysql_view_definition_format?`, plus the first-line test of `compiled_coffeescript?`. Linguist has no rule for Swift, so a `.pb.swift` stays in review, as on github.com.

Rules needing the whole file or its end aren't ported: `minified_files?` (average line length over every line), `has_source_map?` and `vcr_cassette?` (the last lines), `generated_net_docfile?` (the second-last line), `generated_postscript?` (a scan of all its data) and `compiled_coffeescript?`'s scoring of every line. Each would mean reading whole files, often large ones, for little: minified bundles are mostly caught by `vendor.yml`'s `.min.js` patterns already. The path-only rules of `generated.rb` (more lockfiles, `.idea/`, `Pods/` and so on) are a separate question and aren't taken here.

The content is read from git, not the working tree: the file as the range shown leaves it (the PR's head, or the picked commit), or for a deleted file as it was at the range's base, since the checkout may be on any branch and is the user's own. Only paths whose name brings in a content rule and that path rules and attributes haven't already decided are read, all in one `git cat-file --batch` per diff (and one for all of the commit picker's ranges), keeping each file's text only up to the last line its rules read. A `.gitattributes` `linguist-generated` either way still wins, and such a path is never read. A file hidden by its content is hidden exactly as one hidden by its path: out of the diff, in the hidden section with its line counts, out of the review count, the reviewable paths recorded for the Self-reviewed badge, and the commit picker's stats. A stored diff record's reviewable paths from before this keep the old answer until the PR's diff is next produced. On atrium, reading all 569 non-vendored files that have a content rule, 6.5MB, took about 130ms in a debug build, git itself about 50ms; a PR's few dozen such files cost a few milliseconds.

### Review threads show inline in the whole PR's diff, as native views over reserved rows

Each review thread shows under the line it ends on in the file's diff, as on github.com: its comments in order, each with its author, a relative time and its body. A thread over several lines notes the range in its header. The anchor is GitHub's own `line` on `diffSide`, a file line number on the head (RIGHT) or base (LEFT), so a comment on a deleted line sits under that line; it's matched against the rows' line numbers, so lines revealed around a hunk can bring a thread into place. Threads with nowhere to go, outdated ones (`line` is null), those on the whole file, and those on a line the diff doesn't show, are listed after the last row under "Not on the current diff", each with the end of the diff hunk it was made on, so nothing is lost. A resolved thread is one quiet line, "Resolved · N comments · login" naming who started it, until clicked; a hidden comment is a line saying so until clicked. What's opened stays open while the tab lives. The file list shows each file's unresolved count beside its name, hidden files' included, and the reviewed count is untouched.

Threads only show on "All changes". GitHub anchors a thread to the PR's current diff, and a single commit's diff numbers its lines differently, so a thread placed there could sit on the wrong line; with a commit picked, neither the diff nor the file list shows any.

The diff stays one `NSTextView`, which "What I'd change in the plan" named the risk. Each block of threads gets an empty row of its own height in the attributed string, a one-line paragraph with a fixed line height, and an `NSHostingView` is laid over that row as a subview of the text view, so it scrolls with the text and the lazy layout, wrapping, find and copying of the code are untouched. The row is tagged as gutter, so a copy across it leaves it out, as it does the line numbers. The SwiftUI view reports its natural height for the width it's given and the row's paragraph is changed to match, which moves only what's below. Rejected: TextKit 2 attachment view providers, as the view is TextKit 1 for its row painting; and a text view per hunk with views between, which breaks selection across hunks. Placing a block lays out the text above it, so a thread near the end of a very large file costs a whole-file layout when shown.

Bodies are GitHub's `bodyHTML`, read natively into paragraphs with bold, italic, code and links, code blocks, quotes, list items, table rows and rules, and shown as SwiftUI `Text`, whose links open in the browser. A web view per comment was ruled out as heavy, and `NSAttributedString`'s HTML import because it runs WebKit on the main thread and fetches images; here images become links to themselves, so nothing is fetched to show a comment. Threads come with the conversation, which now asks each thread for its anchoring (`startLine`, `diffSide`, `originalLine`, `originalStartLine`, `subjectType`), who resolved it, what the viewer may do with it, its first comment's `diffHunk`, and each comment's REST `databaseId` and `minimizedReason`; they're stored with it, so they show at once and refresh when it does.

### Replies post at once over REST, and resolving shows before GitHub agrees

Each thread the viewer may reply to has a Reply button that opens a plain-text field under it, with the description editor's conventions: markdown as GitHub takes it, ⌘↩ sends, Esc cancels, and cancelling with text asks first. A refusal keeps the draft open with the reason under the thread, as the description editor does.

A thread's header has Resolve conversation or Unresolve conversation, whichever GitHub says the viewer may (`viewerCanResolve`, `viewerCanUnresolve`), through `resolveReviewThread` and `unresolveReviewThread`. The change shows at once and is put back with the reason if GitHub refuses, as viewed files are; a thread resolved here folds to its one line, as on github.com. After a reply or a change, only the PR's review threads are fetched again, in one query rather than the conversation's paged timeline, so the thread shows as GitHub has it, and stored. Drafts and errors are kept per thread while the tab lives, so moving to another file and back doesn't lose them.

### New comments start from a "+" in the gutter and post at once

### The viewer's own PRs can be merged from the header, with merge commits only

On a PR the viewer wrote, decided by login as for its reviewers, a Merge button sits under the reviewers while it's open, and goes once it's merged or closed. It only ever makes a merge commit, as the user never wants squash or rebase, so there's no method to pick and the repo's merge settings aren't fetched; a repo that doesn't allow merge commits refuses the merge, and GitHub's message shows like any other refusal. On anyone else's PR the place stays empty, kept for review controls.

Whether it can be merged is GitHub's own merge-box verdict, `mergeStateStatus`, rather than one worked out here from checks, reviews and conflicts: only GitHub knows the base branch's protection rules, which checks are required and whether pre-receive hooks apply, and recomputing those would drift from what github.com says. It's asked for, with `reviewDecision`, in the lookup by id that already fetches checks and `mergeable` after each refresh, stored in its own column, so it costs no extra request and is as fresh as the checks. The button is green and enabled for `CLEAN`, `HAS_HOOKS` or `UNSTABLE` (failing checks that aren't required) with the review decision `APPROVED`, and red and disabled otherwise with the first reason that applies, in this order: "Conflicts with <base>" (`DIRTY`, or `mergeable` `CONFLICTING`), "Changes requested" or "Not approved" (any other review decision, none included, as only approved PRs are merged from here), "Checks failing" (`BLOCKED` with a failing rollup) or "Blocked by branch protection" (`BLOCKED` otherwise, such as required checks still running), "Draft", then "Behind <base>" (`BEHIND`). GitHub answers `BLOCKED` for a draft, `DRAFT` being deprecated, so a draft is told by `isDraft` and given as the reason rather than branch protection. `UNKNOWN`, or a PR not yet looked up, gives a plain disabled button with no reason while GitHub works it out. A disabled button loses its tint, so the red is carried by a symbol beside the reason.

Clicking asks first, naming the branches ("Merge grpc-cache-status into master?"), then calls `mergePullRequest` with `mergeMethod: MERGE` and `expectedHeadOid` set to the head last looked up, so a push between that lookup and the click is refused by GitHub rather than merged unseen. A spinner shows while it runs. Once merged the PR is looked up again by id, so the header's badge says Merged, the lists update and the button goes; a refusal shows GitHub's message under the button. The head branch isn't deleted: GitHub's "Automatically delete head branches" repo setting does that where a repo wants it, and Loupe doesn't second-guess it.

### The header is three sections: info, merge, reviews

The PR header is one top-aligned row of three sections. It sits outside the file list's `List`, so the list shows no selected row meanwhile; its selection is kept, and picking any file shows the files again. The sidebar is there before the diff is ready, with only the Conversation row until the commit picker and files can be listed. PRs still open on the conversation, ⌃1 and ⌃2 still switch, and each PR's choice is kept as before. The "Files changed (N)" count went with the tabs; the commit picker's "All changes" row already counts the files.

### A hunk is parsed led by the line its header names

A hunk that starts inside a declaration lost most of its colours. Parsed alone, a TypeScript type's members or a Go struct's fields read as labelled statements or broken code, and the highlights query doesn't colour those. In PRs reviewed in Loupe, porter's `src/config.ts` had no colours at all, and Go struct, Ruby class and YAML list hunks lost their keywords and keys. Git's hunk header already names the enclosing line (`@@ -122,7 +122,6 @@ export type grpcServiceConfigs = {`), so each hunk's sides are parsed with that line in front, parsed but not shown. It's git's nearest line that starts a declaration, not one known to enclose the hunk: when that declaration closed before the hunk, the line nests what follows inside it. So a side is parsed both ways over its first lines, and in full whichever way colours more of them, ties going to the header's line. A line git cut short at its 80-byte limit is never used, as half a signature makes the code after it parse as parameters, and colours more for it. Across 960 hunks from recent merges and PRs in the repos I review, 38 hunks gained colour and none lost any correct colour (some `go.mod` hunks lost a keyword colour wrongly given to `go` inside module paths). On the bench, highlighting a Go file of 63 short hunks went from 31 to 47ms, and a TypeScript file of 51 hunks from 147 to 158ms. Parsing the whole file instead, as a checkout allows, would also colour hunks inside a multi-line string, such as a GraphQL template literal, which the header can't help with, as tree-sitter can't make an unterminated template string. That needs both versions of each file read before the first paint, so it's left for now.

### The commit picker is drawn as a sidebar row, not a pop-up button

The commit picker is a plain row like the Conversation row: a history symbol, the shown choice ("All changes" or `abc1234  headline`) truncating at the tail, and a small secondary `chevron.down` at the trailing end as the hint that it opens the list. It sits among rows, and a bordered pop-up-style button there read as a form field. It never takes the accent selection fill, being a choice of what the files show rather than a place to go; instead it shows a faint fill while hovered or while its list is open. The divider between it and the Conversation row is gone and the two sit as consecutive rows, with the divider under the picker still setting off the file list.

### The request-review control is a button the size of Merge

Asking for a review is a bordered "Reviewers" button with the `person.badge.plus` symbol, the same size as the Merge button and level with it, at the header's right end. As a caption-sized borderless glyph in the corner it read as decoration and sat higher than the Merge button beside it. Only the reviewer rows stay caption-sized, to the button's left, with the first row on the button's text baseline.

### Codecov's coverage failures don't make a PR's checks fail

GitHub's rollup read as failing on most PRs because of Codecov alone: its project check fails on tiny drifts in total coverage that nobody acts on, and its patch check's target is set too high in these repos, so a well-tested diff still fails it. So a failed `codecov/project` (name in any case) is tolerated, and so is a failed `codecov/patch` while the diff coverage that leads its description ("76.92% of diff hit (target 98.23%)") is at least 70%, Glen's threshold for a diff worth a look. A patch check whose description is missing or doesn't parse still fails, as do Codecov's other checks. When GitHub's rollup is failure or error and every failing check is tolerated, Loupe shows pending if any check is still pending and passed otherwise; any other rollup is shown as GitHub gave it, and so is a failure with no failing check fetched to explain it (rows not yet looked up, or a commit with more checks than are fetched).

The rule is one function in `LoupeModel` (`CheckContext.isToleratedFailure`, `CheckState.tolerating(_:)`), applied when the store turns a row into a `PullRequestSummary`, so the list glyph, the header glyph and its failed names, the popover and the merge button's reason all take the same state without each working it out. The store keeps GitHub's rollup and checks as given, so the rule can change without a migration or a fresh lookup. In the popover a tolerated failure keeps its row and description with its cross in the secondary colour, listed after real failures and pending checks; the summary line doesn't count it as failed but ends "1 coverage failure ignored". The header names a patch check below the threshold as `patch`. GitHub's own `mergeStateStatus` is untouched, so a `BLOCKED` PR whose only failures are tolerated gives "Blocked by branch protection" rather than "Checks failing". The conversation page's checks list still shows each check as GitHub reports it.

### Revealed lines can all be hidden again from the file's header

While a file has lines revealed around its hunks, its header bar shows a small borderless button, `arrow.down.right.and.arrow.up.left`, that hides every one of them, back to the diff as produced. It only hides what's revealed in the changes shown, the whole PR's or one commit's, as each keeps its own. Hiding them one gap at a time isn't offered: GitHub has no such control either, and once gaps have merged hunks there's no clean step back. It's absent while nothing is revealed, so the header stays as it was for most files. When the diff is shown anew without an arrow having been clicked, as when the revealed lines go, the first code row in view that's still there holds still on screen, rather than the scroll offset, so hiding lines above the reader doesn't move what they were reading.

### Lines revealed around a hunk take comments too

This revises "New comments start from a "+" in the gutter and post at once" where it says revealed lines offer no "+". The user wants to comment on code next to a change, as github.com's new Files changed page allows after expanding. Revealed lines are unchanged, so they take comments on the new side with their new line number, posted the same way as any other. Whether the REST endpoint takes a `line` outside the diff's hunks isn't settled by GitHub's docs: they call `line` "the line of the blob in the pull request diff", and the September 2025 changelog that brought comments on unchanged lines to the new page says "API support is currently limited" while such comments are returned by the existing APIs. So it's offered and tried live; if GitHub refuses, the refusal shows under the draft as any other does. Hunk headers and the row after the last hunk still offer no "+".

### Double-clicking a row starts a comment on it

Double-clicking anywhere on a row that offers the "+", its gutter or its code, starts a comment there as the "+" does, so a reviewer needn't aim for a small target at the row's edge. The double-click is taken before the text view's own handling, so it selects no word on those rows; on rows that take no comment (hunk headers, the rows held for threads, one commit's changes) it selects a word as before. Selecting a word to copy from a commentable row now needs a drag; a triple-click still selects the row. The "+"'s tooltip mentions it. It uses the same row lookup as the "+", so the two can't disagree about which rows take comments.

### The pull skips its dwell when a drag begins at the end, and the diff ends in a scroll gutter

The user found marking reviewed by pulling worked less well in a file shorter than the view. Such a file is at its end from the start, so every drag began there and its first 200ms of travel was spent in the dwell, which for a quick deliberate pull is most of it. The dwell is there for a scroll that runs into the end mid-drag; a drag that begins at the end has no scroll behind it to guard against, so `OverscrollTrigger` now skips the dwell then and counts from the 40pt lead-in straight away. The scroll view says whether the view was at its end as the fingers touch down. The same makes pulling immediate in a long file already scrolled to the bottom, lifted and then pulled. A drag that reaches the end while scrolling still dwells, and so does one that began at the end, went back into the document and came down again.

The user also asked for room to scroll past the end. The diff now ends in a gutter of half the view's height, as a bottom content inset below the footer, so a long file's end has its footer about mid-view, and the pull counts only once the view is scrolled to the gutter's end. A file shorter than the view can scroll the gutter too, past the view's own height, but no further than brings its footer to the top, so the footer still shows the pull's progress; a very short file scrolls only that far. The footer stays directly under the last row, and the hint stays in the rubber band's gap below the end.

### A draft offers "Ready for review" in place of Merge

On the viewer's own open draft, the merge section shows a "Ready for review" button where Merge would be, the same size and prominence with the default accent tint, and no reason beneath it. A disabled red Merge with "Draft" under it said nothing the header's Draft badge didn't, while the useful next step for a draft is leaving draft. The wording is GitHub's own, so it reads as the same action as on github.com. A draft gives this button whatever its reviews, conflicts or checks, as github.com offers "Ready for review" on any draft; "Draft" is no longer one of the merge's blocked reasons. This refines "The viewer's own PRs can be merged from the header".

Clicking calls `markPullRequestReadyForReview` at once, with no confirmation, since GitHub lets a PR be turned back into a draft. The merge's spinner shows while it runs, and a refusal shows under the button as a refused merge's does. Afterwards the PR is looked up again by id, and its merge state with it, because GitHub's `BLOCKED` for the draft no longer applies; the button becomes Merge with whatever reason then holds.

### The pull reveals a hidden strip below the footer, and the fill follows once it shows

This reverses the gutter in "The pull skips its dwell when a drag begins at the end, and the diff ends in a scroll gutter"; the dwell skip stands. A scrollable empty gutter helped nothing: it was just a big empty section to scroll to. What the user wants is the pull-to-refresh pattern, as `UIRefreshControl`, `SwipeRefreshLayout` and MacPullToRefresh show it: the normal scroll maximum, with the footer directly under the last row and a short file resting unscrolled, and then, pulling at that maximum, a strip that was hidden below the end comes into view saying what the pull will do, and only once it's showing does the button start to fill.

The strip is as tall as the trigger's lead-in, 40pt, one constant: the lead-in's travel brings the strip into view one-to-one with the fingers, and only travel beyond it fills the button, at the drag rate towards the target as before. The diff moves past its end by itself rather than by AppKit's rubber band, whose damping wouldn't keep to the fingers: a PR's diff has no vertical elasticity, and while a live drag is past the end the clip view holds its bounds past the scroll maximum by the revealed amount, as MacPullToRefresh does, with the strip laid out below the end in the document's coordinates. In a file shorter than the view the strip sits below the view's bottom edge, as below the footer it would show at rest. Letting go, armed or not, animates the view back to the maximum in 0.2s; when it fired, the next file replaces the view once marked, and a file replaced mid-pull drops it at once. A scroll that runs into the end mid-drag reveals the strip with its spent travel, which reads as a bounce, while the dwell still holds the fill. Momentum and mouse wheels never reveal it. A plain diff file, with no footer, keeps the rubber band.

Scrolling back up the document after the button has filled cancels the pull: a live drag that moves with the view away from its end now undoes the pull, so letting go there never fires, and coming back to the end dwells again.

### The file list is a tree of directories, as on github.com

The sidebar's files are a tree, as github.com's "Files changed" tree is: directories as disclosure rows with a folder symbol, open to start with, files under them with a document symbol, and a run of directories each holding only one directory shown as one row named `a/b/c`. Each directory lists its subdirectories before its files, each alphabetically, ignoring case and taking numbers by value. The flat list repeated a long directory path under every file; a tree shows the structure once, and each file is one line with its `+A −D` at the trailing end, where the counts line up down the list. A file with no lines counted says added, deleted, renamed or binary there instead. The tick's slot, the unresolved-thread count and the "changed" capsule stay beside the name, and directories can't be selected, so the arrow keys move between files. Folded directories are remembered while the PR's view lives.

The "Vendored, lockfiles and generated" section is a second tree under its own header, so a generated `.pb.go` still sits under its directory; its rows say added, deleted, renamed or copied before their counts at the trailing end. Moving on to the next file not viewed, and the file a PR opens on, follow the tree's order rather than git's, so they go down the list as shown; git sorts `a/b.txt` before `a/c/d.txt`, the tree the other way round. The diff file mode (`swift run Loupe <diff>`) uses the same tree.

### `.gitattributes` is read at the head of the changes shown, not from the working tree

This supersedes the checkout's own `.gitattributes` in "Languages and hidden files follow GitHub Linguist's data" and the fetch entry's `:(attr:…)` note. A PR that marked `client/src/generated/**` as `linguist-generated` still had those files listed for review, because `git check-attr` reads the working tree's `.gitattributes`, and the checkout is the user's own, on whatever branch it was left on. GitHub reads attributes from the PR's head commit, and Loupe hides what GitHub hides, so the `linguist-*` attributes now come from the `.gitattributes` files at the head of the changes shown: the PR's head for all its changes, the commit itself for a picked commit and for each commit's stats. A file deleted at the head takes the head's attributes too, as GitHub's diff does; its first lines are still read at the base, as before.

`git check-attr --source=<commit>` would do this directly, but needs git 2.40, and Loupe runs `/usr/bin/git`, which Command Line Tools ships as 2.39. So the `.gitattributes` blobs that could apply (one in each changed path's directory and above) are found with one `git cat-file --batch-check` for every head at once, written into a throwaway index file in the temporary directory (`GIT_INDEX_FILE`, `update-index --index-info`), and read with `check-attr --cached`, which ignores the working tree. The checkout's index, working tree and refs are untouched; `$GIT_DIR/info/attributes` and the user's global attributes still apply, as they did. Each head costs two short git runs, a few at a time across the commit picker's commits.

### Homebrew's git is preferred to Apple's

Loupe runs the first of `/opt/homebrew/bin/git` (Homebrew on Apple silicon), `/usr/local/bin/git` (Homebrew on Intel) and `/usr/bin/git` that exists and can be run, chosen once at first use and logged with its `git --version`. Apple's git, from Command Line Tools, lags upstream (2.39 here, against Homebrew's 2.49). Homebrew's is the one Glen's shell runs, so Loupe's diffs match what he sees in the terminal, and newer flags become available. Both read the same global config and credential helpers, so nothing else changes, and with no Homebrew git Loupe behaves exactly as before.

`PATH` isn't consulted: an app launched from Finder or the Dock doesn't get the shell's `PATH`, and recovering it by running a login shell would be slow and fragile. The fixed list covers both Homebrew prefixes. A `LOUPE_GIT` environment variable naming a path wins outright, for testing against a particular git.

Homebrew's git is new enough for `check-attr --source`, but the throwaway-index reading of `.gitattributes` stays, so Apple's git and Homebrew's behave alike and a machine without Homebrew needs nothing else.

### The pull reveals its strip by growing the bottom inset, and its travel says where the end is

This revises how "The pull reveals a hidden strip below the footer, and the fill follows once it shows" moves the view and tells that the drag has left the end; what the pull shows and when it fires stand. The clip view held its bounds past the scroll maximum against AppKit, and on a file that exactly fits the pane AppKit kept resetting them: on a trackpad the strip jumped in and out while the button filled with the content still, and a reset read as the view having left its end mid-drag, which disarmed the pull, so letting go did nothing.

Now the pull adds what it has revealed to the scroll view's bottom inset and scrolls to the new maximum, so the view is held there by AppKit's own scrolling, not against it, and a short file is scrollable by exactly the revealed amount. While past the end the drag's moves go to the pull alone, not to AppKit, so nothing else moves the view. Letting go, armed or not, animates the view back to the footer's maximum in 0.2s and then drops the extra inset; momentum after a drag that ended in the pull is dropped, so it can't fling the document as it settles.

Whether the view is at its end is read from its bounds only until a drag is past it; from then the pull's own travel says, so nothing AppKit does to the bounds can disarm it. Travel back at zero is leaving the end: the pull is undone, the fill empties, further moves scroll the document as usual, and coming back to the end is a scroll reaching it, so it dwells. The rubber band stays off for a PR's diff, as at the bottom it would add to the strip's movement and a drag scrolling into the end would leave AppKit mid-bounce under the inset; so the top doesn't bounce either.

### Links to PRs open them in the app

This relaxes "links open in the browser" in "The conversation tab is a web view of GitHub's own HTML" and "Markdown files can be read rendered, by GitHub's own renderer". PRs reference each other constantly, as one PR's description says "Needs porter#1522", and following such a link out to the browser leaves the review behind. So a link to `github.com/<owner>/<repo>/pull/<number>`, whatever part of the PR it points at (its files, a commit, a comment's anchor), opens that PR's tab, or shows it if it's already open, from the conversation, a rendered markdown file or a review thread's comments in the diff. Every other link, issues, commits and compares included, still opens in the browser, as does ⌘-click or a middle click on a PR link, which ask for a browser tab.

A PR in either list, or already open, opens at once. Any other is looked up on GitHub by repo and number, with the same fields as the lists' rows, and stored with its tab in one write, so a list refresh can't drop it as unlisted first; it then behaves as any PR opened from the lists, viewed files and conversation included, and is forgotten when its tab closes. The lookup doesn't block the window. If GitHub has no such PR the viewer can see, or the lookup fails, the link opens in the browser instead and the reason is logged.

### "Review required" is a badge in GitHub's attention colour

As plain caption text, "Review required" read as information rather than as the thing blocking the merge. It's now a badge like Conflicts, in Primer's attention colour as GitHub shows it, with help saying a review is needed before merging. "Approved" and "Changes requested" stay as coloured text: they're outcomes rather than something still owed.

### Who could review is offered most recently asked first, from a history of requests

The request-a-review popover offered candidates in GitHub's order, people then teams, so the few colleagues the viewer usually asks were wherever their logins happened to sort. Now everyone asked lately in that repo comes first, most recent first, then the rest in GitHub's order; typing filters that list as before. Each request made from Loupe, re-requests included, is appended to a `reviewRequest` table once GitHub accepts it, never on the optimistic add or after a refusal: the repo (lowercased `owner/name`), the reviewer's node id, login or team `org/slug`, kind, the PR's id and when. It isn't tied to the `pullRequest` table, so the history outlives the PRs it was made on.

An empty history would order nothing at first, so the reviewers already on the viewer's own stored PRs count too: anyone asked or reviewing on one counts as used at that PR's last update, unless the table has something newer for them. GitHub doesn't say when a request was made, and those requests weren't made from Loupe, so they aren't written to the table; the one store query merges both. The order is read from the store once a run per repo, alongside the candidates, and each accepted request updates it in memory so the list reorders straight away; reviewers stored with a conversation later in the run count from the next launch.

The ordering is one function of the candidates and when each was last asked, so more can be weighed in later: spreading reviews around, so the same few people aren't always asked, and GitHub's suggested reviewers. Neither is built yet.

### Only the diff waits for a reload; the rest of an open PR follows GitHub

This narrows "Open PRs learn of changes from notifications, and offer a reload". The banner now appears only when new commits are pushed, "New commits pushed" with Reload, as the diff is the one thing a reviewer is partway through and must not have replaced under them. A comment, a review, an approval or a change of state moves nothing in the diff, so there's nothing to protect, and "Updated on GitHub" for those was noise the user had to act on to see what they'd been told about.

When the stored PR shows activity (its update time, state, review decision or counts) and its head hasn't moved, the tab fetches its conversation, which brings the review threads with it, and its viewed states in the background. It waits a couple of seconds first so a burst of changes is one fetch, never starts one while another or the tab's load is underway, and checks again once done for anything stored meanwhile. The tab notices by observing its stored row in the lists, so it doesn't matter whether a notification, the fallback timer or the lists' refresh stored it. A failed fetch keeps what's shown, as before. While new commits wait for the reload, nothing else is fetched either: GitHub places threads by the head's lines, so threads for the new head could sit on the wrong rows of the old diff. Reload still brings everything; dismissing the banner keeps the old diff and the rest follows GitHub again.

The conversation's web view loads a whole new page for new content, which put the reader back at the top, so it reads the scroll position before replacing the page and restores it once loaded. That's done from the app's own script world, which the page's no-script policy doesn't govern. Reply drafts and the description editor are native, outside the page, so a refresh never touches them.

A noticed change on an open PR also looks up its checks and merge state, which the lookup by id leaves out. Before, an approval reached the review decision within a minute but `mergeStateStatus` stayed `BLOCKED` until the lists' next refresh, so the merge box said "Blocked by branch protection" on a PR that could merge. It reuses the status lookup the lists run after each refresh, as "Ready for review" already did, rather than widening the by-id query, so both stay one query each with known costs.

### "Review required" isn't shown in the To review list

Every PR in To review is there because a review is being asked of the viewer, so a "Review required" badge on each row said nothing and drew the eye in amber to every one alike. The To review list leaves it out; "Approved" and "Changes requested" still show there, as they say how others' reviews went. Mine and an open PR's header keep the badge, as there it's news.

### Links from other apps open in Loupe, which is an alternate https handler, not the browser

This extends "Links to PRs open them in the app" to links clicked outside it. Most PRs reach a reviewer as links in Slack and mail, and each one opened in the browser leaves the review there rather than in Loupe. Loupe declares its own `loupe` URL scheme, and `https` with the `Alternate` handler rank. Taking over every https link as the default browser would put the rest of the web in an app that can only send it on, so Loupe never asks to be the default; instead a link router such as Finicky or Velja, which already chooses a browser per link, sends `github.com/*/pull/*` here, either rewritten to `loupe://` or by opening the https URL with Loupe. `open -a Loupe <url>` works the same way.

A PR link is `loupe://github.com/<owner>/<repo>/pull/<number>`, which is exactly a GitHub link with its scheme swapped, as a router's rewrite produces, or the shorter `loupe:///<owner>/<repo>/pull/<number>`; anything after the number is allowed, as for links inside the app. Either brings the window forward, unhidden and unminimised, and opens or focuses the PR's tab as a link in a conversation does, stored PR at once, otherwise looked up by number. A PR GitHub won't show, or a failed lookup, opens the link's github.com page in the browser so the click isn't lost. An https link that isn't a PR goes to the default browser without bringing Loupe forward; a `loupe:` URL that names no PR is logged and dropped, as there's no page to send it to. Links that arrive while Loupe is launching wait until the window has been restored, then open in the order they came.

### While new commits wait for a reload, the rest still follows GitHub; only the diff's threads stay put

This revises "Only the diff waits for a reload", which fetched nothing else while new commits waited. Stopping everything to protect the inline threads also froze what had no need to wait: a reviewer reading the old diff still wants to see a new comment, an approval or a resolved thread in the conversation, the header and the file list. So the tab keeps fetching the conversation, threads and viewed states in the background while the banner shows, as it does with no reload pending.

What waits is where threads are placed on the diff. GitHub places a thread by the current head's lines, so once the head moves a freshly fetched thread could sit on the wrong row of the old diff. The tab keeps the threads as last fetched while the diff was of the PR's head, and while new commits wait, the inline threads and "Not on the current diff" are drawn from those; once the diff is produced again, by Reload or a retry, or the banner is dismissed to keep the old diff as before, they're the conversation's own again. Everything else, the file list's unresolved counts included, follows the latest fetch, so a count can briefly differ from the threads shown inline.

The one way the diff's threads change before Reload is the viewer's own action on them: a reply, resolving or unresolving, or a new comment on a shown line. Those act on the lines being shown, so their result appears inline at once; after the threads are fetched again, the threads acted on, and a new one the viewer started, take GitHub's latest copy, and the rest stay as they were. The diff reads all of this through one property, `placedThreads`, separate from the conversation's threads, so anything else that shows on the diff's lines, such as a pending review's comments, is placed the same way.

### Review requests left unanswered for two weeks are hidden from To review

A PR stays out of the To review list once the viewer's request to review it is more than 14 days old. The age is the request's, not the PR's: when the viewer was last asked, re-requests included, taken from the newest `ReviewRequestedEvent` naming them in the PR's latest request events. The check that drops fulfilled requests already looks up each to-review PR by id on every refresh, so it now asks for those events as well, on the first load as on later ones, and stores the time on the PR as `reviewRequestedAt`. A request of any team counts as asking the viewer, as team membership isn't cheaply known. With no request of the viewer among the events, the PR's update time stands in, since GitHub counts a request as an update.

The PR is hidden when the list is read, not removed from the store, so it stays known to tabs and links, and a fresh request brings it back with the next refresh. The viewer's own PRs aren't affected. A quiet caption under the list says how many are hidden, so a shorter list isn't a mystery.

A request nobody acted on for two weeks is stale noise in a list meant for what to review next; GitHub's own list never prunes them, so they pile up. Glen's list on the day this was built held six such requests, the oldest a year old.

### ⌘§ shows the lists

"Show Pull Requests" is ⌘§ rather than ⌘T. The lists are tab 0 beside ⌘1–⌘9 for the PR tabs, and on the UK layout § is the key left of 1, so ⌘§ reads as "tab 0"; ⌘T means "new tab" everywhere else, which showing the lists isn't. ⌘T isn't kept alongside, as SwiftUI's menu commands can't carry a second key without a second, visible menu item.

### A PR's toolbar can copy its GitHub link

### Reviews are submitted as on github.com: a pending review, then "Finish your review"

This settles review submission, which was left undecided from the start, and fills the place "Reviewers show in the header on the viewer's own PRs" and "The viewer's own PRs can be merged from the header" kept on anyone else's PR. The flow is GitHub's own: comments made into a review are held in the viewer's pending review, which only they can see, until it's submitted with a summary and a verdict. Submitting with no review pending calls `addPullRequestReview` with the event and summary, which submits at once. None of them was run live; their inputs are from introspection.

The pending review is asked for beside the review threads, `reviews(first: 1, states: [PENDING], author: $viewer)` with its id, body and comment count, in both the conversation's query and the threads-only one, and stored on the conversation's row, so the header knows of it at once on the next launch. GitHub lists the viewer's pending comments in `reviewThreads`, as captured on stagehand#1723, so each thread comment's `state` is asked for and stored, and a thread whose first comment is pending is the review's. Those show in place like any thread, each pending comment with a "Pending" badge in the attention colour, but without Reply or Resolve: GitHub says `viewerCanReply` on them (and not `viewerCanResolve`), but how a reply posted at once would sit beside an unsubmitted comment hasn't been tried, and no one else can see the thread to answer yet. After every change to the review the threads and pending review are fetched again. They're the viewer's own, so, as replies do, they show on the diff being read at once even while new commits wait for a reload, turn submitted there once the review is, and go from it with an abandoned review. A refusal while adding to the review fetches them anyway, so a review started or submitted on github.com since is known when the comment is sent again; GitHub allows one pending review per viewer per PR, so the stale case is refused rather than doubled.

On anyone else's open PR, the header's right end, where the viewer's own PR has its Reviewers button, has a bordered-prominent "Review" button, titled "Finish review (N)" while N comments are pending. The right end is where the viewer's own actions sit on their own PRs, so the review goes there too, and the merge section stays empty. It opens a popover with github.com's heading, "Finish your review": a markdown field for the summary, filled from the pending review's body the first time it opens, then Comment, Approve and Request changes as radio rows under github.com's descriptions of each, and "Submit review" (⌘↩). With a review pending, "Abandon review" deletes it after asking. The summary and verdict are kept while the tab lives, so closing the popover loses nothing. Approving needs nothing more; commenting or requesting changes needs a summary or pending comments, as GitHub requires a body for those without comments. Approve and Request changes are disabled with a reason on the viewer's own PR, which GitHub refuses, though the button isn't offered there. After submitting, the conversation is fetched again, so the review shows in it and in the reviewers, and the PR's status, so the review decision and merge state in the header, its tab and the lists follow. A refusal shows in the popover with the draft kept, as the reviewers popover shows its refusals.

### Loupe marks the GitHub links it sends to the browser with `via=loupe`

A second comment into a review that's still being started waits for that review rather than starting another, which GitHub would refuse. The stored copy keeps the sending flag, so a comment still on its way when Loupe quits shows as sending on the next launch until the conversation is fetched, which settles whether GitHub has it. Only the description's editor still waits for GitHub: its rendering is GitHub's markdown, and its save lives in the editor, not the conversation.

### The header says when GitHub is being checked for the PR's changes

A mini spinner sits after the header's "updated …" while GitHub is being asked for anything that will update this PR's row or conversation: a refresh of the lists while the PR is in one of them (the searches, the review-request check and the status lookups), a lookup of it by id (the check when its tab is shown or returned to, a notification naming it, the timer fallback, and the lookups after merging or marking it ready), and a fetch of its conversation. The tab exposes it as one flag, `isCheckingGitHub`, from the conversation fetch and the lists' per-PR count of lookups by id underway, so overlapping checks don't clear it early. It doesn't spin for git work, which has the commit picker's spinner, for the viewer's own writes, which have their sending states, or for the reviewer picker's candidates and suggestions, which only fill that picker. The selection settling before a shown PR is checked isn't a fetch, so it doesn't spin either. It's `DelayedSpinner`, as on the commit picker, so a check GitHub answers quickly shows nothing and the caption doesn't flicker; it takes no width while hidden, and it's the caption's last item, so nothing moves when it appears.
