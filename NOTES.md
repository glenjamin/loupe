# Loupe spike: findings

A spike for a native macOS PR-review app. It checks the GitHub GraphQL data shapes we'd need (`probe/`) and prototypes the diff view, the riskiest part (`Sources/`).

## Build and run

Needs Swift 6 (Command Line Tools are enough; no Xcode). All commands run from the project root.

```sh
swift build                 # debug build
swift test                  # diff tests, plus PR list tests against a fake GitHub and SQLite (swift-testing)
swift build -c release      # for meaningful bench numbers
```

Open the start screen: your open PRs (drafts included) beside the open PRs awaiting your review, newest first. It authenticates with `gh auth token`, so `gh` must be signed in. The `gh` run is Homebrew's when installed (`/opt/homebrew/bin/gh`, then `/usr/local/bin/gh`), else `/usr/bin/gh`, else whichever `PATH` finds; `LOUPE_GH=<path>` overrides the choice, as `LOUPE_GIT` does for git. Clicking a PR (or selecting it with the arrow keys and pressing Return) opens it in a tab:

```sh
swift run Loupe
```

The PRs are kept in SQLite at `~/Library/Application Support/Loupe/loupe.sqlite`, so launch shows the last-known lists straight away, then refreshes in the background: on launch, every few minutes, on ⌘R, and when the app comes to the front with lists more than a few minutes old. A list's first load pages through its search for open PRs in full and makes the stored list match it. Every refresh after that asks only for PRs in the list updated since its last refresh (`updated:>=`, two minutes earlier to allow for lag, any state), and adds or updates those without dropping anything; the refresh time recorded is when the request started. Merged and closed PRs therefore stay stored with their state, and the list shows only open ones unless the toolbar's "Show closed and merged" toggle is on (remembered between runs), when they appear muted with a badge. To review is two searches, `review-requested:@me` and `is:open reviewed-by:@me -author:@me`, merged by id; the second always asks for open PRs only. A PR you've reviewed never reappears in the first to say so, and one merged since never reappears in the second, so each refresh also checks every to-review PR directly (`nodes(ids:)`) and drops those that are no longer open, or neither request your review nor hold your approval or request for changes (`latestOpinionatedReviews`); a request to any team keeps a PR there, as team membership isn't checked. What it fetches stays stored, but the list leaves out what's over a month old (`PullRequestListModel.isStale`): a PR whose request for your review is that old, or one you approved or asked changes of that's had no activity (its `updatedAt`) for that long. The caption at the foot of the column counts them ("17 older than a month hidden") and lists them last, newest first, for the session when clicked. The same check asks for your latest review of any kind (`viewerLatestReview`), the PR's last 30 commits and its last 5 force-pushes, and stores what they say (`PullRequestSummary.viewerReviewMark(viewer:)`): a row you've reviewed carries a chip, "You approved", "You requested changes" or, for a review that only commented, "You commented", with "· updated" in orange once commits have been pushed since your latest review (its head isn't the commit you reviewed, force-pushes included) or you've been asked by name to review it again since. Its tooltip says when you reviewed and what's happened since: how many commits and when the newest was committed, when it was force-pushed, when you were asked again. A row awaiting your first review has no chip. Your login for that check is looked up once and stored. If it fails, the stored lists stay up with a banner saying how old they are. To start afresh, quit the app and delete the database (and its `-wal`/`-shm` files):

```sh
rm ~/Library/Application\ Support/Loupe/loupe.sqlite*
```

After each refresh the app looks for each listed repo's local checkout, for diffing PRs locally later. A repo it has no checkout stored for is looked for as a directory with the repo's name (not `<repo>-<branch>` worktree copies) under each of the checkout folders in turn, and accepted only if its `origin` is that repo on github.com. Finds are stored in the `localRepo` table; misses aren't, so they're looked for again next refresh. A stored checkout whose directory has gone is dropped and looked for afresh. Each row shows a folder icon when the checkout is known; right-click to reveal it in Finder, or to locate it by hand when it wasn't found. The checkout folders are kept in `~/.config/loupe/config.json` (under `$XDG_CONFIG_HOME` when set) as `{"checkoutFolders": ["~/Development/tamarinworks", "~/Development/GitHub"]}`, editable by hand while the app isn't running; a clone goes under the folder named after the repo's owner, else the last one. Until the file has them, as on first launch, a banner above the lists and the no-checkout pane ask for them, and nothing is searched; Loupe ▸ Checkout Folders… changes them later. A snapshot run reads the file but never writes it. Git is only ever run read-only against checkouts. The git run is Homebrew's when installed (`/opt/homebrew/bin/git`, then `/usr/local/bin/git`), else `/usr/bin/git`; `PATH` isn't consulted, and `LOUPE_GIT=<path>` overrides the choice. The path and its `git --version` are logged once, at first use: `log stream --predicate 'subsystem == "com.glenmailer.Loupe" && category == "git"'`. To fix a wrong mapping, quit the app and delete its row:

```sh
sqlite3 ~/Library/Application\ Support/Loupe/loupe.sqlite "DELETE FROM localRepo WHERE nameWithOwner = '<owner>/<repo>'"
```

The app has one window. Under its title bar a strip starts with a "Pull Requests" button, always there and not a tab, which shows the lists, then a tab per opened PR in the order opened. A tab is two rows: `repo #number` in bold over the PR's title, cut short with an ellipsis; it shows a close button while hovered or selected. Tabs share the strip's width equally between a minimum and a maximum, and past the minimum the strip clips rather than scrolls. The window is titled "Pull Requests" with the lists shown, or `repo #number` with the PR's title beside it, and its toolbar holds the lists' refresh controls or the PR's "Open on GitHub" and "Copy Link" (⇧⌘C), which puts the PR's github.com link on the pasteboard. Each PR's view is made when its tab is first shown and kept, hidden, while another is, so it keeps its diff, scroll positions and conversation. Opening a PR that already has a tab shows it. Keys: ⌘1 shows the lists; ⌘W closes the shown PR's tab (nothing on the lists) and ⌥⌘W all of them, closing the shown tab shows the one after it, or before it if it was last; ⌘⇧[ / ⌘⇧] and ⌃⇧Tab / ⌃Tab step through the strip with the lists first, wrapping; ⌘2–⌘8 pick the 1st–7th PR tab and ⌘9 the strip's last item. `?` lists every shortcut in a sheet; they're all defined in `Shortcut` (`Sources/Loupe/Shortcuts.swift`), which the menus bind theirs from and the review keys' monitor matches the plain ones against, so the list can't miss one. The window has no close button. Open PRs and the shown one are stored (`openTab` table, `selectedTab` setting) and reopened next launch; a PR with an open tab stays stored even after it leaves both lists.

A PR's tab shows the PR's header (state, CI, review decision, `head → base`, where clicking the head branch copies its name, "Open on GitHub") over its changed files and diff, produced from the repo's local checkout, showing each step: finding the checkout, fetching, diffing. With no checkout known it says so and offers "Locate Checkout…". In the checkout it runs, all without touching branches, the index or the working tree:

```sh
git fetch --no-tags --no-write-fetch-head origin +refs/pull/<N>/head:refs/loupe/pull/<N>/head
git cat-file -e <baseRefOid>^{commit} || git fetch --no-tags --no-write-fetch-head origin <baseRefName>
git merge-base <baseRefOid> <head>
git log --reverse -z --format=%H%x1f%P%x1f%s <merge-base>..<head>   # the PR's commits, oldest first
git diff --name-status -z -M <merge-base> <head>                   # every changed path and what happened to it
git cat-file --batch-check   # <head>:<dir>/.gitattributes per line, for each changed path's directories
GIT_INDEX_FILE=<temp> git update-index -z --index-info   # those found, into an index of their own
GIT_INDEX_FILE=<temp> git check-attr --cached -z --stdin linguist-generated linguist-vendored linguist-documentation   # the paths on stdin
git cat-file --batch   # <head>:<path> per line (<base>:<path> if deleted), for paths only content can decide
git diff -M <merge-base> <head> -- . ':(exclude,top,literal)<hidden path or directory>' ...
git diff -M <merge-base> <head> -- ':(top,literal)<hidden path>'   # a hidden file, once it's shown
```

A single commit's changes are diffed the same way, from its first parent (or the empty tree, for a root commit) to the commit.

Hunk headers have GitHub's expand arrows in their gutter: ↑ reveals 20 more lines above a hunk, ↓ 20 more below the one before, ↕ the whole gap when it's 20 lines or fewer, and a row after the last hunk has ↓ for the file's end. The lines come from the file at the head of the changes shown (the PR's head, or the picked commit), read once with `git show --no-textconv <oid>:<path>` when the file is shown and kept while the tab lives. Added, deleted and binary files have no arrows. What's revealed is kept per file and range, so it survives switching files and commits, and Reload drops it.

Fetches time out after two minutes and other git commands after one; a failure shows git's stderr with a "Try Again" button. Which paths are hidden is `PathFilter`'s decision: a path under the repository's root `vendor/` (or matching Linguist's `documentation.yml`, off by default), a lockfile (`go.sum`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`), a file whose first lines Linguist's `generated.rb` takes for generated (`GeneratedCode`, such as Go's `// Code generated … DO NOT EDIT.` header on a `.pb.go`; read from git at the head, or the base for a deleted file, only for names a rule applies to), or a path the `.gitattributes` files at the head of the changes shown (not the checkout's working tree) mark `linguist-generated` or `linguist-vendored`; either attribute set to false keeps a path that would otherwise be hidden. The hidden paths are excluded from the diff by literal pathspec, collapsed to the highest directory with nothing kept in it, so a vendored tree is one argument. The sidebar still lists them, below the files to review under "Vendored, lockfiles and generated", each with what happened to it (from `--name-status`); one is diffed on its own only when it's selected, and kept in memory, its row then showing its line counts. They can be marked reviewed like any file, but the "N of M reviewed" count, ⌘↓ and `]`, and "All files reviewed" go by the files to review alone. The diff is kept in memory per PR, so switching tabs doesn't redo it. When each PR's diff was last produced, from which head and merge-base, is stored in `pullRequestDiff` (the diff text isn't). Review threads show in the whole PR's diff ("All N commits"), not in a commit's. Each thread sits under the line it ends on (`line` on `diffSide`: the head for RIGHT, the base for LEFT, so a comment on a deleted line sits under it), with its line range in its header; threads on one line share a block. Outdated threads, those on the whole file, and those on a line the diff doesn't show come after the last row under "Not on the current diff", each with the end of the diff it was made on; revealing a hidden line brings its thread into place. Resolved threads are one line ("Resolved · N comments · login") until clicked, and hidden comments a line saying so. Bodies are GitHub's `bodyHTML` read by `CommentBlock` (in `LoupeCore`) into paragraphs, code, quotes, list items and rules, shown as SwiftUI `Text`; images become links. Each block is an `NSHostingView` laid over an empty row of the text view (`DiffBlock` in `DiffRenderer`), whose height follows the view's own; that row is tagged as gutter, so copies leave it out. The file list shows each file's unresolved threads beside its name, hidden files' included. Threads come with the conversation, on opening and Reload.

A thread's "Reply…" opens a plain-text field (⌘↩ sends, Esc cancels, asking first if anything is typed); the reply posts at once with `POST /repos/{owner}/{repo}/pulls/{number}/comments/{comment_id}/replies`, naming the thread's first comment by `databaseId`. "Resolve conversation" and "Unresolve conversation" in a thread's header call `resolveReviewThread` and `unresolveReviewThread`, showing the change at once and putting it back if GitHub refuses. After either, the threads alone are fetched again (`GitHubClient.reviewThreads(ofPullRequest:)`) and stored. Refusals show under the thread. None of these was run against the real API; the tests drive them through the fake.

With text selected in a comment, `r` quotes it into a reply, as on github.com: the selection is written back as markdown (code, links, emphasis, lists and code blocks kept), every line marked `> `, and put after anything already written in the composer, which takes the focus with the cursor after the quote, back on Write if it was previewing. A comment on the diff, or in a thread's popover over the conversation, is quoted into its thread's reply; one in a thread on the conversation page into that thread's reply in its popover, unless the thread takes no reply (as one in the viewer's pending review), when it goes to the PR's "Add a comment…" like any other comment on the page. A thread on the diff that takes no reply takes no quote. `r` types as usual wherever text can be typed; with no selection, or one beyond a single comment, it does nothing.

Hovering a row of the PR's own diff (not a hunk header or a revealed line, and only on "All N commits") shows a "+" in its gutter; clicking it opens a field under the row that posts a new single-line thread at once with `POST /repos/{owner}/{repo}/pulls/{number}/comments` (`commit_id` is the diff's head, `path`, `line`, `side`), then fetches the threads again. One new comment is open at a time.

A PR is one pane: a sidebar with a "Conversation" row at the top, then the commit picker and file list, beside either the conversation or the selected file's diff. Clicking the Conversation row (or ⌃1, in the View menu) shows the conversation and leaves no file selected in the list; clicking a file (or ⌃2) shows the files again, and the file selected before comes back. A PR opens on its conversation and each tab remembers its choice while open. Above the file list a popup picks "All N commits" (the PR from its merge-base, the default) or one of the PR's commits, oldest first, listed by `git log` from the checkout. A commit's changes are diffed the first time it's picked and kept in memory, so switching back is instant; the shown file stays if the commit changed it. Reload goes back to "All N commits". "All N commits" in the picker's list counts the whole PR's files to review. After it, "Since your last review" diffs from the head the viewer's latest submitted review was made against (the conversation's `viewerLatestReview { commit { oid } }`) to the PR's head, and "Since you last opened it" from the head the PR's tab last showed before this tab was made (the `seenHead` table, recorded each time the diff is produced and read once as the tab is made), each shown only when known and behind the head. When the commits are first shown, each such head the checkout lacks is fetched from the remote by oid (`git fetch --no-tags --no-write-fetch-head <remote> <oid>`, making no ref), checked with `git merge-base --is-ancestor`, and counted. A head the PR was rebased from has its changes replayed onto the head's new base, and the entry diffs that replay to the head, so it shows only what the author changed since, not what the base gained; a file whose old changes don't replay cleanly shows its whole change since, base's included, flagged "Couldn't separate from rebase" in its header and "rebase" in the file list, each explained when hovered. A push that only rebased is listed dimmed as "Only rebased since, no changes", and a head that couldn't be fetched dimmed too; neither can be picked, and a popover says why when the pointer rests on it. The replay, run in the checkout without touching branches, the index or the working tree, writes its objects to Loupe's own object directory, `~/Library/Caches/Loupe/replayed-objects`, never the checkout's; local git runs that diff it read that directory as an alternate (`GIT_ALTERNATE_OBJECT_DIRECTORIES`), fetches never do:

When the conversation has CI's diff-book comment (an issue comment whose markdown starts `<!-- diff-book-review -->`, edited in place on each CI run), the header shows a quiet "Visual changes N" flag, nothing when it says none differ, whose popover lists each story and how it changed and how many stories were rendered; clicking it, the sidebar's "Visual review" row under Conversation, or ⌃3 shows CI's interactive report beside the sidebar. The most recently updated such comment counts. Its markdown is why issue comments' `body` and `updatedAt` are fetched and stored. The report is a CircleCI artifact of a private project, which CircleCI serves only to a signed-in session. Sign the `circleci` CLI in with `circleci auth login`. When a report not kept from before is opened, Loupe runs `Scripts/circleci-token` (bundled into the app's resources; `LOUPE_CIRCLECI_TOKEN_COMMAND=<path>` overrides it), a stop-gap until the CLI can print its own token, which prints the token the CLI keeps in the login keychain (service `com.circleci.cli:<host>`, account the OS user; see DESIGN.md for the layout and its source). The token is kept in memory only, and the script is run again once when CircleCI turns it down. With it, the report and each file it loads are fetched from CircleCI as the page asks for them, with `Circle-Token` sent only to CircleCI's hosts (polecat #14589's report: 9 files, 0.9 MB, about half a second). Without one, the CLI downloads the whole job with its own sign-in (`circleci artifact <job> --output <dir>`; polecat's diff-book job: about 570 files, 59 MB, two and a half minutes), showing files written of the count the CLI announces, with Cancel. The CLI is Homebrew's (`/opt/homebrew/bin/circleci`, then `/usr/local/bin/circleci`), else whichever `PATH` finds; `LOUPE_CIRCLECI=<path>` overrides the choice. Either way files are kept in `~/Library/Caches/Loupe/artifacts/<job id>` (`LOUPE_ARTIFACT_CACHE` overrides it), so later opens are instant, and a job unopened for 30 days is deleted when a job is next fetched or downloaded. They're served from there under the `loupe-artifact:` scheme. Without the CLI, the pane says to `brew install circleci`; signed out or refused, it shows why and `circleci auth login`; any other failure shows what CircleCI or the CLI said; each with Try Again, Open in Browser and Open Artifacts Tab.

When the PR's checks include failed jobs CircleCI ran, the sidebar has a "CircleCI" row under Conversation, counting them; it or ⌃4 shows a tab for each failed job and, for the one shown, its failed steps' output (coloured as the terminal showed it, from its end; a step that failed on several parallel runs is listed once per run), its failed tests with their messages, and its artifacts as a tree, each opening in the browser. They're read with the CLI's token, as above, from the v3 API the `circleci` CLI 1.7 uses (`/api/v3/jobs/<id>`, `…/stdout` and `…/stderr` by `filter[execution]` and `filter[step_num]`, `…/tests` as JSONL, `…/artifacts`, which answers 404 for a job that kept none), sent as `Authorization: Bearer`. A check's link gives the job's id (`app.circleci.com/workflow/<id>/job/<id>`), else its workflow (`/workflow/<id>`, or `/pipelines/…/workflows/<id>[/jobs/<n>]`), whose jobs (`/api/v3/jobs?filter[workflow_id]=`) are matched by number, then by the check's name, else all its failed ones are taken; an older project's `circleci.com/gh/<org>/<repo>/<n>` is found through v2's `/api/v2/project/<slug>/job/<n>`, whose `latest_workflow` leads to the workflow. What's read of an ended job is kept in memory until the app quits. Signed out or refused, the pane says to `circleci auth login`. Playwright's stored test messages are only its attachments' paths; its error is in the step's output.

```sh
git merge-base <base> <old head>; git merge-base <base> <head>       # old and new merge-bases
git rev-parse --path-format=absolute --git-path objects             # the checkout's object directory
GIT_OBJECT_DIRECTORY=<loupe's> GIT_ALTERNATE_OBJECT_DIRECTORIES=<checkout's> \
  git merge-tree --write-tree -z --name-only --no-messages --merge-base=<old merge-base> <new merge-base> <old head>
# exit 1 lists the conflicted paths; those take the old head's version, through an index outside the checkout:
GIT_INDEX_FILE=<temp> (same objects) git read-tree <replayed tree>
GIT_INDEX_FILE=<temp> GIT_LITERAL_PATHSPECS=1 git ls-tree -r -z --full-tree <old head> -- <paths>
GIT_INDEX_FILE=<temp> git update-index -z --index-info               # those entries, or removals
GIT_INDEX_FILE=<temp> git write-tree
git rev-parse --verify <head>^{tree}                                 # the same tree: only rebased
git diff -M <replayed tree> <head>                                   # and so on, as for any range
```

`--merge-base` needs git 2.40 or later; with an older git the entry says it couldn't be shown, with git's message. In the conversation each force-push with both heads known has "Show changes", a `loupe-changes://force-push/<before>/<after>` link the web view catches, which shows the files with that push's changes picked, from the head it replaced to the one it pushed (not the PR's head, if it has moved on), worked out as above with either head fetched if missing; the push then stays in the picker as "Force-push <before> → <after>" while the tab is open. If it only rebased, the picker opens on it to say so. The conversation is fetched by GraphQL when the PR's tab opens and on Reload (`GitHubClient.conversation(ofPullRequest:)`: the description's `bodyHTML`, the timeline paged by 100, review threads with their comments, and the head commit's CI contexts) and stored in the `conversation`, `timelineItem`, `reviewComment`, `reviewThread`, `threadComment` and `checkContext` tables, so a later opening shows it at once. It's shown in one `WKWebView` per tab, made the first time the conversation is shown and kept while the files are shown, so its scroll position survives switching. The page is assembled by `ConversationHTML` (in `LoupeCore`) from the template `Sources/Loupe/Resources/conversation.html` and its stylesheet `conversation.css`: GitHub's `bodyHTML` goes in verbatim, everything else is escaped, a Content-Security-Policy allows no scripts and only GitHub's images, and links open in the default browser.

On the viewer's own PRs (their login against the PR's author), the Conversation tab has an "Edit description" button at the right of the Conversation / Files changed row. It fetches the description's markdown afresh (`node(id:) { ... on PullRequest { body } }`, `GitHubClient.pullRequestBody(id:)`), never the stored `body`, and shows it in a monospaced plain-text editor in place of the web view, with Cancel (Esc, asking first if anything changed) and Save (⌘↩, disabled until the text changes). If the fetch fails it says so with Retry. Save sends `updatePullRequest(input: { pullRequestId, body })` (`updatePullRequestBody`), then fetches the conversation again so the page shows GitHub's rendering, and closes the editor; a refusal keeps the draft with the error under it. The editor's state is `DescriptionEditor`, held by the tab.

While a PR's tab is open the app watches it for changes on GitHub, as github.com does, and never replaces the diff being read. It polls `GET /notifications?participating=true` with the `If-Modified-Since` of the last poll, waiting between polls as long as `X-Poll-Interval` says (60 seconds when it doesn't); a 304 means nothing changed and costs no rate limit, and nothing is marked as read. When a poll returns notifications, the open PRs they name (by `subject.url`) are looked up in one `nodes(ids:)` query and their stored rows updated. If notifications are refused (403 or 404, as for a token that can't read them) every open PR is looked up that way each minute instead, for the rest of the run; any other failure does the same for that round and polls again next time. When an open PR's stored row has changed since its diff was produced, by this or by the lists' refresh, a banner at the top of its tab says "New commits pushed" (its head moved) or "Updated on GitHub" (its update time, state, review decision, or commit, comment or review thread count changed), with Reload, which looks the PR up again and produces the diff anew, keeping the shown file, and a dismiss button, which keeps the diff until the PR next changes. The lists show the updated rows as usual. A snapshot run doesn't poll.

Or open a diff file directly. Make a diff to view from PR `<N>` in a local checkout of `<owner>/<repo>`, with vendored code left in (the app hides it itself):

```sh
git -C <checkout> fetch origin refs/pull/<N>/head
git -C <checkout> diff \
  $(git -C <checkout> merge-base <head> <base>) \

```

(`fixtures-local/` is gitignored. `<head>` and `<base>` are the PR's `headRefOid` and `baseRefOid` from the API.)

`swift run` gets a Dock icon but ⌘-Tab shows a generic one, as it reads the icon from an app bundle. To build a release `.app` (ad-hoc signed, under `.build/`) and open it:

```sh
./start.sh                 # debug build of Loupe.app, then opens it
./start.sh release         # same with an optimised build
./start.sh install         # release build copied to ~/Applications/Loupe.app
sh Scripts/bundle.sh && open .build/Loupe.app   # the two steps separately
```

`start.sh` first quits the Loupe running from this checkout's `.build/Loupe.app`, found by its executable's path and asked to quit by pid, and waits until it has exited and Launch Services no longer lists it before opening the new build; an `open` sent while the old one is still exiting is handed to it and fails with `_LSOpenURLsWithCompletionHandler() failed with error -600`. If it hasn't quit within 10 seconds (it may be asking something), the script says so and stops without opening. Snapshot runs and other checkouts' bundles are left alone.

`Scripts/bundle.sh` builds `Loupe.app` with its own SwiftPM scratch path, `.build/app`, so `start.sh` never waits on the lock a `swift build` or `swift test` holds on `.build` (a long test run, say). It has its own build products, so its first build in a checkout is a full one. Snapshot bundles still build in `.build`, sharing products with `swift test`. The bundle stays at `.build/Loupe.app`.

### Opening PR links from other apps

The bundle declares the `loupe` URL scheme, and `https` as an alternate handler only, so Loupe can be picked for a link without becoming the default browser (see "Links from other apps open in Loupe" in `DESIGN.md`). Launch Services learns the URL types when the bundle is registered, which opening it does, so `./start.sh` after a rebuild is enough. To force it without opening the app:

```sh
/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister -f .build/Loupe.app
```

To try it, with the bundle built and registered (each launches Loupe if it isn't running):

```sh
open 'loupe://github.com/tamarinworks/porter/pull/1522'
open 'loupe:///tamarinworks/porter/pull/1522'
open -a Loupe https://github.com/tamarinworks/porter/pull/1522
open 'loupe:///tamarinworks/porter/pull/1522#issuecomment-6139849638'
```

A link to part of a PR lands there (see "Links to a comment, thread, file or commit land on it" in `DESIGN.md`). GitHub's anchors, checked 2026-10-20 against `url` fields from GraphQL and a public PR's files page: `#issuecomment-<id>` (a comment on the PR), `#pullrequestreview-<id>` (a review), `#discussion_r<id>` (a review thread's comment, `#r<id>` on the files), `#diff-<hex>` on the files (the SHA-256 of the file's path, then an optional line such as `R12`), and the pages `/files`, `/files/<oid>`, `/files/<oid>..<oid>` and `/commits/<oid>`; `/changes` is taken as `/files` too, for GitHub's newer files view, though no such link was seen, as the page fetched was the logged-out, classic one. The ids are REST database ids: GraphQL's `databaseId`, which answered ids past 2³¹ (5829229341) as plain numbers.

A router such as Finicky can send Slack's and mail's PR links here, either by rewriting `https://github.com/*/pull/*` to the same URL with the scheme `loupe`, or by opening those URLs with the app `com.glenmailer.Loupe`. The PR opens in its tab at once: a stored PR as it's stored, any other as a tab made from the link alone, `repo #number` with a spinner, while it's looked up on GitHub, which becomes the PR's tab in place once found. A PR GitHub won't show, or a failed lookup, leaves that tab saying why, with Retry, Open on GitHub and Close. Any other https link Loupe is given goes to the browser. A `loupe:` URL that names no PR is logged and dropped. Links Loupe sends to the browser carry `via=loupe` when they're on github.com, so the router's PR rule should skip URLs with that parameter, or it sends Loupe's own "Open on GitHub" straight back.

Snapshot runs use their own bundle, `.build/LoupeSnapshot.app`, named "Loupe Snapshot" with the id `com.glenmailer.Loupe.snapshot` and no URL types, so Launch Services, AppleScript, `open -a Loupe` and links never pick a snapshot run (or a worktree's snapshot bundle) for the real app, and building one never replaces a running `Loupe.app`. Its defaults are its own, with the real app's read beneath them, so it shows the same View settings and never writes the real app's.

The run is an accessory process that's never activated, and its window is transparent and off every screen, so nothing shows while it runs. Popovers and any other window it opens are made transparent as they appear, as AppKit moves popovers onto a screen.

Every snapshot run only reads. Each GitHub request goes through `ReadOnlyTransport`, which sends GraphQL queries, REST `GET`/`HEAD` and `POST /markdown` and refuses everything else (mutations, merges, review requests, comments, reactions) before it leaves the process, printing `blocked in snapshot run: <mutation or METHOD path>`; the UI then shows the refusal as it would GitHub's. git is kept to reads by `ReadOnlyGit`: fetches into `refs/loupe/` and Loupe's own objects and indexes still work, but cloning, switching branches and the like are refused the same way. Links for the browser and checkouts for an editor are printed instead of opened.

The UI suite is every `Scripts/ui-tests/*.loupe`, run against the fixtures. Run it after UI changes, alongside `swift test`, with the sandbox off:

```sh
Scripts/ui-tests.sh               # every script
Scripts/ui-tests.sh reviewer      # only those whose file name contains "reviewer"
LOUPE_UI_JOBS=1 Scripts/ui-tests.sh   # one at a time (4 at once by default)
```

It builds the snapshot bundle (`Scripts/bundle.sh` keeps the bundle as it was when nothing changed) and the fixture checkouts (kept in `.build/ui-tests/.checkouts` until `FixtureCheckouts.swift` or `FakeRepository.swift` changes), then runs each script in a snapshot run of its own: a copy of the bundle with a bundle id of its own (`com.glenmailer.Loupe.uitest.<script>`, so its settings start empty and are deleted afterwards), its own empty database and its own APFS clone of the checkouts. The copies are kept in `.build/ui-tests/.apps` with the executable hard-linked, and made again only when the bundle changes: macOS checks each new executable on its first launch, which took most of a second per copy, one copy at a time. It prints `pass` or `FAIL` with the time for each script, then for each failure its last passing steps, the failing step's output and the path of its `failure.png`, and exits 1 if any failed. Each script's PNGs and full output are kept in `.build/ui-tests/<script>/`.

`LOUPE_FIXTURES=<dir>` is what makes a run hermetic (`FixtureRun`): GitHub is `FixtureGitHub` from the `LoupeFakeGitHub` target, the tests' fakes serving the anonymised captures under `probe/` in-process (the viewer is `glenjamin`, the org `tamarinworks`), with no network and no `gh auth token`; any request none of the fakes can answer prints `fake GitHub: …` and fails the script at its end, even if every step passed. The database is `<dir>/loupe.sqlite`, empty until the first refresh, unless `LOUPE_DATABASE` says otherwise. Checkouts are looked for only in `<dir>/checkouts`, unless `<dir>/config.json` says otherwise, which `Loupe --fixture-checkouts <dir>/checkouts` fills: atrium #2928 (to review, with the conversation's threads on its files and three commits) and the viewer's gazette #272 and #273 (stacked on it) have real git repos there, made with `FakeRepository` as the tests' are, with fixed commit dates so their oids are the same each build; the fake serves those PRs with their commits. Other PRs say there's no checkout. The lists judge age by noon on 14 October 2026, when the captures were made, so the quiet and stale sections stay put; relative times shown ("last week") still follow the real clock. The real app's settings aren't read, the window is always 1440×900, web pages load nothing over the network (avatars stay blank), CircleCI is `FakeCircleCI`, serving marmot #14268's failed playwright and typecheck jobs, and CircleCI's CLI is never run. The write guards are on as in any snapshot run, so `expect-request` works the same.

To add a script, put a `.loupe` file in `Scripts/ui-tests/`; a `<script>.config.json` beside it becomes the run's config file, as `checkout-folders.config.json` starts a run with no checkout folders chosen, and choosing them in a fixture run picks its checkouts rather than showing a panel. Open PRs by name (`open tamarinworks/gazette#272`) rather than by list position, and name only the fixtures' people, never real ones. Every PR in `probe/pr-list.json` is listed; to give one a checkout, add its repo and branch to `FixtureCheckouts`; for data no capture has, add to the fake or its fixture JSON, anonymised as `probe/NOTES.md` describes. Wait on conditions (`wait until`, `wait settled`), not with `wait <duration>`. Run the suite a few times to see a new script pass every time.

Ad hoc, against real data, write the script anywhere (the scratchpad is fine), then run it against a copy of the database; it reads from GitHub and the user's checkouts, so what it sees changes as they do:

Either way a run starts once the lists have refreshed, prints `ok <line>: <step> — <what it found>` for each step and `passed N steps`, and exits 0. At the first failure it prints `FAIL <line>`, what was expected and found, and the part of the accessibility tree it looked in, writes `failure.png`, and exits 1 (2 if the script doesn't parse). The suite's scripts are working examples: the reviewer picker's keys (`reviewer-picker.loupe`), the Conversation row's hover (`conversation-hover.loupe`), ⌘F on the lists (`list-search.loupe`), the tab strip (`tab-strip.loupe`) and the file header's Hide whitespace toggle, hovered, clicked and by ⌃⌘H (`whitespace-toggle.loupe`).

One step a line; `#` starts a comment (`#name` mid-line is an identifier). Things are found in the accessibility tree, as VoiceOver sees it, across the window and any popover. Start with `dump` to find handles.

Finding things, wherever a step takes `<query>`: `[role] ["text" | ~"text"] [#identifier] [selected] [N | last]`, then optionally `in <query part>` for something it must be inside, repeatable (`#reviewer-choice 2 in #reviewer-picker`). `"text"` matches a label, title, value, placeholder or identifier whole; `~"text"` matches part of one, ignoring case. `N` picks the Nth match from 1, in reading order; with no `N` the first is acted on. `selected` keeps only selected matches. Roles: `button`, `row`, `cell`, `text`, `field`, `search`, `textarea`, `checkbox`, `radio`, `list` (lists, outlines and tables), `group`, `image`, `link`, `menuitem`, `popup`, `menubutton`, `scroll`, `toolbar`, `popover`, `web`, `disclosure`, `tabs`, `segments`, `window`, `any`, or a raw `AXRole`/`AXSubrole`. Add `.accessibilityIdentifier("…")` (with `.accessibilityElement(children: .contain)` on a container) where there's no stable label.

Conditions, wherever a step takes `<condition>`: `exists` (the default), `missing`, `is [not] selected|focused|enabled|disabled`, `has [no] value|title|label "text"|~"text"`, `count N|>N|<N` (over every match).

| Step | Does |
| --- | --- |
| `open lists` / `open mine <n>` / `open to-review <n>` / `open owner/repo#<n>` | Shows the lists, the nth PR of a list, or a PR as a link from another app would (looked up on GitHub if not stored) |
| `wait settled [timeout 30s]` | Until the lists have refreshed and the shown PR has its diff, not still being replaced, and its conversation, or they failed |
| `wait <duration>` | A pause: `500ms`, `2s` |
| `wait until <query> [<condition>] [timeout 10s]` | Polls until it holds |
| `click` / `double-click` `<query>` | At the element's centre, after moving the pointer there |
| `right-click <query>` | Asks for the context menu without showing it and prints its items; `choose "Item"` then picks one |
| `hover <query>` / `unhover` | Moves the pointer onto the element / off the window; a hover popover, such as the checks' or conflicts', opens after its dwell, so `wait until` it |
| `press <key> [<key>…] [until <query> <condition>]` | Keys in turn, as `down`, `return`, `esc`, `tab`, `space`, `delete`, `up`/`left`/`right`, `home`, `end`, `pageup`, `pagedown`, `f1`…, or a character, with `cmd+`, `shift+`, `opt+`, `ctrl+`, `fn+` (`cmd+shift+p`, `ctrl+tab`); `until` repeats them (up to 30 times) until the condition holds |
| `type "text"` | Types each character into whatever has the focus |
| `scroll <query> up\|down <points>` | Scrolls whatever scrolls under the element |
| `drag <query> left\|right <points>` | Presses at the element's middle, moves that far in steps and lets go, each event sent through the window; for AppKit views that track drags themselves, as SwiftUI's `DragGesture` ignores synthesised events |
| `expect <query> [<condition>]` | Fails the run unless it holds |
| `expect-request <name>` / `expect-no-request <name>` | Whether a blocked write was attempted, by a substring of its name: a mutation (`requestReviews`, `mergePullRequest`), a REST write (`DELETE /repos/…/requested_reviewers`, `merge-async`), `git switch …`, or `open … in the browser` |
| `expect-copied "text"` | Fails the run unless the app last copied that text; a run copies to a pasteboard of its own, never the user's |
| `snap <name> [<query>]` | Writes `<name>.png` of the window, or cropped to the element |
| `expect-different <a> <b>` / `expect-same <a> <b>` | Compares two snaps' pixels, as for a hover tint |
| `dump [<query>]` / `dump windows` | Prints the accessibility tree (or the matches' subtrees) with frames / each window's frame, alpha and first responder |

How input gets there, should something not respond: keys and clicks are `NSEvent`s queued with `NSApp.postEvent`, so local key monitors, menu key equivalents, the first responder and SwiftUI's `onKeyPress` see them as real ones; keys go to an open popover or sheet, else the window. Sheets, alerts included, are searched and drawn into snaps as popovers are, but an alert never takes posted keys, as an inactive app's alert never becomes key, so a script clicks its buttons; wait until `AXSheet missing` before opening another, as one still closing stops the next. Nothing goes through the window server, so the user's real mouse and keyboard are untouched. Before each key the menus are brought up to date, as AppKit does for an active app, so a menu item enabled since launch, such as View ▸ Hide Whitespace once a PR is shown, takes its key equivalent. The app is never activated, which would take the user's keyboard, so in a script run the window reports itself key, and a click on a view that doesn't take a non-key window's first click (a list's rows) is sent to that view directly, as AppKit would once the window was key. Hover sends each tracking area's owner the enter, move and exit AppKit would send for the window server's mouse positions, which an off-screen window never gets; SwiftUI's `onHover` fires from these. Tooltips aren't shown, and a shown context menu would track the real mouse, so right-click only asks for the menu. After each input the run waits until the main thread has handled it and what it set off there (the main run loop about to sleep with nothing left to do, twice, or a quarter of a second at most), then lays the window out and draws it; work off the main thread, such as a fetch or git, needs `wait until`. Waits poll every 25ms. SwiftUI builds its accessibility tree only once an assistive app asks, so a script run asks at launch, as VoiceOver would.

Some hooks have script ports, covering one PR rather than every tab: `LOUPE_SNAPSHOT_CLICK_CONVERSATION` (`conversation-hover.loupe`), `LOUPE_SNAPSHOT_CLICK_TAB` (`tab-strip.loupe`), `LOUPE_SNAPSHOT_SEARCH`'s list part (`list-search.loupe`) and `LOUPE_SNAPSHOT_REVIEWERS`' opening of the picker (`reviewer-picker.loupe`). The hooks stay for what they print.

## What the probe showed

Details are in `probe/NOTES.md`. In short:

- A review thread's `line` + `diffSide` is a **file line number** on the head (RIGHT) or base (LEFT) side, not a diff position. That's the same `(path, side, line)` the diff view reports on click, so comment anchoring lines up. A test checks this against a real `diffHunk`.
- **Outdated threads have `line: null`**: only `originalLine` is set (10 of 21 recent marmot threads). They need the diff of the original commit, or a separate list.
- `startLine` is `null` on some single-line comments and equal to `line` on others.
- **CircleCI reports as legacy `StatusContext`s**, not `CheckRun`s (only Codecov uses check runs). The two have different field names, so CI status has to handle both.
- **`files` includes vendored code and pages at 100.** On atrium#2912, 98 of the first 100 entries were `vendor/` (741 total); the 4 real files were on later pages.
- `mergeable` is `UNKNOWN` until GitHub computes it (and always on merged PRs). `viewerViewedState` is there for syncing "viewed".
- The inbox is a single `search` query; `reviewDecision` and `isDraft` come back inline.
- Excluding `':!vendor' ':!go.sum'` from `git diff` worked: 741 files went down to 4, removing 736 vendor files and `go.sum`. For merged PRs, use `baseRefOid` for the merge-base, not `origin/master`, or the diff comes out empty. Don't rely on `FETCH_HEAD` in a shared checkout: another fetch overwrote it during the probe.

## Diff view approach

- `DiffParser` (pure Swift) turns `git diff` output into files → hunks → lines. Each line is `.context(old:new:)`, `.addition(new:)` or `.deletion(old:)`, so line numbers are never optional where they exist. It handles renames, copies (the user's git config has `diff.renames=copies`), deletions, pure renames with no hunks, "\ No newline", and CRLF (it splits on LF bytes, because Swift treats `"\r\n"` as one `Character`). `PathFilter` hides a root `vendor/` and lockfiles, and the sidebar shows how many it hid.
- `RenderedDiff` turns one file into a single `NSAttributedString`. The gutter (old/new numbers and the `+`/`-` marker) is inline text, tagged with an attribute so copying a selection yields plain code. Each row is tagged with its kind, and an array of row start offsets maps a click to a row (binary search) and from the row to its `DiffAnchor`.
- `DiffTextView` is an `NSTextView` subclass: non-editable, selectable, with a find bar. It uses TextKit 1 with **non-contiguous layout**. A small `NSLayoutManager` subclass paints full-width row backgrounds, once per visual line, so wrapped rows are tinted throughout. A single click (not a drag-select) reports the anchor.
- Long rows soft-wrap at the view's width by default. Every row's paragraph style has a `headIndent` of the gutter's measured width, so continuation lines start under the code. View ▸ Wrap Lines (⌥⌘L) turns it off; the setting is `wrapLines` in `UserDefaults` and open diffs follow it live. Clicks map by character offset, so continuation lines resolve to their row's anchor.
- View ▸ Hide Whitespace (⌃⌘H), or the `space` button in each file's header, diffs the shown PR with `git diff --ignore-all-space` (`-w`), as github.com's "Hide whitespace": every choice of changes, hidden files and revealed lines alike. It's per tab, off as a tab opens and not stored. The files listed and their counts come from the diff with whitespace, so a file only whitespace changed in stays listed, its diff saying "Whitespace-only changes"; each way's diffs are kept per range, so toggling back is instant. Line numbers are the file's either way, so threads and new comments work as usual.
- Code is syntax-highlighted with tree-sitter (`SyntaxHighlighter.swift`), chosen by the path's Linguist language; other files stay plain. For each hunk it parses the new side (context and additions) and the old side (context and deletions), runs the grammar's `highlights.scm`, and maps the captures back onto the rows: context and added rows take the new side's colours, deleted rows the old side's. Partial snippets parse with error recovery, so a hunk starting mid-expression can colour a token or two oddly, as GitHub's can. Colours are Primer's syntax palette (`DiffColors.syntax*`), light and dark. Plain identifiers and punctuation stay the text colour, as on GitHub. The colours are applied as the layout manager's temporary attributes rather than to the text storage: on the 46k-row file, adding 70k colour runs to the storage took about 720ms however it was done (each splits an existing attribute run), against 135ms as temporary attributes, which also leave layout and copying alone. Files up to 5,000 rows are highlighted before first paint; larger ones paint plain, are parsed off the main thread, then coloured top first in slices of 5,000 runs.
- Grammars come from CodeEditLanguages 0.1.20, one package bundling about 40 prebuilt grammars (as an xcframework) with their queries. A path's language is looked up in Linguist's `languages.yml` (`Linguist.swift`): exact file name first, then the longest known extension (`schema.yml.mysql` is YAML, not SQL), then the name less its last extension (`Dockerfile.prod`). Linguist's interpreter, modeline and content heuristics aren't run, so an ambiguous extension takes the first of its languages (by name) that has a grammar: `.sql` is SQL rather than PLSQL, `.h` is C. The Linguist language then picks the grammar of the same name, or one from a small table where names differ or languages share a grammar (Shell is bash, JSON with Comments is JSON, Gradle Kotlin DSL is Kotlin). Queries are composed as each grammar's tree-sitter.json does (TypeScript on JavaScript's, JSX with JavaScript and TSX) rather than by CodeEditLanguages' `TreeSitterModel`, which is a non-thread-safe singleton and leaves the JSX patterns out of TSX. (Its `queryURL` would be no use anyway: it assumes Xcode's bundle layout and doubles the `Resources` folder under SwiftPM.) Where several patterns capture one node, the last wins, as in tree-sitter's own highlighter; Go's query is still ordered for the old first-wins rule, so Go uses that.
- Languages found in the repos I review now highlighted: Go (and `go.mod`), TypeScript, TSX, JavaScript, Ruby, YAML, JSON, SQL, Bash, Dockerfile, Markdown (block structure only; inline code and emphasis need the inline grammar's injection, which isn't run), HTML, CSS and Swift, along with Python, TOML, Rust, Java, Kotlin, PHP and others the package carries. Protocol Buffers (`.proto`) comes from coder3101/tree-sitter-proto, vendored as the `TreeSitterProto` target since the package has no grammar for it; `Scripts/update-tree-sitter-proto.sh <tag>` refreshes it, and `Sources/TreeSitterProto/VERSION` says which it is. HCL (`.tf`, `.tfvars`, `.hcl`) comes from tree-sitter-grammars/tree-sitter-hcl with nvim-treesitter's highlights query, vendored the same way as `TreeSitterHCL` and refreshed by `Scripts/update-tree-sitter-hcl.sh <tag>`. Still plain, for want of a grammar in the package: Makefile.
- Linguist's data is vendored from a tagged release under `Sources/LoupeCore/Resources/linguist/`, converted to JSON, with its MIT licence and the tag in `VERSION`. To refresh it, with the sandbox off: `Scripts/update-linguist.sh v9.7.0` (any tag). Its regexes are written for Ruby; any ICU can't compile is skipped and logged under the `linguist` category (none at v9.7.0).
- `r`'s quote is written by `@github/quote-selection` 2.2.0, vendored by hand as `Sources/LoupeCore/Resources/quote-selection.js` (its `src/markdown.ts` and `src/index.ts` with the types taken out, under its MIT licence), with github.com's own rules around it in `quote-reply.js`, read from github.com's bundled JS (the `.js-comment-quote-reply` click handler and its `PRE`/`A`/`IMG`/`DIV` filters). To check for a new release: `npm view @github/quote-selection version`, then diff its repo's `src/` against the tag in the file's header. Both run in WebKit: on the conversation page against its selection, and for the diff's cards in `QuoteConverter`'s off-screen web view, against the same selection found in the comment's `bodyHTML` from `CommentBlock`'s map of where each character came from.
- CodeEditLanguages' `CodeLanguage` isn't used at all: making one reaches its SwiftPM `Bundle.module` accessor, which looks only beside `Loupe.app`'s root and in the build directory, and stops the process if both miss. The highlighter calls the grammar functions in its prebuilt framework directly and finds the queries itself, beside the executable or in the app's `Contents/Resources` (where `Scripts/bundle.sh` copies every resource bundle), as it does Linguist's data. A grammar or query it can't find is logged once and that language stays plain. Checked by running the bundled app's `--bench` with the build directory's copy moved aside (it highlights), then with both moved aside (plain, no crash).
- `DiffView` is the `NSViewRepresentable` wrapper; the `App` is a `NavigationSplitView` with the file list on the left.

Whole-file layout is slower, with the file a third taller.

So a 5k-line file opens in about 35ms, comfortably fast. A 46k-line file takes about 170ms to open, then is smooth, apart from a one-off ~0.8s if you jump straight to the end.

## What was hard

- **Painting full-width row backgrounds without losing lazy layout.** The obvious place, `NSTextView.drawBackground(in:)` plus `glyphRange(forBoundingRect:)`, silently forced layout of the whole file on first paint: 61ms at 5k rows and 500ms at 46k, against 9ms once fixed. Moving the painting into `NSLayoutManager.drawBackground(forGlyphRange:at:)`, which only sees glyphs already laid out, fixed it. A test samples pixels to check the backgrounds are painted, and fails if they aren't.
- **Swift 6 concurrency with AppKit.** `NSLayoutManager` isn't `@MainActor`, so its overrides can't touch the view's state. Filling to the graphics context's clip bounds avoided needing the view at all.
- Merged-PR merge-bases and `FETCH_HEAD` races, covered above.

## What I'd change in the plan

1. **Get the diff and file list from git, not the API.** `files` pages at 100 and is dominated by vendored code, and the API's patch text isn't in GraphQL anyway. Fetch `refs/pull/N/head`, then diff `headRefOid` against the merge-base with `baseRefOid`, in a bare cache clone the app owns rather than the user's working checkouts. Use GraphQL for metadata, threads, CI and the inbox.
2. **Inline comment rendering is now the riskiest part**, and the next spike. A single `NSTextView` has no natural way to put a block between two rows. Options: a text attachment with a view provider, TextKit 2 custom layout fragments, or a stack of per-hunk text views with comment views between them. The last is simplest, but makes selection across hunks harder.
3. **Outdated threads need their own path.** Either fetch `originalCommit` and show that diff, or list them separately.
4. **Build the attributed string off the main thread** (or collapse files over ~10k rows by default), so a huge file doesn't stall the UI for 130ms.
5. Small things for later: the find bar also matches gutter digits; a "\ No newline" marker isn't drawn yet; quoted paths (filenames with unusual characters) aren't unquoted.

- `Sources/Loupe/`: `Entry.swift` (PR list, diff file or `--bench`), `VisualReviewView.swift` (the header's "Visual changes" flag, the sidebar's Visual review row and the report's web view), `App.swift` (the menu bar and app delegate), `WindowManager.swift` (the AppKit-owned window, its title and toolbar, restoring the tabs, and the tab keys), `TabStrip.swift` (the tab strip under the title bar and the content it switches between), `PendingTabView.swift` (the pane of a link's tab while its PR is looked up), `Snapshots.swift` (window PNGs and the Debug menu), `SnapshotScript.swift` (driving a snapshot run from a script), `FixtureRun.swift` (a snapshot run against the fixtures, `LOUPE_FIXTURES`), `PullRequestView.swift` (a PR's tab), `ConversationView.swift` (its Conversation tab's web view), `DescriptionEditorView.swift` (the description's editor, shown in its place), `ReviewThreadViews.swift` (review threads laid between a diff's rows), `ReviewView.swift` (the header's Review button and "Finish your review"), `StackBar.swift` (the header's stack bar and the merge slot's "Merge #N first"), `Resources/conversation.html` and `conversation.css` (the conversation page's template), `RenderedMarkdownView.swift` (a markdown file rendered by GitHub, toggled from its diff's header), `PackageLockView.swift` (a hidden npm lockfile's package changes, toggled the same way), `ImageDiffView.swift` (an image file's versions, 2-up, swipe or onion skin, laid in its diff or, for an SVG, toggled like markdown), `GitHubWebPage.swift` (what both web views share: template, link handling), `Browser.swift` (every link sent to the default browser, marked when it's GitHub's), `Editors.swift` (opening a checkout in GoLand or VS Code), `PullRequestListView.swift`, `TodoListView.swift` (the lists' TODO mode, picked in the toolbar), `DiffView.swift`, `DiffCommands.swift` (the View and Review menus, and the review keys for the shown PR), `Bench.swift`
- `Sources/LoupeFakeGitHub/`: the fake GitHub the tests and the UI suite share: `FakeGitHub.swift` (the lists, lookups, checks, notifications and merges), `FakeConversations.swift` (conversations, reviewers, threads, reviews and edits), `FakeViewedFiles.swift`, `FakeMarkdown.swift`, `FakeRepository.swift` (real git repos as GitHub and a reviewer's machine hold them), `Checks.swift` (what a fake does with a request it can't answer), `FixtureGitHub.swift` (the fakes as one GitHub for a snapshot run) and `FixtureCheckouts.swift` (the fixture PRs' checkouts)
- `Scripts/ui-tests/`: the UI suite's scripts, run by `Scripts/ui-tests.sh`
- `Tests/LoupeTests/`: tests, with fixtures from atrium#2912 (the 4-file diff, and edge cases cut from the full diff)
- `Tests/LoupeInboxTests/`: PR list tests against an in-memory GitHub (`LoupeFakeGitHub`) that matches searches (author, review request, the viewer's reviews, `is:open`, `updated:>=`) and review-request, PR and status lookups against the PRs in `probe/pr-list.json` (with their checks and mergeability from `probe/pr-status.json`), checking the shape of each search it receives, plus `probe/graphql-error.json`, and serves notifications in `probe/notifications.json`'s shape for each changed PR, with 304s, `X-Poll-Interval` and refusals; checkout tests against real `git init` repos in temp search roots; diff and tab tests against `FakeRepository`, a temp bare origin exposing `refs/pull/<N>/head` with a contributor clone and a reviewer checkout
- `probe/`: GraphQL queries, raw responses and `NOTES.md`; `incremental-query.graphql` → `incremental.json` confirmed the `updated:>=` search, PR `state`/`mergedAt`/`closedAt`, `viewer { login }` and the `reviewRequests` shape
